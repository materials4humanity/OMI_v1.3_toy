# audit/

`baselines/` — one frozen observation-record file per criterion generation. See
`audit/BASELINES.md` for the table of generations and how to verify a claim against one
after later generations exist. The v1.3, seven-item-interface generation is
`baselines/v13-items7.json`, frozen at commit **`57f7db8`** ("M10.4 Part B: plan the
proposed-v1.4 constitutive track"), the last commit before `src/omi/` was touched by the
proposed constitutive extension.

It is the baseline for the audit-preservation gate (ADR-042, `docs/DECISIONS.md`;
M11.1, `docs/ROADMAP.md`): the claim that every quantity the repository measured
before M11 is byte-identical after M11, and that the extension only *added*
observations.

**A second generation exists since ADR-071, and it is the one to gate against today.**
`baselines/redesign-items8.json` (547 rows) is the **eight-item** interface — Core §4 item 1
split into 1a (state schema) and 1b (declared parameters) per `docs/V1.4-EDITS.md` E-46.
`v13-items7.json` is not superseded and is never edited: it remains the reference for any claim
stated under v1.3's seven-item criterion. What must not be done is compare a run of today's code
against it and read the difference as drift — the item criterion changed, which is exactly what a
generation label exists to make visible. Run the current check from a clean clone with:

```bash
scripts/check_audit_gate.sh audit/baselines/redesign-items8.json
```

and the historical one, which needs E-53's declared exceptions *and* still reports the ten rows
the item-1 split moved, with:

```bash
scripts/check_audit_gate.sh audit/baselines/v13-items7.json audit/e53-label-changes.json
```

Unlike `build/observations.json` (git-ignored, regenerated by every test run), this
file is committed and never regenerated in place — it is a fixed reference. It was
verified authentic by regenerating it from a fresh checkout of `57f7db8`
(byte-identical). See `REPRODUCE.md` §7 for the regeneration recipe.

**On what "267 observations" guarantees, precisely (ADR-069).** The file holds 267
rows. The gate compares by `(test, name)`, and all 267 `(test, name)` pairs are
distinct and are all compared on every run — **267 of 267 audited**, not a
name-deduplicated subset. This was not always true: the gate keyed on `name` alone
until ADR-069, and under that keying 44 of the 267 rows (16.5%) were silently never
compared, because 17 names are each recorded by more than one test
(`docs/V1.4-EDITS.md` E-60). Those 44 rows were checked for drift before the keying was
repaired and before this generation was frozen — zero drift found, recorded in
`audit/BASELINES.md`. Any report stating a coverage count for this gate should state
267 audited pairs from this point forward, not the un-audited "267 observations" the
count read as before the repair.
