# V1.4-EDITS.md

The ledger of everything this build has learned that the framework itself —
not this repository's implementation of it — should absorb before a v1.4
revision. CLAUDE.md §2: "the codebase's primary outputs are evidence and
*corrections*." This file is where a correction goes the moment it is found,
before any ADR records how the code copes with it in the meantime.

This document is written to be read **without** the repository: it quotes
rather than cross-references wherever the finding itself needs no repository
context to state or evaluate, and gives repository pointers only as
supporting evidence for readers who want to verify a finding, not as a
substitute for stating the finding in full.

**Finalised as a standalone document (M10.4, `docs/ROADMAP.md`), restructured
by root cause rather than discovery order.** Entry IDs (`E-NN`) are
permanent and never renumbered — every citation in `docs/COVERAGE.md` and
the ADR log points to them by number — but the order they are *presented*
in below groups them by the mechanism that produced them, not by when they
were found. Twenty-eight entries in discovery order is a log; grouped by
cause, it is a diagnosis. §0 states the evidence base this diagnosis rests
on and its limits. §1 is the summary. The entries themselves follow in six
groups, derived from the entries — not imposed on them — plus a seventh,
one-entry category for a finding that is a composition effect rather than a
defect in any single section, and an eighth for the one investigation that
found nothing wrong. The closing section states what this implementation
attempt could not test at all, and why.

---

## 0. Evidence base, and its limits

Every finding below was produced against two fully implemented domains
(flagship: a metallurgical process chain; contrast: an electrochemical cell
under service) plus four interface-only sketches (layer-wise additive
manufacturing and crystallisation/formulation, discussed throughout this
ledger; two further sketches named in `docs/SKETCHES.md`) declared against
Core §4's seven items but never simulated. All of it is **analytic**: every
evolution operator in both implemented domains is a closed-form function
chosen by this repository's own authors, not a fit to measured process
data, and every "ground truth" any oracle or comparison in this ledger
checks an estimator against is itself one of these same analytic
constructions — a constructed answer, not an independent measurement. No
field data of any kind entered this build, at any point. The one baseline
characterisation this ledger draws on (M10.2, informing E-26/E-27/E-28) ran
gradient-boosted trees and tabular regression against the authors' own
simulators, under the authors' own generative assumptions — record counts,
noise levels, and the trust-region/admissible-set bounds Core §5 needs were
all declared by the experimenter running the comparison, not drawn from
either domain's own declared interface (E-27's own finding is exactly that
neither interface supplies them). This distinction matters for how the two
kinds of finding below carry. Findings about framework **structure** — a
marker that is stale, a table that miscounts, a declaration checklist
satisfiable without the property it exists to establish, a slot mis-typed
against the framework's own stated definition — hold regardless of which
domain, real or toy, instantiates the framework: they are facts about the
text, established by direct quotation and cross-reference, not about any
one simulator's behaviour. Findings about framework **performance** — which
model wins a comparison, how large a measured bias is, whether a search
stalls at a particular record count — are only as strong as the generative
model that produced them. This repository's simulators are deliberately
simple enough to isolate one mechanism at a time cleanly, which is exactly
why they are unsuited to answering "how big is this effect in a real
production line" — that question needs field data this build never had,
and no entry below should be read as answering it. Each entry's own
**Confidence** field states which kind of claim it is making; this
paragraph is the general caveat that field does not repeat every time.

## 2. Core §2.5 (the body-indexed state): the framework's single most consequential unresolved dependency

Four entries trace directly to one unresolved section: Core §2.5, marked
`[Pass C]`, and named explicitly in CLAUDE.md §9's own anti-goal listing
("body-indexed state and the registration operator"). No other single
section in either document produces as many independent findings. Two
distinct failure shapes are visible, not one, and the distinction matters
for what fixing each requires:

- **E-14 and E-21 are *blocked by* §2.5 remaining unresolved** — a
  validation claim (Class-B dimensional reduction, Spec §4.4) and a
  declaration item (Core §4 item 1) both need body-indexing to exist in
  order to be honestly checked or filled, and it does not exist. These
  close only when §2.5 itself is written.
- **E-22 and E-25 show that §2.5's own proposed repair, once actually
  followed for a domain where it matters, is itself a type error** — not
  an absence, a mistake in what already exists. The `ν` slot is typed by
  §2.5's repair as locally-owned (a per-point field, coupled only to its
  neighbours) when Core §3.1's own definition of `ν` says it cannot be
  owned by a pointwise operator at all. This surfaced only because a third
  and then a fourth domain — additive manufacturing, then crystallisation,
  neither sharing any physics with flagship or contrast — needed `ν` to be
  *dominant* rather than incidental, which neither implemented domain ever
  does.

Both shapes were found by attempting to *use* §2.5, not by reading it in
isolation: flagship and contrast never needed it, since both declare `ν`
non-dominant, and it took two further, structurally unrelated domains to
surface the gap twice more independently. **E-24 immediately follows as
this pattern's own boundary case, confirmed rather than assumed**: a
*different* `[Pass C]` section (Core §3.4, hybrid continuous-discrete
structure) does *not* block the declaration item it superficially looks
like it should, and the distinction it draws — declaring a control space
versus evolving a hybrid system — is exactly the over-generalisation a
reader of E-21/E-22 alone might otherwise make from this section's
pattern.

## E-14 — Class B's dimensional-reduction claim (Proposition 4.2) cannot be validated as an emergent phenomenon at Tier I or Tier I½; only formula self-consistency is checkable until Core §2.5's body-indexed state resolves — one blocker, surfacing in two places (the flagship bend campaign and the ranking-inversion oracle)

**Target.** Spec §4.4 (dimensional reduction) read against Core §2.5 (the
body-indexed state, `[Pass C]`)

**Kind.** Correction

**Discovered.** Phase 2 review, prompted directly by the question "does
thickness-insensitivity emerge from sampling a driver field correlated over
`ℓ_D > t`, or only from `n_eff`'s branch selection?"

**Finding.** Spec §4.4 states the dimensional-reduction mechanism as a
consequence of the driver field's *spatial* correlation structure relative
to the process zone's own spatial extent: "correlation length `ℓ_D`
obtained from the two-point autocorrelation of the driver field... When
`ℓ_D` exceeds the zone thickness `t`, independent units tile only
in-plane." This presumes the driver field has a genuine spatial coordinate
*through the thickness* for `ℓ_D` to be compared against `t` in the first
place. Core §2.5 marks exactly this — "a production unit is not one state
but a field of states indexed by material coordinate — position along the
body, **through-thickness**, across-width" — `[Pass C]`, requiring "the
registration operator relating apparatus-frame observations to material
coordinates," and CLAUDE.md §9 lists "body-indexed state and the
registration operator (Spec §5.2)" as an anti-goal. The flagship's state
schema has no such coordinate: every component in
`src/omi_domains/flagship/state.py:10–20` is declared with dimension `1`
(a scalar), and `BendAngle.evaluate` (`src/omi_domains/flagship/
readouts.py:183–197`) varies only the *driving control* across its
through-thickness quadrature — `for i, eps in enumerate(strain): ...
operator.respond(control)` — never the bound `operator`'s state, so
`inclusion_content` (the defect-population component) is constant across
every quadrature point in a single evaluation. The `ℓ_D` the Phase 2
campaign estimates is measured along a *different* axis entirely (an
invented "site" coordinate standing in for separate specimens/locations,
`classb_bend.py`'s `_correlated_pareto_field`), never coupled to the
through-thickness axis at all. Consequently, the thin-regime
thickness-insensitivity this repository reports — both in the original
closed-form campaign and in the empirical resampling attempted for E-12 —
follows entirely from `n_eff`'s algebraic identity
(`(volume/thickness)/ℓ_D² = FIXED_FOOTPRINT_AREA/ℓ_D²`, thickness cancelling
against `volume = FIXED_FOOTPRINT_AREA × thickness`), confirmed
numerically: `n_eff` returns `12.755102040816325` at three different
declared thicknesses (`0.21`, `0.42`, `0.70`) in the same run. No sampling
of an actually-extended, actually-correlated through-thickness field ever
occurs, and per Core §2.5's own `[Pass C]` status this cannot be made to
occur without the body-indexed state refinement — which is out of scope
(CLAUDE.md §9) and was **not** synthesised to force this validation to look
more real than it is.

**Second surfacing, same blocker.** `tests/oracles/known_ranking_inversion.py`
is the repository's other place this shows up. Its module docstring frames
the oracle as "the quantitative content of Core §3.6's claim that 'the
two-tier formulation explains why rankings invert between specimen
thicknesses'" (Spec §4.4, Proposition 4.2), and
`KnownRankingInversionOracle.failure_probability` computes its result by
calling `omi.classb.n_eff` directly with two materials' hand-supplied
`correlation_length_a`/`correlation_length_b` and
`severity_a`/`severity_b` constants (`known_ranking_inversion.py:27-31`) —
there is no driver field, no spatial sampling, and no `estimate_correlation_length`
call anywhere in this oracle; `truth()` is simply the two process-zone
thicknesses (`THICK_ZONE_THICKNESS`, `THIN_ZONE_THICKNESS`) the parameters
were chosen to invert at. `test_the_inversion_is_driven_by_dimensional_reduction_not_by_severity_alone`
(`tests/oracles/test_known_ranking_inversion.py:53-75`) asserts
`n_eff_a_thick == n_eff_a_thin` and `n_eff_b_thin > n_eff_b_thick` — properties
of `n_eff`'s own regime-branch arithmetic under chosen constants, the same
kind of check as the bend campaign's thin-regime test, not a recovery of an
independently-generated ground truth from a spatially-correlated field. The
oracle is a legitimate unit-level check that the two-regime branch logic is
wired correctly (CLAUDE.md §7's "known by construction" philosophy applies
to *that* claim), but it is not, and was never built to be, evidence that
the reduction is an *emergent* consequence of sampling a real
through-thickness-correlated driver field — the same gap E-14 already
names for the bend campaign, surfacing here because this is the only other
place in the repository `n_eff`'s regime split is exercised at all.

**Proposed wording.** Append to Spec §4.4: "Proposition 4.2's dimensional
reduction is a claim about the driver field's spatial structure relative to
the process zone. An instantiation whose Tier I (or Tier I½) state has no
spatial coordinate through the suppressed dimension — i.e., every domain
before Core §2.5's body-indexed state refinement is adopted — cannot
observe the reduction as an emergent consequence of sampling; it can only
confirm that its own `N_eff` formula is evaluated self-consistently across
thicknesses. Reports MUST distinguish these two and MUST NOT present the
latter as validation of the former."

**Confidence.** High — every element (Core §2.5's `[Pass C]` marker,
CLAUDE.md §9's anti-goal listing, the flagship schema's all-scalar
declaration, `BendAngle`'s control-only quadrature loop, the numeric
identity of `n_eff` across three thicknesses, and `known_ranking_inversion.py`'s
absence of any driver field or `estimate_correlation_length` call) is a
direct quote or a direct re-run, not an inference.

## E-21 — Core §4 item 1 does not ask a domain to declare whether its state is point-valued or body-indexed, so an instantiation attempt can under-declare a genuinely field-valued domain without any warning — confirmed by a second, independent domain beyond E-14's Class-B-validation finding

**Target.** Core §4 item 1 ("State schema — occupants of each slot...
with resolution limits, and which slots are empty") read against Core
§2.5 (the body-indexed state, `[Pass C]`) and Core §3.1 (the four-slot
schema's own text, which describes `m` as including "order parameters,
indicator fields, orientation fields" — naturally field-valued
quantities, not scalars)

**Kind.** Addition

**Discovered.** M10.1 (docs/ROADMAP.md), attempting to declare item 1 for
the layer-wise additive processing sketch
(`src/omi_domains/sketches/layerwise_additive.py`) — the second of the
four interface-only sketches Spec §11.4/Core §7.3 call for.

**Finding.** `omi.state.StateSchema` (ADR-011, docs/DECISIONS.md) is a
flat, finite-dimensional vector: a fixed tuple of named, fixed-size
components. This is a sound Tier I representation for a domain whose
state is genuinely point-valued (or treatable as one representative
material point/SVE), and it is what every declared domain and sketch in
this repository uses — flagship, contrast, and the device-yield sketch
(E-19, E-20's own evidence base) all fill item 1 this way without strain.
Attempting the same move for layer-wise additive manufacturing exposes a
real limit: the domain's actual state is a field over a body that is
itself under construction, growing one layer at a time, and its dominant
slot by the domain's own physics — `ν` (whole-part residual stress and
distortion, the mechanism most responsible for warpage, often this
domain's dominant commercial failure mode) — is *definitionally* a
whole-body quantity (Core §3.1: "quantities that do not localise to a
material point because they are determined by a global balance"). A
single flat `StateSchema` instance can declare one representative build
location's state (which the sketch does, `LAYERWISE_ADDITIVE_SCHEMA`), but
doing so and calling it *the* state schema silently reverts the domain to
Tier I and discards exactly the physics that makes it commercially hard —
this is a forced approximation, not a genuine fill, and nothing in Core §4
item 1's own text prompts a declarer to notice the difference. Core §4
item 1 asks for "occupants of each slot... with resolution limits" — it
does not ask whether the state is point-valued (Core §2.4's Tier I) or
requires body-indexing (Core §2.5, `[Pass C]`), so a well-intentioned
instantiation attempt can under-declare a genuinely field-valued domain
exactly the way this sketch's first draft would have, without item 1
itself ever flagging it.

**Distinct from, but confirming the same root cause as, E-14.** E-14
found that Spec §4.4's Class-B *validation* claim (Proposition 4.2,
dimensional reduction as an emergent consequence of sampling a
spatially-correlated driver field) cannot be checked empirically without
Core §2.5's body-indexed state — a downstream *measurement* gap, on one
domain (flagship). This entry is upstream and domain-independent: it is
about Core §4 item 1's own *declaration* requirement not surfacing the
point-valued/body-indexed distinction at all, discovered via a second,
structurally unrelated domain (layer-wise additive manufacturing has no
metallurgical or electrochemical content in common with flagship). Taken
together, the two entries show Core §2.5's `[Pass C]` status blocks two
different things at two different points in the framework's own
pipeline — first declaring a domain's state (item 1, this entry), later
validating a specific claim about it (Class-B dimensional reduction, E-14)
— not merely one narrow measurement procedure.

**Proposed wording.** Append to Core §4 item 1: "State whether the domain's
state is point-valued (Tier I, Core §2.4) or requires body-indexing (Tier
II, Core §2.5); a domain that cannot honestly answer 'point-valued' MUST
say so and name which slot(s) force the issue, rather than silently
filling this item with a Tier I stand-in and leaving the approximation
undocumented." (Mirrors item 3's existing "if none [erasure operators], how
condition (b) of §3.9 is satisfied instead.") Whether this declaration
belongs in item 1 itself or in item 7 (`scale_structure`) is not settled by
this finding and is left to the authors — item 7 already carries some of
this weight, but currently only after a domain's state is declared, not as
part of declaring it.

**Confidence.** High that the representation gap is real and that this
sketch's item 1 required a forced approximation: it follows directly from
`omi.state.StateSchema`'s own definition (a fixed tuple of fixed-size
components) compared against the domain's actual physics (a growing,
spatially-coupled body whose dominant slot is a whole-body quantity by
Core's own definition of `ν`). Medium on the exact proposed wording's
placement (item 1 vs. item 7), since both readings of Core §4's text are
defensible and the framework authors would need to choose; high that
*some* explicit point-valued/body-indexed declaration requirement is
missing from item 1 as currently worded, since two independent domains now
show its absence in different ways (E-14's validation gap, this entry's
declaration gap).

## E-22 — ν is mis-typed under Core §2.5's own body-indexing repair: the repair fixes m, z, and Γ, and contradicts §3.1's own stated reason for carrying ν separately

**Target.** Core §3.1 (ν's definition: "quantities that do not localise to
a material point because they are determined by a global balance...
Carried separately because pointwise evolution operators cannot own
them") read directly against Core §2.5's own repair ("The Tier I state is
a section of a bundle over the material body: `s : X_body → S`. Evolution
acts pointwise or with local coupling")

**Kind.** Correction

**Discovered.** M10.1 (docs/ROADMAP.md), while declaring the layer-wise
additive processing sketch's item 1 (E-21) — noticing that `ν`
(`part_scale_residual_stress_field`) is defined as a whole-body quantity
*independent of* body-indexing being available at all, and re-reading
Core §2.5's own repair formula directly against Core §3.1's `ν` definition
rather than only recording "this slot costs the most" as E-21 did.

**Finding.** Core §3.1 defines `ν` by exclusion from the other three
slots: it is carried separately *specifically because* "pointwise
evolution operators cannot own" it — it does not localise to a material
point at all, by construction, regardless of how finely the body is
resolved. Core §2.5's repair for extended bodies states the Tier I state
becomes a section of a bundle over the material body, `s : X_body → S`,
with "evolution act[ing] pointwise or with local coupling." Read
literally, this indexes *all four* components of `S = (m, z, ν, Γ)` by
material coordinate `x`, giving `ν(x)` as a per-point value evolved
pointwise or via *local* coupling between neighbouring points.

This is the correct repair for `m`, `z`, and `Γ`: each is naturally a
per-point or per-local-region quantity (Core §3.1's own descriptions —
"resolved structural fields," "sub-resolution internal variables," "surface
and interface state" — never say otherwise), so body-indexing them and
coupling only locally is a faithful generalisation of Tier I. It is **not**
a correct repair for `ν`, because `ν` is defined in the very same section
as the one component of `S` that *cannot* be owned by a pointwise operator
in the first place. Indexing `ν` by `x` and coupling it only locally
directly contradicts the reason §3.1 gives for carrying `ν` separately at
all — a global-balance quantity, by definition, needs information from the
whole body (or the whole relevant coupled region), not from `x` and its
neighbours. Core §2.5's formula, as literally written, does not carve out
the exception its own companion section already established.

**Confirmed on one domain so far, with a specific prediction for a
second.** Layer-wise additive processing's `ν`
(`part_scale_residual_stress_field`, E-21) is exactly this: set by a
global heat-conduction balance across the whole build, not by any material
coordinate and its neighbours, and it is this domain's *dominant* slot by
its own physics (whole-part distortion/warpage) — the first domain in
this repository where `ν`'s nonlocality is load-bearing rather than
incidental. **Both implemented domains conceal this same tension**:
flagship's `levelling_field` and contrast's `potential`/
`concentration_overpotential` are both, by Core's own §3.1 definition,
equally global-balance quantities — but Core §7.1/§7.2 both declare `ν`
*non-dominant* for these two domains ("Dominant slot: `m`, `z`" for
flagship; "`Γ`" for contrast), so neither implemented domain has ever
needed to resolve `ν` with any spatial precision, and the mis-typing has
never surfaced as a practical problem. This entry is written before the
third sketch (crystallisation and formulation) is attempted specifically
because Core §3.1 names supersaturation — a global-balance quantity,
`ν`'s own worked example — as plausibly dominant there too; if the same
tension recurs on that unrelated physics, it stops being a single-domain
artifact and becomes a schema-level finding confirmed across three
independent domains. That check is pending and will be recorded as an
addendum to this entry once the crystallisation sketch is written, not
folded in speculatively now.

**Proposed wording (1 of 2 — the typing fix, revised for the degeneracy
argument).** The original form of this proposal read: "`ν` should be
typed as a field coupled to the point states, not as a component of
them," with `s(x) = (m(x), z(x), Γ(x))` for `x ∈ X_body` coupled to "a
single, shared, body-wide... `ν`." That wording is itself now shown to be
insufficient by the three-domain evidence below: it silently assumes
`ν`'s own indexing domain is *either* the full body `X_body` (a genuine
field) *or* a single global point (a bare scalar), and picks language
("body-wide `ν`") that leans toward the latter — but layer-wise
additive's `ν` needs the *former* (a genuine field, merely coupled rather
than owned pointwise) while crystallisation's needs the latter (a bare
scalar, no local value at all), and a domain with partial, regional mixing
(neither fully local nor fully global) would need something *between*
the two. "A field over the body" over-localises additive's case no less
than the original formula did if read as requiring a value at every `x`;
"a single global scalar" would under-localise a domain whose `ν` genuinely
varies by region. The corrected proposal: `ν` has its **own** domain
`X_ν`, declared independently of `X_body`, which may equal `X_body` (a
genuine spatially-resolved field — additive's case, when the body is not
well-mixed), a coarser subdomain or partition of `X_body` (an
intermediate case, not yet observed in this repository's domains but not
excluded by the argument), or the trivial one-point domain (a bare global
scalar — crystallisation's well-mixed case). Formally: `s : X_body →
(m, z, Γ)` (a genuine section, as §2.5 already states, evolving pointwise
or with local coupling) **coupled to** `ν : X_ν → 𝒱_ν` via a declared
coupling operator, with `X_ν` a separate, domain-specific choice — not
fixed to `X_body` and not fixed to a point. A correction that only offers
"field over the body" is no more complete than the original formula it
replaces; it must cover the degenerate case too.

**Proposed wording (2 of 2 — a separate edit: the coupling's dynamical
direction, not only `ν`'s spatial extent).** Fixing `ν`'s domain (above)
is not sufficient on its own. The three domains examined differ in *how*
`ν` couples to the point states, not only in *how localised* it is:
flagship's residual stress is **determined by** the point states — an
(at least approximately) instantaneous function of the current
local/history state, eliminable in principle as a derived quantity with
no dynamics of its own beyond what the point states already carry.
Crystallisation's supersaturation is **depleted by** the point states
under a conservation law — it carries its **own** dynamical state (the
remaining dissolved solute), driven by a consumption flux aggregated
across every growing crystal, decreasing as growth proceeds and
replenished only by external mass transfer; it cannot be eliminated as a
derived quantity, because at a given instant it depends on the
*integrated history* of consumption, not on the current point states
alone. Layer-wise additive's part-scale stress sits between the two:
spatially extended like a field (needing PDE coupling, unlike flagship's
simpler case), but still primarily *determined by* the accumulated
local/thermal history rather than depleted under a conservation law the
way supersaturation is. Core §3.1's own phrase — "determined by a global
balance" — reads naturally as the first case (`determined-by`) and does
not cover the second (`depleted-by`, with its own carried dynamics and
conservation constraint) at all; "balance" is doing ambiguous work,
gesturing at an equilibrium/flux relationship without distinguishing
whether `ν` is a snapshot function of the point states or a
conservation-coupled variable with memory the point states merely drive.
A corrected spatial type for `ν` (proposed wording 1 of 2) is not enough
without also declaring this coupling's dynamical character: an
implementation that types `supersaturation` correctly as a global scalar
per (1) but treats it as an instantaneous function of the point states
(the `determined-by` reading, appropriate for flagship) rather than as
its own conservation-coupled dynamical variable would get materially
wrong numerics — a corrected type with the wrong dynamics is no better
than the current under-declaration. Core §4 item 1 (or §3.1's own text)
should require a domain to state which coupling applies: `ν`
determined by the point states (an eliminable, derived quantity), `ν`
depleted by them under a declared conservation law (a genuine,
non-eliminable dynamical variable), or an intermediate case, naming which.

**Confidence.** High that Core §2.5's formula, read literally, omits `ν`'s
own already-stated exception, and high (see the addendum below) that the
degenerate/global-scalar case is real and not covered by "field over the
body" either — both are direct textual/structural comparisons, not
inferences requiring implementation evidence. Medium-high on proposed
wording (2 of 2)'s coupling-direction distinction: the three-way split
(determined-by / depleted-by / intermediate) is grounded directly in this
session's three sketches, but Core's own text would need to commit to
this specific taxonomy rather than some other framing of "coupling
character," which is a genuine framework-design choice, not a derivation
the text already implies.

**Addendum (after the crystallisation and formulation sketch, M10.1's
third).** Confirmed a third time, on physics with nothing in common with
either metal processing or electrochemistry.
`src/omi_domains/sketches/crystallisation_formulation.py`'s `ν` is
`supersaturation` — Core §3.1's *own named example* of this slot — and it
is plausibly this domain's dominant slot too, since polymorph selection
(the phenomenon this sketch exists to test) is itself supersaturation-
driven. The tension recurs in the same structural shape (Core §2.5's
literal repair still does not carve out `ν`'s exception), but with a
sharper limiting case than layer-wise additive's: in the well-mixed
idealisation common to batch crystallisers, supersaturation is not merely
a field satisfying a global PDE (as residual stress is, at least in
principle, still resolvable to *a* local value at each point) — it
collapses further, to a single shared scalar for the whole vessel, since
no crystal's local growth model can account for remaining solute without
reference to what every other crystal has already consumed. This is an
even purer instance of "pointwise evolution operators cannot own them"
than either previous domain supplied: there is not even a meaningful local
value to approximate in this limit, only a well-mixed reservoir shared by
construction. (An imperfectly-mixed real vessel reverts to the
field-with-global-coupling case, the same structure as flagship's residual
stress and layer-wise additive's part-scale stress — both regimes are
named in `docs/SKETCHES.md`.)

**This is no longer a single-domain artifact.** Three structurally
unrelated domains — metallurgical processing, additive manufacturing, and
crystallisation — each independently expose the same mis-typing the
moment `ν` is asked to be dominant rather than incidental, and the reason
is the same each time: Core §2.5's repair formula does not carry forward
Core §3.1's own stated exception for this one slot. Confidence is raised
from medium (pending confirmation) to **high** that this is a schema-level
correction Core needs, not an artefact of any one sketch's construction.
It is also this third domain's own well-mixed-limit degeneracy — a
supersaturation with no local value to approximate at all — that forced
the revision of proposed wording (1 of 2) above: "field over the body,"
this entry's original proposal, would have been exactly the same kind of
incomplete fix for crystallisation that Core §2.5's own formula is for
`ν` generally. A correction is only as good as its coverage of the
degenerate case, and the two-domain version of this entry did not yet
have that case in evidence.

**On Core §6.2's open problem.** Core §6.2 lists, among its open
problems: "Whether the four-slot schema is complete, or whether some
domain requires a fifth." Three domains' evidence now bears on this
question directly, but answers it in a different shape than the question
expects: none of the three sketches needed a fifth slot, and nothing in
this entry's finding suggests one is missing. Instead, one of the
existing four — `ν` — is mistyped in a way that recurs across every
domain where it is asked to be dominant. Core §6.2's open problem should
be restated to ask whether the four slots are each *correctly typed*, not
only whether a fifth is needed: a schema can be complete in *count* (four
slots, no missing occupant) while still being wrong in the *type* of one
of them, and the current wording only tests for the former.

## E-25 — Core §3.3's ensemble lift (pushforward, Markov kernel, Chapman-Kolmogorov) is linear in the measure, and does not cover the mean-field coupling Core §3.2's own "statistical representative volume" reading requires whenever the shared field E-22 found is depleted-by rather than determined-by

**Target.** Core §3.3 ("Lift to ensembles": pushforward `μ_{k+1} =
(G^{(k)}_evol(·,u_k))_# μ_k`; the Markov-kernel form `μ_{k+1} = ∫
K_k(s,·) μ_k(ds)`; "Chapman–Kolmogorov guaranteeing consistency of
composition") read against Core §3.2 (`𝒫(𝒮)`: "A 'statistical
representative volume' is an element of `𝒫(𝒮)`, not of `𝒮`") and Core
§3.6 (Class B: "`N = V/V_0` statistically **independent** sub-volumes"),
cross-referenced to `docs/V1.4-EDITS.md` E-22 (`ν`'s depleted-by
coupling, crystallisation's supersaturation)

**Kind.** Correction

**Discovered.** Following E-22 directly: asked whether the claim holds
that Core §3.3's stated lift — pushforward and the Markov-kernel form —
is linear in `μ` and silently excludes the mean-field/McKean-Vlasov case
E-22's `depleted-by` coupling implies. Verified against both Core's text
and this repository's implementation before writing this entry, per
instruction; the verification is reported in full below, not only the
conclusion.

**Verification of the claim.** Core §3.3's two lifts are both linear
operators on measures. Pushforward of a *fixed* map (`G^{(k)}_evol` here
depends on `u_k`, not on `μ_k`) is linear by construction:
`T_#(aμ_1+bμ_2) = aT_#μ_1+bT_#μ_2`. The Markov-kernel form is linear for
the same reason whenever `K_k(s,·)` depends only on the point `s`, not on
the current ensemble `μ_k` — which is exactly what Core §3.3 writes: `K_k`
carries a `k` subscript (time-dependence) but no `μ` argument anywhere in
the text. Chapman–Kolmogorov itself is the further, confirming signal:
`∫K_{k+1}(s',·)K_k(s,ds') = K_{k,k+2}(s,·)`, the classical identity Core
invokes for "consistency of composition," is a statement about a *fixed*
family of transition kernels; it does not hold in this simple form for a
kernel that depends on `μ_k` (a nonlinear/McKean-Vlasov Markov process
needs its own, more delicate propagation-of-chaos consistency argument,
not the textbook Chapman–Kolmogorov identity restated verbatim). Core's
own justification for the lift's consistency is therefore further
evidence that a `μ`-independent kernel is what is meant, not an
incidental omission.

This repository's own implementation matches that reading exactly:
`EvolutionOperator.lift` (`src/omi/operators.py:108-116`, ADR-012, generic
for every domain) is
```python
def lift(self, ensemble: Ensemble, control: Control) -> Ensemble:
    new_particles = np.stack(
        [self.step(ensemble[i], control).values for i in range(ensemble.n_particles)],
        axis=0,
    )
    return Ensemble(ensemble.schema, new_particles)
```
— `self.step` is called once per particle, independently, with no
reference to the ensemble as a whole. E-22's `depleted-by` coupling
(crystallisation's supersaturation, consumed by aggregate growth across
every crystal in a batch) requires exactly the opposite: `ν`'s own
evolution — and therefore, via `ν`, each particle's own growth rate — is
a function of `μ_k` itself (the current population's aggregate
consumption), not of that one particle's point state alone. A faithful
lift for a population coupled this way is nonlinear in `μ`: the
transition law itself must depend on the current measure (a mean-field /
McKean-Vlasov-type evolution), which neither pushforward nor Core's
stated Markov-kernel form expresses, and which no term in Core or Spec
names (`mean-field`, `McKean`, `Vlasov`, `population balance`, and
`interacting particle` all return zero matches across both documents).
**The claim holds**, on both counts asked for: Core §3.3's stated lift is
linear in `μ`, and does not cover the coupling E-22 found.

**The resolution turns on what `𝒫(𝒮)` denotes, and both readings are
required in different places.** Core §3.2's own gloss — "A 'statistical
representative volume' is an element of `𝒫(𝒮)`" — names the classical
materials-science RVE concept directly: one representative volume
containing many internal sub-regions, and Core §3.6 confirms this is the
same object ("representative volume element," "no RVE exists" for Class
B). Read this way, an "ensemble" is a population of sub-volumes *within
one body*, potentially sharing a common `ν` the way E-22 showed for three
domains. Core §2.1's sufficiency test reads oppositely: "prepare or
simulate specimen pairs with matched `s` but deliberately different
histories" — independent, separately-evolving specimens, each carrying
its own full state including its own copy of `ν` if any, with no
cross-specimen coupling at all. **Both readings are load-bearing, not
redundant**: §2.1's independent-specimen sense is exactly what pushforward
is correct for, and is exactly what this repository's `Ensemble`/`.lift`
mechanism actually implements everywhere it is called — chain rollout
(`src/omi/chain.py:69`), EnKF forecast (`src/omi/assimilate.py:168`),
`component_recoverability`'s R² estimation (`src/omi/erasure.py:110`),
and every domain's own `build_incoming_ensemble` (confirmed directly,
e.g. flagship's: independent per-component Gaussian draws, one row per
particle, no particle referencing any other). §3.6's RVE/sub-volume
sense is what Class B's weakest-link formula needs, under its own stated
independence assumption — and this repository's Class-B sub-volume
population (`_correlated_pareto_field`,
`src/omi_domains/flagship/classb_bend.py`) is generated by an entirely
separate mechanism that **never calls `.lift()` at all**. This
repository's code has therefore already avoided the tension operationally
— by accident of how the two mechanisms evolved, not by a stated
policy — while Core's text presents a single "ensemble on `𝒫(𝒮)`" concept
without saying the two uses need different mathematical treatment.

**Proposed wording.** Core §3.2 should disambiguate explicitly: `𝒫(𝒮)`
hosts at least two structurally different populations. (i) *Independent
replicas* — separate specimens, incoming units, or filter samples, each
evolving under its own full copy of the state with no cross-particle
coupling; Core §3.3's pushforward/Markov-kernel lift, and its
Chapman–Kolmogorov consistency argument, are exact and sufficient for
this case. (ii) *A representative volume's own internal sub-volume
population* — many sub-regions of one body, per Core §3.2's "statistical
representative volume" gloss and Core §3.6's RVE/Class-B usage,
potentially coupled through a shared, self-consistently-determined field
`ν` (Core §3.1) that is itself determined or depleted by aggregating over
the whole population. Whenever such coupling is present, Core §3.3's
linear lift does not apply as stated; a faithful lift needs the
transition law itself to depend on the current population (a mean-field/
McKean-Vlasov-type nonlinear lift), which Core neither names nor
provides. A related, further question this entry does not resolve: §3.6's
own independence assumption for case (ii) becomes questionable exactly
when the same coupling is present, since sub-volumes sharing a
depleted-by `ν` are, by construction, not independent — left open here as
a distinct, adjacent gap rather than folded into this entry's own claim.

**Confidence.** High that the two lift formulas are linear in `μ` as
written, and high that Core names no nonlinear/mean-field alternative
anywhere (direct textual facts, confirmed by search, not inference).
High that this repository's own code has, so far, only ever used
`.lift()` for the independent-replica case, confirmed by reading every
call site rather than sampling one. Medium-high on whether Core §3.2 is
the single correct place to add the disambiguation, as opposed to Core
§3.3 itself or a joint note spanning both — a genuine framework-editing
choice; high that the disambiguation is needed somewhere in this
neighbourhood of the text, since the two readings are both textually
present, both load-bearing elsewhere in Core, and not currently
distinguished from each other anywhere.

## 4. Declarations satisfiable without the property they exist to establish

Seven entries share one shape, named first and most directly by E-12: a
Spec procedure or a Core §4 declaration item can be satisfied exactly as
written while the substantive property it exists to establish is absent.
Spec §4.6 rung 4 can be satisfied by validating a formula against data
generated by that same formula, recovering it to machine precision by
construction rather than by measurement (E-12). Proposition 4.1's transfer
machinery can be exercised as a no-op identity function at `β ≈ 1` and
still count as "called" by every letter-of-the-law test (E-13). Spec
§9.1's OMI-2 line item can be satisfied by an arbitrary label string
standing in for a certificate Core §5 unconditionally forbids in its
unsound form (E-17). Spec §3.3's triage machinery can produce a labelled
result at a query point structurally incapable of showing what the label
exists to distinguish, and a domain's declared satisfaction of Core §3.9's
condition (b) can look confirmed by the same degenerate query point
(E-20). Core §4 item 5's "latency" can be satisfied by a modality that
contributes zero information to the condition it is meant to support,
because it arrives only after the process it would need to correct has
already finished (E-23). And Core §4 item 2 can be satisfied twice over —
once for readout sensitivity (E-26), once for a numeric admissible-set
bound (E-27) — while the control inverse it exists to license remains
either vacuous or unexecutable. No two of these seven are the same defect;
all seven are the same *form* of defect: a per-item, presence-only check
that cannot see past its own letter to the property behind it.

## E-12 — Spec §4.6 rung 4 does not distinguish "observed" from "recomputed," and a closed-form implementation can satisfy its letter while validating nothing

**Target.** Spec §4.6, rung 4 ("Volume-scaling exponent")

**Kind.** Correction

**Discovered.** Phase 2 review (post-implementation audit of
`src/omi_domains/flagship/classb_bend.py`, Tier I½/ADR-035), by re-reading
the committed rung-4 call site against Spec §4.6's text.

**Finding.** Spec §4.6 rung 4 reads in full: "Volume-scaling exponent — at
≥3 driven volumes, chosen to straddle ℓ_D where §4.4's reduction is
expected." This states *what* to compute (an observed exponent, compared
against a predicted one) but not *how* "observed" must be obtained. The
flagship's Tier I½ Class B campaign
(`src/omi_domains/flagship/classb_bend.py:205–209`) satisfies rung 4's
letter this way:

```python
def _failure_probabilities(thicknesses: FloatArray, ell_d: float, p0: float) -> tuple[FloatArray, FloatArray]:
    volumes = FIXED_FOOTPRINT_AREA * thicknesses
    counts = np.array([n_eff(float(v), ell_d, float(t)) for v, t in zip(volumes, thicknesses)])
    failure_probabilities = 1.0 - (1.0 - p0) ** counts
    return volumes, failure_probabilities
```

`failure_probabilities` here is the closed-form weakest-link formula
applied to `n_eff`'s own output — the same function
`validate_volume_scaling_exponent`'s `predicted_exponent` is supposed to
represent "the exponent n_eff's regime predicts." Fitting an exponent from
data generated by the formula being checked against necessarily recovers
that formula's own exponent, up to floating-point error: the committed
residuals were `2.22e-16` (bulk) and `-2.23e-16` (thin) — machine epsilon,
not a measurement. Re-running rung 4 with a genuine empirical
`P_fail` — drawing `round(N_eff)` i.i.d. sub-volume samples per trial,
taking the per-trial maximum driver value, thresholding, and repeating
across many trials — produces residuals of `-1.8e-3` (bulk) and `1.8e-2`
(thin): three to four orders of magnitude larger, and of the size genuine
sampling noise should be. The gap between "closed-form residual ≈ 1e-16"
and "empirical residual ≈ 1e-3–1e-2" is entirely attributable to Spec §4.6
never having said which of these two "observed" is required — an
implementation that never samples anything can still produce a rung-4
number and a low residual, and nothing in the text flags that number as
uninformative.

**Proposed wording.** Append to Spec §4.6, rung 4: "The observed exponent
MUST be obtained from data independent of the model being validated — by
direct measurement, or by Monte Carlo simulation of the weakest-link
construction (drawing `N_eff` sub-volumes, recording the per-trial maximum
driver value, thresholding) — never by substituting the predicted count or
probability back into the same formula used to state the prediction. A
rung-4 residual computed from the latter is not a validation and MUST NOT
be reported as one."

**Confidence.** High — the closed-form/empirical residual gap
(`1e-16` vs `1e-3`–`1e-2`) is a direct, reproducible measurement, not an
interpretation; re-run command and full output are in this session's
transcript (`empirical_rung4.py`, not committed — see the Phase 2 review
report for the exact figures per thickness).

## E-13 — Spec §4.3 gives no guidance for the degenerate β ≈ 1 case, where Proposition 4.1's transfer is a no-op

**Target.** Spec §4.3 ("Tail transfer: the defect-population → driver map")

**Kind.** Demotion

**Discovered.** Phase 2 review, by comparing the flagship Class B
campaign's declared physics-map exponent (`BETA = 1.0`,
`src/omi_domains/flagship/interface.py`'s item 4b) against Spec §4.3's own
worked example.

**Finding.** Spec §4.3's own "sanity check" is explicit that the point of
Proposition 4.1 is to demonstrate a *nontrivial* rescaling: "for defect-
initiated fatigue with a threshold scaling as `(√area)^-1/6`, the driver
exponent... is β = 1/6, so ξ_D = ξ_a/6: a heavy-tailed inclusion population
produces a markedly *lighter*-tailed strength distribution... **Any
implementation of §4 SHOULD reproduce a known scaling of this kind as a
check on Ψ**." At β = 1, `tail_index_transfer(xi_a, beta) = beta * xi_a`
(`src/omi/classb.py:27–32`) returns `xi_a` unchanged — the flagship
campaign's own `xi_d_hat` is numerically identical to `xi_a_hat` in every
run (confirmed: `xi_d_hat == pytest.approx(xi_a_hat)` passes in
`tests/test_flagship_classb_bend.py`). `estimate_tail_index_hill` and
`tail_index_transfer` are both genuinely *called* (`classb_bend.py`'s
`xi_a_hat = estimate_tail_index_hill(...)` and
`xi_d_hat = tail_index_transfer(xi_a_hat, BETA)`, plus a second, internal
call inside `join_driver_tail`), so by the letter of "is the symbol
referenced," Proposition 4.1's transfer machinery is exercised. But at
β = 1 it is exercised as the identity function — no rescaling is ever
observed, so Spec §4.3's own "SHOULD reproduce a known scaling... as a
check on Ψ" is not actually satisfiable at this declared exponent, and
nothing in Spec §4.3 says whether β ≈ 1 is a legitimate physics-map
declaration or a sign that Ψ is too weak to be worth declaring at all
(as opposed to measuring the driver's own tail directly and skipping the
transfer machinery entirely).

**Proposed wording.** Append to Spec §4.3: "Where the physics map's
exponent β is at or near 1, the transfer `ξ_D = β·ξ_a` is at or near the
identity and does not exercise Proposition 4.1's substantive claim. An
implementation declaring β ≈ 1 MUST additionally report that the transfer
step is degenerate for that readout, and SHOULD state whether the driver's
tail was measured directly instead. §4.6 rung 3 (fractography) remains the
required check on Ψ regardless of β, but rung 3 alone cannot distinguish a
correctly-declared β ≈ 1 from an undeclared or incorrectly-omitted Ψ."

**Confidence.** Medium — the degeneracy at β = 1 is a direct reading of
`tail_index_transfer`'s formula and is not in dispute; whether Spec should
require additional reporting at β ≈ 1 (as opposed to leaving it to
implementer judgement) is a framework-design choice, not a derivation the
text already implies.

## E-17 — Spec §9.1's OMI-2 "reachability certificates" line item does not, at the level-table text itself, restate the soundness requirement Core §5 makes unconditional — and this repository's own conformance.py demonstrates the gap is real, not hypothetical

**Target.** Spec §9.1 (OMI-2 row, "reachability certificates (§7.1)") read
against Core §5 ("Learned reachable sets are unsound and **cannot discharge
this contract**; sound certificates are constructed from the invariants
declared in §4, item 6") and Spec §7.1's own boxed definition ("A
**reachability certificate** is a functional `Φ`... with a provable bound...
Any target with `Φ` beyond the achievable bound is **provably**
unreachable")

**Kind.** Correction — to Spec §9.1's text, and to this session's own
earlier conclusion on the same question.

**Discovered.** Direct challenge to this session's prior finding
(`docs/COVERAGE.md`'s S-9.3 "Depends on" cell, first version): "presence-only
checking being satisfiable by an unsound certificate is not the absence of a
defect." Re-verified rather than defended.

**Finding.** The prior conclusion — "not a regime defect, since Spec §7.1's
hierarchy anticipates weaker, unsound-but-present certificates that would
satisfy [OMI-2's presence check]" — conflated two different things and does
not survive a careful re-read. Spec §7.1's hierarchy (forward sampling →
latent-space over-approximation → invariant certificates) lists three
*workflow tools* of increasing strength, but its own **definition box**
("A reachability certificate is a functional `Φ`... with a provable
bound...") describes only the last, sound kind — forward sampling and
latent-space over-approximation are not instances of "a reachability
certificate" under Spec's own definition; they are weaker, separately-useful
artefacts on the way to one. Core §5 is unconditional and names the
excluded case explicitly: "Learned reachable sets are unsound and **cannot
discharge this contract**." Read together, Spec §9.1's OMI-2 line item —
"reachability certificates (§7.1)" — by cross-reference already means the
sound kind; there is no textual gap in what Spec *says*, once the
cross-reference into §7.1's definition is chased.

**The gap is that this repository's own implementation did not chase it,
and nothing forced it to.** `ConformanceInputs.reachability_certificates`
(`src/omi/conformance.py:221`) is typed `tuple[str, ...] | None` — a tuple
of **strings**, not `tuple[omi.inverse.ReachabilityCertificate, ...]`. It is
entirely decoupled from `omi.inverse.ReachabilityCertificate`, the actual
sound, `Φ(s)=w·s` dataclass (ADR-031). `_check_satisfied`
(`src/omi/conformance.py:379-380`) checks only
`inputs.reachability_certificates is not None` — a caller could satisfy
`reachability_certificates_reported`, and therefore OMI-2's line item, by
passing a tuple of arbitrary description strings, with **no type-level
guarantee that a real certificate object of any kind — sound or unsound —
was ever constructed.** This is not a hypothetical risk: it is the literal
current state of this repository's own conformance-reporting code, following
directly from ADR-028's general "presence, not accuracy" philosophy (correct
for most OMI-line items — e.g. "sufficiency test run and reported" is
genuinely presence-only, its accuracy read from the residual, not
gatekept) applied without exception to a line item Core §5 treats
differently in kind: not a reporting-completeness matter but an
unconditional prohibition on the artefact class. ADR-028's philosophy is
right for most of §9.1's table and wrong for exactly this row, and nothing
in `conformance.py` or its own ADR flags the row as an exception.

**Answering the question as posed.** Not "OMI-2 as written can be claimed
with an artefact Core forbids" in the sense of a framework text defect —
Spec's own definition, chased fully, already excludes it. It **is** true
that OMI-2 **as implemented in this repository** can be so claimed, because
the implementation's type does not encode what the cross-referenced Spec
text requires. The defect is real and is best located at the boundary
between the two: Spec §9.1's level-table entry is terse enough ("reachability
certificates (§7.1)") that an implementer applying the *general* philosophy
established for the rest of the table (presence, not accuracy) — exactly
what this repository's own author did — will not be warned that this
particular row is the one exception where presence of the wrong kind is
equivalent, in Core's own terms, to absence. The same composition trap this
session's dependency sweep already found once (E-15: a diagnostic
satisfying its own stated MUST can still miss the dominant thing that
matters) recurs here at the conformance-gate level.

**Proposed wording.** Append to Spec §9.1's OMI-2 row, inline, not merely by
cross-reference: "reachability certificates (§7.1) — **sound**, per §7.1's
definition; a forward-sampling or other unsound artefact (Core §5) MUST NOT
be reported against this requirement, and an implementation checking for
this line item's presence MUST verify the reported object is of the sound,
invariant-based kind, not merely that *something* was supplied."

**Related, but not itself a framework finding — fixed.** `reachability_certificates`
is now typed `tuple[ReachabilityCertificate, ...] | None`
(`src/omi/conformance.py:221`), not `tuple[str, ...]`, so the type system —
not just documentation — prevents what this entry found: a caller can no
longer satisfy `reachability_certificates_reported` with an arbitrary
label. This was an ordinary implementation-defect fix, not itself a
V1.4-EDITS-worthy framework correction (CLAUDE.md §10 reserves this file for
the framework, not this repo's own bugs); recorded here because the defect
was exactly what E-17's framework-level finding is about. No existing test
constructed `ConformanceInputs` with a non-`None`
`reachability_certificates` value (the field was `None` everywhere, matching
the OMI-2 gap C-5a already records — no test imports both `omi.inverse` and
`omi_domains`), so this closes the loophole structurally without changing
any current test's claimed conformance level; it only takes effect the
first time a domain actually supplies a certificate, at which point it can
no longer be a bare string. Residual risk not closed by typing alone: a
caller can still construct a type-correct `ReachabilityCertificate` for an
invariant it does not actually hold (a fabricated `weight` vector) — that
relies on the same good faith every other OMI line item already depends on,
per the Confidence note below.

**Confidence.** High — the type mismatch is a direct code citation
(`src/omi/conformance.py:221,379-380`), and the Core §5 / Spec §7.1 textual
argument quotes both sources directly rather than paraphrasing. Medium for
whether "unenforceable at the conformance level" (the alternative this entry
was asked to weigh) is entirely ruled out: a sufficiently motivated caller
could still fabricate a type-correct-but-substantively-fake
`ReachabilityCertificate` (e.g. a `weight` vector for an invariant it does
not actually hold), so type-checking closes the gap this entry found but
does not make the honesty of the underlying claim self-enforcing — that
residual relies on the same good faith every other OMI line item already
depends on.

   suite Core §7.2 declares "genuinely poor"). There is no near-diagonal
   observation to `time_index=0` in either domain, so `near_diagonal_share`
   is `None` for every direction and OBSERVED is unreachable at this query
   point regardless of how good the eventual sensor suite is downstream.

2. **OBSERVED_BUT_IRRELEVANT and MARGINALISABLE both require influence
   below the median, and both domains' target sets push that median to
   exactly zero.** Flagship declares two readouts derived from one
   three-component-sensitive constitutive operator; contrast declares one
   scalar readout touching two components — in both cases the target set is
   low-dimensional enough relative to state size that well over half of all
   eigendirections carry *exactly zero* influence, making `influence_median
   == 0.0` (confirmed directly for both domains). Since influence is a
   quadratic form (never negative) and "influential" means `influence >=
   influence_median`, a zero median makes *every* direction influential by
   definition — the non-influential branch is empty by construction
   whenever a target set is sparse enough relative to state dimension to
   zero out the median, which is not a hand-picked adversarial
   configuration.

Only INFERRED and DANGEROUS remain reachable. Contrast does produce
`Triage.INFERRED` directions (4, weighted search per instruction) — but with
danger scores `[3.1e-12, 0.0, 0.0, 0.0]`: present as a label, not as a
demonstration that a *dangerous* direction is specifically inferred rather
than observed, since contrast's single sensor and single target barely
touch most directions in the first place. Flagship's 4 INFERRED directions
score `[8.0, 4.3, 0.0, 0.0]` — nonzero, but flagship is the domain condition
(a) (erasure) covers, not condition (b), so a nonzero flagship INFERRED
score is not itself evidence bearing on observation-density sufficiency.
Neither domain, at this query point, supplies what the INFERRED category
exists to showcase: a genuinely dangerous direction identifiable
specifically because the chain model propagates information from a
downstream sensor, with OBSERVED structurally ruled out *for that
direction* rather than ruled out for every direction by construction before
any direction-specific reasoning happens.

**This bears directly on Core §3.9's error-control dichotomy, and the
bearing is not confirming.** Core §7.2 declares contrast satisfies condition
(b) ("observation density sufficient for assimilation to correct drift") by
declaration; Core §7.3 states the claim explicitly: "the absence of erasure
is the load-bearing inversion... the answer being continuous assimilation
from telemetry, which is exactly what condition (b) of the dichotomy
predicts." This is the first evidence in this repository bearing on that
declared claim, and what it shows is: contrast's single terminal-voltage
sensor leaves `influence_median == 0.0` and produces INFERRED directions
with ~zero danger score at `time_index=0` — consistent with condition (b)
holding, but equally consistent with the declared target set simply being
too sparse at this query point to expose whether it holds. Whether
contrast's condition-(b) claim survives at a query point and target set
where danger scores are *not* uniformly near zero is untested by this
repository as it stands, and Spec §3.3 gives no instrumentation-condition
language that would have flagged `time_index=0` as an uninformative choice
before the test was run.

**Proposed wording.** Spec §3.3 should state the instrumentation conditions
under which the triage is non-degenerate, at minimum: (1) OBSERVED is
reachable at query index `k` only if the sensor suite includes an
observation within the declared `near_diagonal_window` of `k` — an
implementation MUST report, alongside any triage result, whether such a
sensor exists at the query point, since its absence silently collapses
OBSERVED into INFERRED for every direction and is structural, not
incidental; (2) an implementation MUST flag when `influence_median` (or
`uncertainty_median`) at a given query point is degenerate in a way that
collapses one side of the corresponding split for every direction, since
this is a property of the declared target set's dimension relative to
state size, not of instrumentation quality, and MUST NOT be read as
evidence that no non-influential/non-identifiable directions exist.
Separately, Core §3.9's error-control dichotomy should note that a domain's
declared satisfaction of condition (b) is not validated merely by producing
INFERRED-labelled directions with near-zero danger scores — that outcome is
consistent with condition (b) holding, but equally consistent with the
declared target set being too sparse to test it — and that a claim of
condition-(b) sufficiency should be checked at a query point and target set
chosen so OBSERVED is structurally reachable, making INFERRED-vs-OBSERVED a
live choice rather than a foregone one.

**Confidence.** High for the two structural mechanisms — both are direct
citations of `danger_triage`'s own comparison logic
(`src/omi/observability.py`) plus directly observed values
(`influence_median == 0.0` for both domains, recorded in
`build/observations.json`), and the mechanism is generic to any domain
whose target set is sparse relative to state dimension and whose sensors
are all downstream of the query index — a common configuration, not a
contrived one. Medium for the dichotomy-linkage claim: it correctly states
what this test does and does not show (this session's evidence neither
confirms nor refutes condition (b) for contrast), but a stronger confidence
would need a targeted follow-up — a query point/target set for contrast
where OBSERVED is structurally reachable — that this entry does not itself
perform, consistent with reporting the inconclusive finding rather than
manufacturing a stronger one.

## E-23 — Core §4 item 5 cannot express that an observation arrives only after the chain ends, so a domain can appear to satisfy Core §3.9's condition (b) while satisfying it not at all

**Target.** Core §4 item 5 ("Observation suite — available modalities,
what each constrains, latency and coverage") read against Core §3.9's
error-control dichotomy, condition (b): "observation density sufficient
for assimilation to correct drift"

**Kind.** Addition

**Discovered.** M10.1, layer-wise additive processing sketch
(`src/omi_domains/sketches/layerwise_additive.py`'s observation suite):
post-build X-ray CT is rich but strictly terminal — available only once,
after the build has already finished — and the same sketch's only
declared erasure, `hot_isostatic_pressing` (E-21), is *also* terminal
(a post-build step, not mid-chain), which is what exposed the concern from
both sides at once rather than only one.

**Finding.** Core §4 item 5 asks a domain to declare "available
modalities, what each constrains, latency and coverage" — "latency" is
present in the text, but nothing in the item's wording forces a
distinction between two qualitatively different kinds of delay: an
observation that arrives with *some* lag but still *during* the chain, in
time to inform assimilation and correct subsequent evolution (flagship's
in-die force/torque sensing at index 1, contrast's terminal voltage still
within one assimilation cycle), and an observation that arrives only
*after* the chain has already run to completion (this sketch's CT scan,
evaluated once, post-build). A domain can write "latency: available after
the build completes" for a modality and thereby satisfy item 5's literal
requirement to *state* a latency — while that same statement, correctly
read, means the modality contributes **zero** information to Core §3.9's
condition (b), since "assimilation to correct drift" requires correcting
drift as it occurs, and an observation that exists only after the process
ends cannot correct anything within that process. Nothing in item 5's
wording, or in condition (b)'s own wording, currently forces this
distinction to be drawn — a domain (or an implementation reading a
domain's declaration) can satisfy item 5's presence check and believe
condition (b) is thereby addressed, when the terminal-only modality
addresses it not at all.

**The same sketch shows this can fail on both sides of the dichotomy at
once, invisibly.** Layer-wise additive's only declared erasure
(`hot_isostatic_pressing`) is also terminal — during the actual build,
condition (a) (contractive erasure bounding accumulated error) is not
satisfied either, since defects compound layer-to-layer rather than being
damped until HIP is applied after the fact. A domain could therefore
declare a non-empty erasure inventory (item 3) *and* a rich observation
suite (item 5) and appear, on the two relevant declarations alone, to
plainly satisfy the dichotomy — while in fact satisfying **neither**
condition in the sense the dichotomy requires (control of error *during*
the process the framework actually models). Both conditions can fail
invisibly behind declarations that are individually true and collectively
misleading.

**Proposed wording — two pasteable additions.** (1) Append to Core §4 item
5: "For each declared modality, state explicitly whether it is available
*within* the chain (in time to inform assimilation and affect subsequent
evolution) or only *after* the chain has completed. These are
qualitatively different kinds of latency, and 'latency' alone does not
force the distinction." (2) Replace Core §3.9's condition (b) with:
"observation density, restricted to observations available *during* the
chain's execution, sufficient for assimilation to correct drift" — making
explicit what "assimilation" already implies (this repository's own
sequential, in-chain assimilation machinery) rather than leaving it to be
inferred.

**Confidence.** High that item 5's current wording does not force the
in-chain/post-chain distinction, and that this domain's own declaration
(CT: terminal; HIP: terminal) is a genuine, not manufactured, instance
where both dichotomy conditions could be misread as satisfied while
neither actually holds mid-chain — this follows directly from the
sketch's own declared items 3 and 5. Medium on whether restating condition
(b) is the more effective lever than fixing item 5 alone, since condition
(b)'s own word "assimilation" already carries a sequential, in-chain
connotation a sufficiently careful reader might infer unaided; this
entry's proposal removes the need for that inference rather than
correcting a case where the current wording is silent on the underlying
requirement.

## 5. The interface has no declarable category for a kind of thing the physics requires

Four entries share a root distinct from §4's. §4 is about a declaration a
domain *can* make being satisfiable without the property behind it. These
four are about a declaration a domain **cannot make at all**: the seven items
have no slot for something the physics is load-bearing on, so a domain that
knows the fact has nowhere to put it and the framework has no way to use it.
Four such categories are missing — a **static parameter** that parameterises
operators without being transported by them (E-29), the **symmetry group**
acting on the state (E-30), the **characterisation suite** that fixes the
`m`/`z` boundary (E-31), and a **domain constitutive form** among the hard
constraints (E-32).

The four are not equally invisible, and the difference is worth stating.
E-32's missing category is the one the framework actively rejects — the
declaration type refuses a constitutive form by name rather than merely
lacking a field for it. E-31's is asked for and then dropped: Core §4 item 1
requires "resolution limits" and the shared declaration object has no field
that could carry one. E-30's is delegated to domains with no destination:
Spec §2.2 prescribes equivariant architectures, the implementation
deliberately defers the equivariant layer to each domain as domain content,
and no item lets a domain say which group acts on which components. E-29's
is the one the framework already has the vocabulary for and no category:
Core §6.2 asks "how much of an operator is composition-conditional versus
composition-**parameterised**" while nothing in the schema can mark a
component as a parameter.

**A fifth instance of this root cause is filed elsewhere, and is cross-
referenced rather than moved.** E-33's second finding is that Core §4 item 7
requires "where homogenisation is applied, between which scales" and nothing
anywhere asks for the **temporal** counterpart — the resolution at which
operators are defined, and the fastest mode timescale the declared state is
meant to represent. That is this group's shape exactly, and it is E-31's shape
in the time axis specifically: an item asks for a resolution and the
declaration has no field that could carry it. E-33 is nonetheless filed in §6,
because its *primary* finding is a diagnostic blind to the metric that swings
it by sixteen orders of magnitude, and an entry is filed under the root cause
of its centre of gravity rather than split across two. A reader auditing "how
many missing categories did this find" should count **five**: the four below
plus E-33's temporal resolution. A reader auditing §6 should still find E-33
there. Both classifications are true; neither is a reclassification of the
other.

The four below are also, with E-33, the five entries whose provenance is a domain
assessment rather than an implementation attempt (`docs/PHYSICS-ADEQUACY.md`,
marked `[domain-assessment]` in each `Discovered.` field). That distinction is
load-bearing and is not flattened here: the twenty-eight entries in §2–§4 and
§6–§9 were found by attempting to build the framework and hitting something
that would not build; these four were found by reading the framework against
a physical system it claims to describe and noticing an absence. An absence
is harder to hit by building, because a missing category does not raise an
error — it silently forces the declarer into the nearest available slot,
which is exactly what E-29's verification found flagship had already done
without anything flagging it.

## E-29 — The schema cannot distinguish evolving state from static parameterisation, so "static by design" and "should evolve but does not" have identical structural signatures and a readout depending only on parameters cannot be flagged; Core §6.2 already names the consequence it cannot express

**Target.** Core §3.1 (the `m` slot's occupant list, which includes
"composition fields") and Core §4 item 1 ("State schema — occupants of each
slot `(m, z, ν, Γ)`, with resolution limits, and which slots are empty"), read
against Core §6.2's own open problem — "Transfer of evolution operators across
composition families: how much of an operator is composition-conditional versus
composition-**parameterised**" — and against Core §2.6's property/performance
distinction, which supplies the legitimate case this gap makes indistinguishable
from a defect.

**Kind.** Addition

**Discovered.** **`[domain-assessment]`** — `docs/PHYSICS-ADEQUACY.md` §3.1 and
§3.7, an external assessment written from flat-rolled steel processing against
the Specification and this build's milestone reports, *without reading the
source*. Not an implementation-attempt finding: nothing in this repository
failed to build on account of it, which is the point — a missing category
raises no error. Both sections were verified against the code before filing,
and they turned out to be one finding at two levels, so they are filed as one
entry.

**Finding, part 1: the missing category.** Core §3.1 lists "composition fields"
among the `m` slot's occupants, so the framework's answer to "where does
chemistry go" is: into a state slot, alongside quantities that genuinely
evolve. But a large class of physically load-bearing quantities are not state
in the sense the slots mean — they are fixed upstream and thereafter
**parameterise every downstream operator without being transported by any of
them**. In flat-rolled steel, hardenability sets the transformation diagram,
carbon sets the martensite-start temperature, microalloying sets precipitation
kinetics and the recrystallisation-stop temperature: none evolves in the bulk,
all change what every subsequent operator does. A transformation operator for
one grade and one for another are not two unrelated operators; they are one
operator at two parameter values, and neither the schema nor the interface can
say so. **Core §6.2 already states the consequence and lacks the category that
would address it** — its open-problem list asks how much of an operator is
"composition-*parameterised*", so the framework has the word and no place to
declare a parameter.

Verified: `StateSchema` (this repository's item-1 implementation) declares
components as `(Slot, str, int)` triples — slot, name, dimension — with no
field of any kind marking a component static, and `InstantiationDeclaration`
has exactly seven fields (`state_schema`, `control_space`,
`erasure_inventory`, `readout_catalogue`, `observation_suite`, `invariants`,
`scale_structure`), none a parameter set.

**Finding, part 2, and this is the load-bearing half: the gap is one of
*detectability*, not only of expressiveness.** Because a component nothing
evolves is, in the schema, exactly the same kind of object as one that evolves,
**"static by design" and "should evolve but does not" have identical structural
signatures.** Nothing distinguishes them — not the schema, not the seven items,
not any conformance check. The immediate consequence is that a **readout
depending only on such components cannot be flagged structurally**: whether it
is a legitimate parameter-dependent readout or a symptom of operators that fail
to move the state they should, the declaration looks the same.

**And the framework supplies a legitimate case that makes the confusion
genuine, not hypothetical.** Core §2.6 distinguishes a *property* — "a
functional of the constitutive operator alone", invariant under configuration
within a test class — from a *performance*, which requires geometry. A property
readout is therefore *supposed* to be invariant to the configuration of the test
that measures it. It is emphatically **not** supposed to be invariant to the
processing controls that produced the state it reads: the constitutive operator
is extracted *from* the state, and the process is what shapes that state. Those
two invariances are different claims, the first sanctioned by Core §2.6 and the
second a modelling error — and the framework has no vocabulary separating them.
An implementation can satisfy Core §2.6's property definition exactly, look
correct on that axis, and be process-invariant for an entirely unrelated and
wrong reason.

**Recorded repository defect — this build is the worked example of what the
missing category costs.** *(Marked as a repository construction fault, not a
framework finding: CLAUDE.md §10 reserves this ledger for the framework. It is
recorded inside this entry, on the precedent of E-17's own marked repo-fix
note, because it is the evidence for the framework claim above and is
unintelligible separated from it.)*

`docs/PHYSICS-ADEQUACY.md` §3.7 predicted that flagship's readouts are
invariant to its controls for one of two reasons — "either the operators do not
change those state components, or the constitutive readout ignores them." **It
is the first; the second is refuted.** Flagship's constitutive operator reads
three real components (`inclusion_content`, `prior_grain_size`,
`accumulated_hardening`) and ignores nothing. But in *both* of flagship's
evolution operators, all three carry relaxation rate exactly `0.0` **and**
control-coupling gain exactly `0.0` — not small, exactly zero — so they are
invariants of the entire chain. Measured: aggregate hardness is
`106.12805030058055` on the incoming state and `106.1280503006` after the full
chain at heating intensities `2`, `8` and `14` — identical to ten decimal
places across a sevenfold control sweep — with `prior_grain_size` unchanged at
`19.603685`; the Class-B bend readout, routing through the same constitutive
operator, is likewise pinned at `107.1280503006`. There are two independent
breaks: separately from the frozen components, the only component in the whole
schema with a nonzero control-coupling gain is `coating_thickness`, which no
readout on the hardness path reads. Metallurgically the diagnosis is exact —
soak temperature and time change grain size, and flagship's grain size has
relaxation rate `0.0` under soak.

**Those three components are precisely flagship's three de-facto-static
components** (identified independently by scanning both operators' coefficients
for rate and gain both zero). So the physics error is not an unrelated slip: it
is a readout depending only on static parameters, in a domain that also
implements Core §2.6's property definition correctly — which is exactly the
confusion part 2 describes, occurring in practice, undetected across nine
milestones of validation. **This is what E-26 detected the symptom of.** E-26
found the invariance and filed it as a Core §4 item 2 gap (the interface does
not require declaring readout sensitivity); that finding stands. What it could
not see is that the invariance is itself a modelling error rather than a
truthful property of a legitimately control-insensitive domain — and E-26's
proposed fix, a sensitivity declaration, would have produced the truthful
declaration "no readout responds to any control", which detects without
distinguishing and without repairing. **The repair is not performed here** and
is recorded as out of scope: it would make the control inverse non-vacuous,
enable the constitutive-form extrapolation test E-32 leaves untested, and make
this build's baseline comparison meaningful on the control axis for the first
time — one task with several payoffs, needing its own decision record.

**One correction to the assessment's own specifics, recorded rather than
absorbed.** §3.1 states composition "sits in `m` as 'composition fields', where
it is inert." That describes Core §3.1's schema *definition* accurately, but
not flagship's instantiation: flagship declares **no composition component at
all**, and its nearest composition-like quantity, `inclusion_content`, sits in
`z`. The finding is unaffected — it concerns the schema's expressive power, not
which slot any one domain chose — but that illustration should not be cited.

**A fifth slot is the wrong fix.** These quantities are not state, and a slot
for them would subject them to every claim the framework makes about state —
pushforward under evolution, Axiom S sufficiency, erasure, assimilation — all
vacuous or misleading for a quantity nothing transports.

**Proposed wording.** (1) **`[authorial-choice]`** — the category's *content*
below is settled by the finding; its *placement* is not, and this entry cannot
resolve it: an eighth item to Core §4's declaration makes the parameter/state
distinction as prominent as the state schema itself, while a sub-item to item 1
keeps the seven-item count that Core §4 and §7.2's comparison table both lean
on. The finding is indifferent between them; finding 5's question of whether
seven is a closed list is not, and the authors should settle that first. Add,
then, either an eighth item to Core §4's declaration or a
sub-item to item 1: "**Parameters** — quantities fixed upstream of the chain
that parameterise one or more evolution or readout operators without being
transported by any of them, each declared with the operators it parameterises.
A quantity that evolves in one region and is fixed in another (the same
chemical species fixed in the bulk and evolving at a surface or interface) MUST
be declared in both roles, naming the region for each. A declaration MUST NOT
place a quantity in a state slot solely because no parameter category exists:
an operator declared as parameterised by `p` is thereby claimed to be *the same
operator* at different values of `p`, which is the claim §6.2's open problem on
cross-composition operator transfer requires in order to be stated at all."
(2) And the check the category makes possible, appended to Core §4 after the
items: "An instantiation MUST report, for each declared readout, whether its
state dependencies intersect the components some declared evolution operator
modifies. A readout depending only on declared **parameters** is legitimate and
is what §2.6's property/performance distinction describes. A readout depending
only on components declared as **state** that no declared operator modifies is
a defect — either the operators or the schema is wrong — and MUST be reported as
such. Without the parameter/state distinction of (1) these two cases are
indistinguishable, and the second is undetectable: every declaration is
truthful and the domain supports no control inverse (§5), no observability
triage of consequence (§3.8), and no baseline comparison on the control axis
(→ Spec §9.3). This is a computable property of the declaration and the
operators, not a matter of self-report, and is a third informative per-domain
failure of this interface alongside the item 3 and item 6 failures already
noted."

**What this gives an interface sketch to look for** (`docs/SKETCHES.md`,
M10.1's four): whether the domain has a quantity fixed for the whole chain that
nonetheless changes what operators do, and — the sharper question — whether it
is a parameter *everywhere* or a parameter in one region and state in another.
The assessment argues semiconductors are the interesting case (dopant identity
a parameter, dopant *profile* evolving under thermal budget), MOF linker
chemistry a pure parameter, polymer molecular-weight distribution state;
**those are argued from domain knowledge, not from instantiations, and are
recorded as claims with that stated basis, not as demonstrated.** A sketch
finding a region-dependent case would show the proposed wording's second
sentence is necessary rather than defensive.

**Confidence.** High that the category is absent — a direct reading of Core §4's
seven items and Core §3.1's slot definitions, confirmed against the declaration
type's seven fields and the schema's three-tuple components. High that the
detectability consequence follows, since it is a structural argument from the
absence, and high that it is realised in practice: flagship's three frozen

measurements, not inferences. High that the proposed check in (2) is
mechanically computable, since this entry's verification computed it. Medium on
the proposed wording's placement (a new item 8 versus a sub-item under item 1;
Core §4 versus Spec §9.1's conformance table for the check in (2) — a reporting
requirement in form, a falsifiability property in substance). **Untested**:
whether operators declared as parameter-conditioned actually transfer across
parameter values with few samples, the assessment's proposed cheap test (train
on one grade, test transfer to another), not performed here.

## E-30 — Spec §2.2 prescribes equivariant architectures but no interface item lets a domain declare which group acts on which state components, and the state metric admits no group action; the prescription has no declarable input

**Target.** Spec §2.2's first hard-constraint category ("**Symmetry.**
Equivariant architectures respecting the relevant point group;
frame-indifference for constitutive operators; permutation invariance over
discrete populations") read against Core §3.2's state metric `d_𝒮` and against
Core §4's seven declaration items.

**Kind.** Addition

**Discovered.** **`[domain-assessment]`** — `docs/PHYSICS-ADEQUACY.md` §3.2,
domain assessment from flat-rolled steel, not an implementation attempt.
Verified against the code before filing, which sharpened the finding and
refuted one of its supporting claims (below).

**Finding.** Spec §2.2 requires symmetry as the *first* of its five hard
structural constraints, and requires that "constraints declared under
interface item 6 (Core §4) MUST appear here as architecture, not as loss
terms." Two things follow that the framework does not supply.

**First: there is nowhere to declare the group.** Core §4's seven items are
state schema, control space, erasure inventory, readout catalogue,
observation suite, invariants, and scale structure. Item 6 is "conservation
laws and monotone functionals" — not symmetry groups. So a domain that knows
its relevant point group has no item in which to state it, and an
implementation that wanted to build the equivariant architecture Spec §2.2
requires has no declared input telling it which group acts on which
components. This repository's own implementation makes the missing
destination explicit rather than hiding it: its constraints module
deliberately declines to supply a general equivariant layer on the stated
grounds that "an equivariant layer's correct form depends on *which* group
acts on *which* state components, which is domain content" — correct, and the
delegation has nowhere to land, because no item accepts that content. The
result is that Spec §2.2's first category is unimplemented in this build and
unimplemented by either declared domain, and the interface gives no way to
notice which domains it should have applied to.

**Second: the state metric cannot respect a group even if one were
declared.** Core §3.2 posits a metric `d_𝒮` on the state space; this
repository's realisation of it carries exactly two fields — a schema and a
per-component scale vector — and computes distance as the Euclidean norm of
the scale-normalised displacement. That is a diagonal rescaling of a
Euclidean metric. Demonstrated directly on a two-component
orientation-like descriptor with equal scales: two states related by a 90°
rotation — related by a symmetry of any isotropic texture measure — are
reported at distance `1.414`, not `0`. A metric that does not quotient by the
symmetry group of the state cannot support an equivariant operator on it in
the sense Spec §2.2 means, so the framework's symmetry prescription is
disconnected from its own state definition, and the disconnection is
structural rather than a matter of this repository's parameter choices: there
is no field on the metric that could carry a group, a quotient, or even a
non-diagonal form.

**Third, and this makes the finding internal to Core rather than contingent on
any domain: Core §3.1 names an occupant its own metric requirement mishandles.**
The `m` slot's occupant list is "Order parameters, indicator fields,
**orientation fields**, composition fields, geometric descriptors of
second-phase and defect populations." Orientation fields are named as a
first-class occupant, not as an exotic case. An orientation field's values are
related by a symmetry group by construction — that is what makes it an
orientation — so a metric that separates a field from its rotation reports two
physically identical states as distant. **The `1.414` demonstration above is the
proof of exactly this**, not merely an illustration of some possible domain's
needs: a two-component orientation descriptor rotated by 90° is the minimal
instance of the occupant Core §3.1 itself names.

Nothing in Core or Spec closes it. Core §3.2 introduces `d_𝒮` with an
illustrative form — "e.g. Wasserstein on descriptor measures ⊕ weighted Sobolev
norms on fields" — far richer than a diagonal scaling, and *still* not a
quotient by any symmetry group: a Sobolev norm separates an orientation field
from its rotation exactly as a diagonal metric does. Core §3.9 and Spec §2.5
require the metric be *declared* and that every metric-dependent quantity carry
it, which is a disclosure requirement, not a constraint on the metric's
structure. **So Core names orientation fields as a first-class `m` occupant, and
neither states that such an occupant constrains which metrics are admissible nor
offers one that handles it.** In this build the defect is latent only because no
implemented domain declares texture or any other orientation quantity — Core
names the occupant regardless, so the gap sits in the framework's own text and
does not wait on a domain to expose it.

**Refutation of a supporting claim in the assessment, recorded because a
refutation carries as much weight here as a confirmation.** The assessment
states that Spec §4.4's directional-`ℓ_D` requirement for banded structures
was "declined" by this build, and calls that "the largest single physics gap
in the build." Two corrections. (a) Spec §4.4 *does* carry the requirement,
verbatim — "Anisotropic correlation (banded structures) requires a
directional `ℓ_D` and reduction along each suppressed axis independently" —
and this build's correlation-length estimator does refuse anything but a 1-D
field while its weakest-link-count consumer takes a scalar, so the
requirement is genuinely unimplemented. But (b) it was not declined: the
governing ADR states in as many words "*Full anisotropic `ℓ_D` now.*
**Deferred, not rejected**", carries an explicit scope paragraph naming the
unimplemented Spec requirement, gives the reason (the toy's driver fields are
1-D and no oracle exists to check a directional extension against), and names
the trigger that would force it. A silently-skipped MUST and an openly
deferred one are different failures, and this is the second. (c) "Largest
single physics gap" is a comparative judgement this verification cannot
settle and does not adopt. **Consequently the directional-`ℓ_D` half of the
assessment's §3.2 is a build-coverage gap against a Specification that is
already correct, and belongs in `docs/COVERAGE.md`, not in this ledger.**
Only the group-declaration and metric halves above are framework findings,
and this entry is scoped to them.

**Proposed wording.** (1) Add a **new declaration item** — deliberately not a
sub-item of item 6, since E-32 shows item 6's existing dual role makes additions
there hazardous: "**Symmetry.** The group acting on the state, if any — which
group, acting on which declared components, and whether the action is a
point-group symmetry, a frame-indifference requirement on constitutive
operators, or a permutation invariance over a discrete population (Spec §2.2's
three named cases). A domain declaring a symmetry group MUST also state whether
the declared state metric (§3.2) quotients by it; a metric that does not is not
a defect in itself, but the gap between the two MUST be stated, since an
equivariant operator over a state space whose metric separates
symmetry-equivalent states is not the object Spec §2.2 requires. An explicit
declaration of *no* symmetry is legal and required, not an omission."
(2) And, because the gap is in Core's own occupant list rather than only in what
some domain may need, append to Core §3.1's `m` definition: "An orientation
field — or any occupant whose values are related by a symmetry group —
constrains which metrics on `𝒮` are admissible: a metric separating a field from
its image under that group reports physically identical states as distant, and
no equivariant operator (Spec §2.2) can be built over it. A declaration naming
such an occupant MUST state the group and how the declared metric treats it.
Neither of §3.2's illustrative forms — Wasserstein on descriptor measures,
weighted Sobolev norms on fields — quotients by a symmetry group, so neither is
admissible for such an occupant without an explicit quotient."

**What this gives an interface sketch to look for** (`docs/SKETCHES.md`):
whether the domain has a directional or orientational quantity in its state
at all, and if so whether the sketch can name the group. The assessment
argues that wafer orientation, MOF pore-channel directionality, electrode
through-plane versus in-plane tortuosity, and additive-manufacturing build
direction each make anisotropy central rather than incidental, and states
it "cannot construct a PSR system where anisotropy is safely ignorable" —
**that is a domain-knowledge argument, not evidence from instantiations, and
is recorded here as a claim with that basis.** A sketch that fills the
proposed declaration cleanly, or one that cannot name its group, is the first
actual evidence either way.

**Confidence.** High that no item declares a group and that the metric admits
none: direct readings of Core §4's item list and of the metric's two fields,
plus a direct demonstration that two rotation-related states are reported at
positive distance. High that Core §3.1 names orientation fields as a
first-class `m` occupant and that neither §3.2's two illustrative metrics nor
the disclosure requirements of §3.9/Spec §2.5 handle the resulting symmetry —
all direct quotations, so this half of the finding does not depend on any domain
declaring texture. High that Spec §2.2 requires the architecture whose input
is missing — a verbatim quotation. Medium-high on the proposed wording's
second sentence (requiring the metric/group gap be *stated* rather than
closed), since requiring a group-invariant metric outright would be a larger
change to Core §3.2 than this finding's evidence supports, and the weaker
disclosure requirement is what this entry can justify. **Not established**:
that any specific non-steel domain's anisotropy is load-bearing — that is the
assessment's argued verdict, untested here.

## E-31 — Core §4 item 1 asks for resolution limits and nothing can carry them, so the `m`/`z` boundary is observer-relative and undeclared; operator reuse across routes is unconditioned on it

**Target.** Core §4 item 1 ("State schema — occupants of each slot
`(m, z, ν, Γ)`, **with resolution limits**, and which slots are empty") read
against Core §3.1's definitions of the two slots the boundary separates: `m`
is "**observable in principle by imaging, at a stated resolution limit**",
and `z` is "path-dependent quantities **below imaging resolution**... Not
observable directly; inferable only through dynamics."

**Kind.** Addition

**Discovered.** **`[domain-assessment]`** — `docs/PHYSICS-ADEQUACY.md` §3.3,
domain assessment from flat-rolled steel, not an implementation attempt.
Verified against the code before filing.

**Finding.** Core §3.1 defines `m` and `z` by *observability*, not by physics:
the same physical quantity sits in `m` if your instrument resolves it and in
`z` if it does not. Solute clustering is `z` with EBSD and `m` with atom
probe; the physics is unchanged and the state space is not. Core §3.1
acknowledges the dependence — `m` is observable "at a stated resolution
limit" — and Core §4 item 1 duly asks for "resolution limits". Neither
follows through on the consequence, which is that **`𝒮` itself is
observer-relative**, and that two implementations of the same domain under
different characterisation suites are working in different state spaces.

That undermines a claim the framework leans on rather than a peripheral one.
Operator reuse across routes and transfer across domains both presuppose
operators are portable objects. An operator trained under one
characterisation suite is a map on a different space than the same physics
under a better suite — same name, same domain, non-composable. Two groups can
follow the interface exactly, declare the same domain, and produce operators
that cannot be chained.

**Verified against the code, and the gap is wider than the text suggests.**
Item 1 asks for resolution limits, but this repository's realisation of item 1
declares components as `(Slot, str, int)` triples — slot, name, dimension —
**with no resolution-limit field at all**, while its own docstring quotes
item 1's phrase "with resolution limits" verbatim. So the framework asks for
the quantity, and the shared declaration object through which every domain
declares item 1 cannot carry it. Nor is a resolution limit the same thing as
the characterisation suite that sets it: a limit is a number, the suite is
what makes that number the boundary, and only the latter tells a second
implementer whether their `m` is your `m`. Item 5 (observation suite) is not a
stand-in either — it declares in-chain process instrumentation for
assimilation, and flagship's is `("in-die force/torque sensing (Type-0 readout
of z)", "coating thickness gauge")`: process sensors, not the
characterisation methods that would fix the `m`/`z` partition.

**And nothing conditions reuse on the boundary matching.** This repository's
chain-composition module contains no reference to a schema at all — no
compatibility check of any kind gates composing one operator after another.
The interface's own diff utility does compare two domains' declared schemas
for inequality, but that is a *report* produced after the fact, not a
precondition on reuse, and it compares component names and dimensions, which
would not detect two suites yielding the same names at different resolutions.

**Distinct from E-26/E-27, and the assessment says so correctly.** Those two
entries find Core §4 item 2 declarations satisfiable without a joint property
(readout sensitivity; a numeric admissible bound). The pattern is the same
shape — a declaration item omitting something load-bearing — but the omitted
property here is *physical* (which instrument fixed the state space) rather
than interface-internal, and its consequence is non-composability across
implementations rather than a vacuous or unexecutable search.

**Proposed wording.** Replace Core §4 item 1's parenthetical with: "**State
schema** — occupants of each slot `(m, z, ν, Γ)`; for each `m` occupant, the
resolution limit *and the characterisation method that establishes it*; and
which slots are empty. Because `m` and `z` are separated by observability
rather than by physics (§3.1), the declared `m`/`z` boundary is a property of
the characterisation suite, not of the material: two instantiations of the
same domain under different suites declare different state spaces. An
operator MUST NOT be reused across, or composed with an operator from, a
declaration whose `m`/`z` boundary differs, unless the difference is declared
and a stated mapping between the two boundaries is supplied."

**What this gives an interface sketch to look for** (`docs/SKETCHES.md`):
whether the sketch can name the characterisation method behind each of its
`m` occupants, and whether it can say what would move to `z` under a weaker
suite. The assessment argues catalysis is the extreme case — active-site
speciation moving between `m` and `z` depending on the availability of
operando spectroscopy — and that MOF defect structure moves with access to
pair-distribution-function analysis; **both are argued from domain
knowledge, not from instantiations, and are recorded as claims with that
basis.** A sketch whose `m` occupants cannot be tied to a named method would
show the declaration is not merely missing but hard to supply, which is a
stronger finding than the absence alone.

**Confidence.** High that the boundary is observability-defined and therefore
observer-relative: this is a direct reading of Core §3.1's own two slot
definitions, one of which says "at a stated resolution limit" and the other
"below imaging resolution." High that item 1 asks for resolution limits and
that the declaration type cannot carry them, and high that nothing conditions
composition on the boundary — direct code readings, including a module that
mentions schemas nowhere. Medium on the proposed wording's final sentence: a
hard prohibition on cross-boundary reuse may be stronger than practice can
bear, and a disclosure requirement ("state the boundary difference and its
effect on the reused operator's validity") may be the more implementable
form — the authors would need to choose, and this entry has no evidence
distinguishing them, since no two-suite instantiation of one domain exists
here to test either against.

## E-32 — None of Spec §2.2's five hard-constraint categories is a domain constitutive form, and interface item 6 does not merely lack a place for one but refuses one by name; item 6 also conflates two roles with different mathematical requirements, so the obvious fix would silently widen the pool Spec §7.1 draws reachability certificates from

**Target.** Spec §2.2's five hard-constraint categories, quoted in full below,
read against Core §4 item 6 ("**Invariants** — conservation laws and monotone
functionals available as hard constraints (→ Spec §5) and as reachability
certificates (§5)") and against Spec §2.2's own closing requirement
("Constraints declared under interface item 6 (Core §4) MUST appear here as
architecture, not as loss terms").

**Kind.** Addition

**Discovered.** **`[domain-assessment]`** — `docs/PHYSICS-ADEQUACY.md` §3.4,
which calls this "the most important finding in this document, and the one
that bears directly on extrapolation." Domain assessment from flat-rolled
steel, not an implementation attempt. Verified against the code before
filing, which strengthened it from "no place to declare one" to "the
declaration actively refuses one" (below).

**Finding.** Spec §2.2's five categories are, verbatim: "**Symmetry.**
Equivariant architectures respecting the relevant point group..."; "**Thermodynamic
admissibility.** GENERIC or port-Hamiltonian structure..."; "**Range
constraints.** Simplex parameterisation for fractions; positivity for
densities and damage; bounded distributions."; "**Monotonicity.** Damage,
accumulated driving measures, and consumed driving force are monotone in
time..."; "**Conservation.** Mass balance across transformation and
partitioning steps." **Every one is a generic mathematical constraint. Not one
is a domain constitutive law.**

The distinction is not cosmetic, and it is where extrapolation comes from.
A constitutive form with a small parameter count and a known validity range
carries the *shape* of the response outside the data: an operator constrained
to such a form, with a handful of fitted parameters, extrapolates to an unseen
driving condition because the functional form is right there, not because the
data covered it. The generic categories buy something different: they
guarantee an operator cannot violate positivity, monotonicity or a
conservation balance anywhere — safety off-distribution, not reach. Read
physically, that is exactly what this ledger's own E-28 measured
independently: a hard monotonicity constraint honestly representing "no
evidence past the training data" produces a flat, zero-gradient shelf, on
which a gradient search cannot move. **E-28 and this entry are the same fact
from two directions** — E-28 found by building that generic hard constraints
give safety without reach; this entry says the category that would give reach
is absent from the framework's list.

**Verified, and the framework is more closed to this than the assessment
argued.** The assessment states "there is no place to declare *'transformation
kinetics follow Koistinen–Marburger, validated 300–500 K'*." There is a place,
and it throws. This repository's item-6 implementation classifies each
declared invariant into exactly two kinds — conservation or monotonicity —
and **refuses any name matching neither**, raising rather than guessing. Run
directly against four canonical metallurgical constitutive forms, all four are
refused: `koistinen_marburger_martensite_kinetics`,
`kocks_mecking_dislocation_evolution`, `jmak_isothermal_transformation`, and
`hall_petch_grain_size_strengthening` each raise, while
`charge_conservation_coulomb_counting` and
`sei_thickness_monotone_nondecreasing` classify. The refusal is not a
repository bug — its own documentation cites "Spec §2.2's two hard-constraint
categories that apply here", which is a faithful reading of item 6's
"conservation laws and monotone functionals." The two-kind restriction is the
framework's, and the code implements it exactly; that is what makes the code's
refusal *evidence for* the framework finding rather than an artefact of it.

Corroborating the same point from the constraints side: this build implements
range (positivity, simplex), monotonicity and conservation as literal
differentiable reparameterisations; declines thermodynamic admissibility as
out of scope (this ledger's E-10); and defers symmetry to domains, where no
domain implements it (E-30). Whatever the implementation status of the five,
none of them — implemented or not — is a constitutive form, so no amount of
finishing Spec §2.2's list would supply the missing category.

**Why the obvious fix is wrong, and this shapes the proposed wording below:
item 6 serves two roles with different mathematical requirements, and a
constitutive form satisfies only one of them.** Item 6 states both roles in one
sentence: "**Invariants** — conservation laws and monotone functionals available
as hard constraints (→ Spec §5) **and as reachability certificates** (§5)." Spec
§7.1 then sources certificates from it directly: "Candidates are drawn from
interface item 6 — conservation balances, monotone accumulations,
equilibrium-limited fractions at attainable driving levels. Barrier-function
style." A reachability certificate is, by Spec §7.1's own boxed definition, a
functional `Φ : 𝒮 → ℝ` with a provable per-step bound `Φ(s_{k+1}) ≤ Φ(s_k) +
c(u_k)`. **A constitutive form is not such an object at all** — it is a
functional *form for an operator*, not a scalar functional of state with a
monotone accumulation bound, so it cannot discharge Core §5's output contract
("route, or certificate of non-reachability plus nearest reachable state"). So
adding constitutive forms to item 6 as a sub-item would silently widen the pool
Spec §7.1 draws certificates from to include objects that cannot be certificates.
The requirement that fixes this is a **role scoping**, not merely a new sub-item.

**And item 6 is already inadequate to its own certificate role, which
strengthens the case for splitting it rather than patching it.** Spec §7.1 names
*three* candidate kinds — conservation balances, monotone accumulations, **and
equilibrium-limited fractions at attainable driving levels** — while item 6 names
only the first two ("conservation laws and monotone functionals"). Verified
against this build's faithful two-kind classifier: an equilibrium-limited-fraction
invariant (`equilibrium_limited_phase_fraction`) is **refused**, exactly as the
four constitutive forms are. So the list Spec §7.1 reads for certificates
under-names by one kind even before any constitutive form is contemplated.

**Scoping the hazard honestly:** it is currently textual, not realised in this
build's code. Nothing here constructs a `ReachabilityCertificate` from a
declaration — `declaration.invariants` is read only by the interface diff and
its classifier, and no test constructs a certificate against a real domain at
all (the C-5a/S-7.1 gap this ledger's E-16 already records). The hazard is that
Spec §7.1's stated sourcing would be wrong the moment that coupling is built,
which is precisely when a silent widening would be least visible.

**Proposed wording.** Add a sixth category to Spec §2.2: "**Declared
constitutive forms.** Where a domain has an established functional form for a
constitutive or kinetic relationship, the operator MAY be constrained to that
form rather than to generic structure alone. Unlike the five categories above,
this constraint carries the response's *shape* outside the training envelope
and is the only category in this list that does so. An operator so constrained
MUST report the declared form, its fitted parameter values, the form's stated
validity range, and where the current query sits relative to that range — a
query outside the declared validity range is an extrapolation warning the
implementation MUST surface rather than silently honour."

And **split Core §4 item 6 by role**, rather than adding a sub-item to it —
replacing item 6 with: "6. **Invariants and declared structure**, in three
role-scoped parts. **6a. Conservation laws** and **6b. monotone functionals** —
available *both* as hard constraints (→ Spec §2.2) *and* as reachability
certificates (§5, → Spec §7.1). **6c. Equilibrium-limited fractions at
attainable driving levels** — available as reachability certificates (→ Spec
§7.1, which names this kind and which this item previously omitted); usable as a
hard constraint where the fraction's bound is structural. **6d. Declared
constitutive forms** — for each, the functional form, its parameters, its stated
range of validity, and the source establishing it. **6d is available as a hard
constraint only, and MUST NOT be read as a reachability certificate**: a
constitutive form is a functional form for an operator, not a scalar functional
of state with a provable per-step accumulation bound, and cannot discharge §5's
output contract. A domain with no established constitutive form for a given
operator MUST declare 6d empty for it; an empty declaration is legal and
required, and is itself the statement that operators for that step carry generic
structure only and should not be expected to extrapolate in form." Spec §7.1's
sourcing sentence should then read "Candidates are drawn from interface items
6a–6c" rather than from item 6 as a whole.

**`[authorial-choice]`** — either the split above or, if the authors prefer to
leave item 6's shape alone, a bare scoping sentence appended to it — "each declared invariant MUST state
which of the two roles it serves, and a member serving the hard-constraint role
is not thereby eligible for the certificate role" — discharges the hazard. The
split is proposed as primary because it *also* fixes item 6's existing omission
of Spec §7.1's third candidate kind, which a scoping sentence alone would leave
in place.

**What this gives an interface sketch to look for** (`docs/SKETCHES.md`):
whether the domain has a canonical constitutive form at all, with a citable
validity range, or only empirical correlations. The assessment argues every
domain has such a canon and names candidates — Fick with
concentration-dependent diffusivity, Arrhenius and Shockley–Read–Hall for
semiconductors; Langmuir/BET/IAST for MOFs; Langmuir–Hinshelwood and
Sabatier/BEP scaling for catalysis; Butler–Volmer and Nernst for batteries —
and calls the finding "universal, and every domain has its canon."
**That is a domain-knowledge argument, not evidence from instantiations, and
is recorded here as a claim with its stated basis, not as demonstrated.** A
sketch able to fill 6b with a citation and a range is the first real evidence
for it; a sketch that cannot is evidence against, and is the more interesting
outcome.

**Confidence.** High that none of the five categories is a constitutive form —
a direct reading of all five, quoted above. High that item 6 admits only
conservation and monotonicity, and high that this build's item-6
implementation refuses a constitutive form by name: a direct run against four
canonical forms, all refused, with the refusal's own justification citing
item 6's two-category wording. High that generic constraints give safety
rather than reach, on E-28's independent measurement rather than on this
assessment's argument. Medium on whether a sixth Spec §2.2 category or a Core
item 6b is the better home (the proposed wording supplies both because the
constraint-as-architecture requirement and the declaration requirement are
genuinely two edits). **Untested, and this is the load-bearing gap**: whether
an operator constrained to a declared form actually extrapolates better than
an unconstrained one with generic constraints. The assessment proposes exactly
that experiment — constrain a transformation operator to a declared form, hold
out a driving-condition region entirely, compare against the unconstrained
operator and a tabular baseline — and it is not performed here. Until it is,
this entry establishes that the category is absent, not that adding it would
deliver the reach it is argued to deliver.

## 6. Diagnostics blind to their own dominant error source

A second, distinct recurring shape: a diagnostic that reports a plausible,
bounded number while remaining blind to whichever alternative actually
dominates in a constructed counterexample. A single-probe divergence
fingerprint cannot distinguish a directional hidden variable from a
non-directional one tuned to match it under either probe alone (E-03). A
component's own raw-magnitude heuristic disagrees with its actual
recoverability (E-04), and — once an erasure genuinely mixes across named
components rather than aligning with one — operator-level rank supplies no
per-component signal at all, agreeing with neither the magnitude heuristic
nor a direct geometric projection (E-18). A pooled tail-index fit is
dominated by whichever defect population is most numerous in the fitting
window, not whichever population actually governs the design point, by
more than three orders of magnitude in the constructed case (E-05). An
unordered infeasibility report cannot say which of three binding terms —
trust region, admissible control, aleatoric spread — is actually
responsible, when the three have a real dependency order (E-06). A
join-threshold-only sensitivity sweep is blind to the tail-index estimation
uncertainty that turns out to dominate the very risk estimate the sweep
was reporting on (E-15). And neither of Core §3.9's two stated
completeness measures, nor literal algebraic rank itself, detects a real,
finite-rate erasure that only the raw singular-value spectrum reveals —
confirmed on this repository's own declared erasure operator, not a
constructed toy (E-19). And the semigroup residual Spec §9.2 makes a
conformance check reports a bare number with no declared metric, so the
answer it gives to a physical question about it moves by sixteen orders of
magnitude depending on a normalisation choice neither document asks the
implementer to state — the diagnostic is blind to the single input that
dominates it (E-33). Every one of these was caught only because a
constructed case existed where the true answer was known in advance and
the diagnostic's reported number could be checked against it directly —
the oracle-testing philosophy CLAUDE.md §7 asks this repository to
practise on its own estimators, turned back on Spec's stated procedures
themselves.

## E-03 — OQ-1: the divergence fingerprint table should name paired-probe contrasts, not single probes

**Target.** Spec §1.6 (divergence fingerprint table)

**Confidence.** High — demonstrated on a constructed counterexample where

## E-04 — OQ-2: erasure completeness must be read from recoverability, not raw magnitude

**Target.** Core §3.9, consequence 3

**Kind.** Addition

**Discovered.** M2, `tests/oracles/test_known_erasure.py`
(`test_oq2_naive_magnitude_heuristic_disagrees_with_recoverability`).

**Finding.** Core §3.9 consequence 3 offers "mutual information between
pre- and post-erasure states, *or* residual variance explained by upstream
variables" as alternative erasure-completeness criteria, without warning
against a third, more naive reading: a component's own raw magnitude or
variance reduction. On a diagonal, designed-rank Jacobian with one
full-gain, one small-gain (0.15), and one exactly-zero-gain component, a
naive "fraction of variance retained" reading calls the small-gain component
more than 95% erased (it loses 97.75% of its variance), while the
operator-level rank (`measure_erasure`, via SVD) and a per-component
recoverability estimate (`component_recoverability`, R² of post-step
regressed on pre-step) agree with each other and correctly call it fully
surviving/assimilable (R² > 0.999). The naive magnitude heuristic is the one
that is wrong.

**Proposed wording.** Append a caveat to Core §3.9 consequence 3: "Erasure
completeness must not be read off a component's raw magnitude or variance
reduction: a component can lose most of its magnitude and remain exactly
recoverable. Use mutual information or residual variance explained (R²)
against the pre-erasure state, not the component's own scale."

**Confidence.** High for the diagonal (non-mixing) case demonstrated here.
The genuinely open half of this question — whether operator-level rank
still predicts *per-component* influence under a mixing (non-diagonal)
erasure Jacobian — is answered at Phase 3.4 (docs/ROADMAP.md); see E-18,
which supersedes this note rather than this entry's own proposed wording,
since the two findings are complementary, not contradictory.

## E-18 — OQ-2's deferred half, answered: operator-level rank does not predict per-component influence for a mixing erasure; a per-component projection is a genuinely distinct, needed diagnostic

**Target.** Core §3.9, consequence 3 (extends E-04's finding, which covered
only the diagonal case)

**Kind.** Addition

**Discovered.** Phase 3.4 (docs/ROADMAP.md), `tests/oracles/
known_mixing_erasure.py` — the mixing-erasure oracle E-04 said would need
to exist before this half of OQ-2 could be answered.

**Finding.** E-04 confirmed, on a *diagonal* designed-rank Jacobian, that
operator-level rank and per-component recoverability (R²) agree — but noted
this proves nothing for a genuinely *mixing* erasure, since a diagonal
map's named components each align with exactly one singular direction by
construction. Built the mixing case directly: a symmetric rank-2 Jacobian
over three named components (`component_a`, `component_b`, `component_c`),
with two distinct nonzero singular values (`1.0`, `0.6`) on directions
`(1,1,1)/√3` and `(1,-1,0)/√2`, and an exact zero on `(1,1,-2)/√6` — none of
the three axis-aligned, so the kernel and surviving subspace both mix all
three named components. `measure_erasure` recovers the designed rank (2)
and surviving subspace exactly (erased-direction alignment with the
designed kernel `> 0.999`, `tests/oracles/test_known_mixing_erasure.py`) —
this half of the machinery is unaffected by mixing, as expected (SVD does
not care whether singular vectors are axis-aligned).

Per-component recoverability is where the diagonal case's clean answer
breaks down. Each named component's designed geometric overlap with the
surviving subspace (`‖P_survive e_i‖²`, computed by construction):
`component_a = 0.833`, `component_b = 0.833`, `component_c = 0.333` — none
is 0 or 1, unlike every component in the diagonal oracle. Measured
`component_recoverability` (R², 2000-particle ensemble): `component_a ≈
0.78`, `component_b ≈ 0.76`, `component_c ≈ 0.33` — intermediate for all
three, correctly ordering `component_c` lowest (its kernel loading,
`-0.816`, is the largest in magnitude of the three), but **not numerically
equal** to the geometric overlap (a ~5 percentage-point gap for `a`/`b`) —
confirming the two are related, not interchangeable, quantities: R² is a
noiseless-linear-map correlation estimate over a finite ensemble;
`‖P_survive e_i‖²` is an exact geometric projection needing no ensemble at
all. **Operator-level rank (the single integer 2) supplies neither number**
— it cannot distinguish that `component_c` is roughly half as recoverable
as `component_a`/`component_b`, information only a per-component diagnostic
supplies. Added `component_surviving_overlap`
(`src/omi/erasure.py`) as that diagnostic, verified to recover the designed
values to within `0.01` (`tests/oracles/test_known_mixing_erasure.py`).

**Answer to OQ-2's deferred question.** No — operator-level rank does not
predict per-component influence once the erasure mixes, and yes, a
per-component projection onto the surviving subspace is needed as a
distinct diagnostic from both rank and `component_recoverability`. All
three (rank, R², geometric overlap) are informative and none subsumes
another once the erasure is not diagonal.

**Proposed wording.** Append to Core §3.9, immediately after E-04's
proposed caveat: "Where the erasure is not diagonal in the declared
component basis (its surviving subspace mixes several named components),
operator-level rank supplies no per-component information at all,
including for components that are not themselves erased; an implementation
MUST supply a per-component diagnostic (e.g. squared overlap with the
surviving subspace, or Core's own residual-variance-explained candidate)
before reporting which named components survive."

**Confidence.** High — every quantity above (designed overlaps, measured
R², measured geometric overlap, their ordering and their inequality to
each other) is a direct re-run against the oracle's own exact construction,
not an inference. This closes E-04's previously-open half; no further
mixing-erasure question is left pending on this ledger.

## E-05 — OQ-3: competing defect populations require separate tail transfer, not a pooled fit

**Target.** Spec §4.3, after Proposition 4.1

**Kind.** Addition

**Discovered.** M6, `tests/test_classb_competing_risks.py`.

**Finding.** Spec §4.3 transfers a tail index from one defect population.
With several populations of differing `α` and `β`, survival is
`∏ₚ[1−Fₚ]^{Nₚ}` and no single `ξ` describes the range of interest. A common,
light-tailed population (`α=5`, 10,000 members) and a rare, heavy-tailed
population (`α=1.5`, 10 members) driving the same component: at a design
point deep enough that the rare population's heavier tail dominates its
total exceedance contribution despite 1000x fewer members, pooling every
descriptor and fitting one Hill tail index — exactly what a practitioner
unaware of the two populations would do — underestimates the true,
competing-risk-aware failure probability by orders of magnitude (observed
ratio > 1000x in the constructed case; a fresh re-run for
`build/REVIEW-EXTRACT.md` measured 2597x at a fixed seed). The pooled fit's
tail index lands close to the *common* population's own `α`, because the
top order-statistic window used for fitting is filled overwhelmingly by its
far greater count, even though every individual common-population value is
smaller than the rare population's.

**Proposed wording.** Append a requirement to Spec §4.3, after Proposition
4.1: "Where more than one defect population plausibly contributes to the
same driver, each population's tail index MUST be measured and transferred
separately (`ξ_{D,p} = β_p·ξ_{a,p}`) and combined via the competing-risks
survival product; fitting a single pooled tail index across populations of
differing severity is non-conforming, since the fit is dominated by
whichever population is most numerous in the fitting window, not by
whichever population actually governs the design point."

**Confidence.** High — demonstrated at more than three orders of magnitude
of error in the unsafe (underestimating) direction, on a constructed case
built specifically so the answer is known.

## E-06 — OQ-4: inverse design must report which term makes the feasible set empty, in order

**Target.** Spec §7.3

**Kind.** Addition

**Discovered.** M9, `tests/oracles/test_known_infeasible_specification.py`.

**Finding.** Spec §7.3 selects within a feasible set but does not say what
to report when the set is empty. `diagnose_infeasibility` (ADR-033,
`docs/DECISIONS.md`) checks three candidate binding terms in a fixed,
principled order — trust region, then control/`𝒰_adm`, then aleatoric
spread at a declared coverage fraction — and four constructed scenarios
(one per binding term, plus a genuinely feasible case) sharing one linear
response model, each engineered so exactly one term is responsible, confirm
the diagnostic recovers the constructed truth in all four. The order is not
incidental: a trust-region violation means the model was never asked to
extrapolate there (a modelling-scope question), a control violation means
the apparatus cannot reach the window regardless of noise (a capability
question), and only when both are satisfied does the aleatoric question
("is incoming variation too wide") become meaningful at all. Checking them
in any other order, or reporting all three simultaneously as an unordered
set, would obscure this dependency.

**Proposed wording.** Append to Spec §7.3, as an explicit requirement: "When
the decision layer's feasible set is empty, an implementation MUST report
which of trust region, apparatus admissibility (`𝒰_adm`), or aleatoric
spread is responsible, checked in that order (a violation earlier in the
order makes the later checks not yet meaningful). Reporting only that the
set is empty is non-conforming."

**Confidence.** High — the diagnostic recovers the constructed truth exactly
in all four engineered scenarios, and the ordering argument follows directly
from what each term means, not from an arbitrary convention.

## E-15 — Spec §4.2's join-threshold sensitivity MUST varies only `u`, so it cannot surface the dominant, already-acknowledged source of `p0` uncertainty that §4.6 rung 2 requires be measured with its own error bar

**Target.** Spec §4.2 ("An implementation MUST state the join threshold,
the quantile at which it sits, the number of ensemble members above it, and
the sensitivity of the final risk estimate to `u` over at least a factor of
two in exceedance probability") read against §4.6 rung 2 ("Defect population
tail `ξ_a` — independently measured by established characterisation
methodology, **with its own error bars**") and §4.3 (Proposition 4.1, tail
transfer `ξ_D = β ξ_a`)

**Kind.** Correction

**Discovered.** Follow-up review of E-12's fix: "was `p0` calibrated or
chosen, and empirically it reads ~13-15% lower than the model-based value —
is the gap threshold instability or GPD fit bias?" Sharpened on a second
pass: the mechanism needed confirming with more than six reseeds, a
bias/noise decomposition, a check against Hill's own theoretical standard
error, and a scaling demonstration rather than a single-seed inference.

**Finding.** All four of Spec §4.2's MUSTs are satisfied and directly
verifiable in `run_bend_classb_campaign`'s output
(`src/omi_domains/flagship/classb_bend.py`, `omi.classb.JoinDiagnostics`):
join threshold `108.070`, quantile `0.9`, `50` ensemble members above it,
and a sensitivity sweep over quantiles `0.90`–`0.975` — a range whose own
marginal exceedance probability spans `0.10` down to `0.025` (4×, exceeding
Spec's "at least a factor of two"). Re-run at seed 0: the resulting
design-point risk estimate varies only `0.0459`–`0.0476` across that span
(ratio `1.037`) — **the gap is not threshold instability**.

**Note, Spec §4.6 rung 2 already requires the missing diagnostic — for
`ξ_a`, just not for the composite `p0` estimate §4.2 governs.** Rung 2
requires `ξ_a` be measured "with its own error bars"; the defect is not that
Spec never asks for tail-index uncertainty, but that §4.2's *own* stated
sensitivity MUST — the one an implementation is told to run to bound `p0`'s
uncertainty — varies only the join threshold `u`, never `ξ_a`'s error bar,
so satisfying §4.2 in full gives no signal that this second source exists,
let alone dominates.

**Bias and noise, decomposed (300 reseeds, not six).** Re-running the
campaign's `_correlated_pareto_field`/`estimate_tail_index_hill` construction
(`top_fraction=0.1`, `N_SITES=500`, so `k=50` tail observations) at 300
independent seeds against the true generative shape (`XI_A_INCLUSION=0.4`):
`mean(ξ_a_hat) = 0.342` (a **displaced mean**: bias `-0.058`, `-14.5%`
relative — a genuine Hill-estimator bias, not sampling noise) and
`SD(ξ_a_hat) = 0.168`. Hill's i.i.d. theoretical standard error,
`ξ_a/√k = 0.4/√50 = 0.0566`, is roughly **3.0×** smaller than the observed
SD — both effects (a displaced mean and an inflated spread) are present
simultaneously, as anticipated.

**The 3× excess variance and the displaced mean are not threshold-selection
artefacts — tested and ruled out directly.** Sweeping `top_fraction` from
`0.30` down to `0.02` (i.e., cutting deeper into the nominal tail, the fix a
"threshold too shallow, contaminated by bulk" diagnosis would predict) makes
the **relative bias worse, not better**: `-4.7%` at `top_fraction=0.30`
(`k=150`) rising in magnitude to `-65.7%` at `top_fraction=0.02` (`k=10`),
while the SD-to-theory ratio stays in the `0.76`–`3.24` band with no
monotonic improvement at shallower cuts. This is the opposite of what
bulk-contamination predicts, and rules it out as the mechanism here — a
result made possible only because `_correlated_pareto_field`'s marginal is
*exactly* Pareto by construction (probability-integral transform), so there
is no separate bulk regime for a shallow cut to leak in from. The actual
driver is **spatial correlation reducing the Hill estimator's effective
independent sample size below its nominal `k`**: adjacent sites within one
correlation length (`~2.0`, i.e. `~20` site-spacings at `SITE_SPACING=0.1`)
are strongly correlated, so the top-`k` order statistics cluster in space
rather than sampling `k` independent extremes.

**Demonstrated, not merely inferred, to scale as `1/√k`.** Varying `N_SITES`
from `125` to `4000` at fixed `top_fraction=0.1` (200 reseeds each): `SD ×
√k` converges to a stable constant (`0.50, 0.94, 1.09, 1.24, 1.28, 1.30` as
`N_SITES` runs `125→4000`) rather than growing or diverging — a genuine
`C/√k` law, just with `C ≈ 1.3` in place of the naive `ξ_a = 0.4` (an
inflation factor consistent with a much smaller effective sample than the
nominal `k`, from spatial clustering). The downstream quantity that actually
matters — `|p0_hat − p0_true|` — was directly measured at the same `N_SITES`
sweep (60 reseeds each, `p0_true = 0.0399` from the earlier `2×10⁶`-sample
ground truth): mean absolute gap shrinks monotonically, `0.0198 → 0.0151 →
0.0106 → 0.0074 → 0.0052` as `N_SITES` runs `250→4000`, while `rmse × √k`
holds constant at `0.118`–`0.133` — the gap in the flagship campaign's own
reported `p0` is not a one-off draw; it is this scaling law evaluated at
this campaign's chosen `N_SITES=500`.

**β-dependence, and why this domain sees the worst case.**
`tail_index_transfer` is exactly `ξ_D = β·ξ_a` (linear), so an *absolute*
error in `ξ_a_hat` propagates into `ξ_D_hat` scaled by `β`, unchanged in
relative terms. At this domain's `β = 1.0` (E-13's degenerate case), the
absolute error transfers **undamped**. At Spec §4.3's own worked
sanity-check value, `β = 1/6` (defect-initiated fatigue, "a heavy-tailed
inclusion population produces a markedly *lighter*-tailed strength
distribution"), the same absolute `ξ_a_hat` error would be damped
**sixfold** before it ever reaches the GPD fit. This domain does not merely
happen to show a `p0` gap — at `β=1`, it is structurally the *worst case*
for this error-propagation mechanism among the `β` values Spec itself
discusses, which is why E-13's finding (this domain cannot exercise Prop
4.1's transfer as anything but the identity) and E-15's finding (this domain
maximally exposes tail-index estimation noise) are the same degeneracy
surfacing twice.

**Proposed wording (1 of 2 — the sensitivity diagnostic).** Append to Spec
§4.2, after the existing MUST: "Where `ξ_a` is estimated (§4.6 rung 2)
rather than supplied with a specification-grade error bar, the sensitivity
MUST above MUST additionally be evaluated over `ξ_a`'s own estimation
interval, not only over the join threshold `u` — propagated through §4.3's
transfer at the domain's declared `β`. A stable result under threshold
choice alone MUST NOT be reported as bounding the risk estimate's total
uncertainty when `ξ_a`'s own interval has not also been swept; at `β` near 1
this second source typically dominates the first."

**Proposed wording (2 of 2 — a separate edit: Spec §4.2 sets no floor on
join depth, and the `top_fraction` sweep shows why one is needed.** Sweeping
`top_fraction` (equivalently, `k`, the count of order statistics the Hill
estimator treats as tail) from `0.30` down to `0.02` — the same sweep that
refuted the bulk-contamination hypothesis above — shows the *relative* bias
in `ξ_a_hat` growing monotonically as `k` shrinks: `-4.7%` at `k=150`,
`-14.5%` at `k=50`, `-65.7%` at `k=10`. This is the standard bias–variance
trade-off of any tail-index estimator (deeper cuts, i.e. larger `k`, improve
asymptotic validity of the "regularly varying" approximation but admit more
of the bulk; shallower cuts, smaller `k`, isolate the true tail but leave
fewer points and inflate variance — and, per this construction, bias too).
Spec §4.2 requires reporting "the number of ensemble members above" the join
threshold, but states no minimum for it and gives no criterion for trading
depth against validity — an implementation can satisfy the letter of §4.2
while choosing a `k` this session's own sweep shows produces a majority-
wrong point estimate (`k=10`: `-65.7%`). This is distinct from Proposed
wording (1): that entry is about `ξ_a`'s *uncertainty* not being propagated
into `p0`; this one is about Spec setting no criterion for the depth choice
that determines how large that uncertainty is in the first place — the two
compose (a badly-chosen `k` makes proposed wording (1)'s uncertainty band
wider than it needs to be, but even a well-chosen `k` still requires (1)'s
propagation). Two options, not mutually exclusive: **(a)** append to §4.2 a
stability-region criterion — "choose `k` (or the equivalent quantile) from
the range over which the estimate is stable as `k` varies (a 'Hill plot'
plateau), not merely a single conventional value (e.g. the top 10%)" — a
standard extreme-value-statistics practice Spec does not currently name;
**(b)**, weaker but unconditionally implementable, require the curve itself
be reported rather than trusting an implementer to have found the plateau:
"An implementation MUST report the tail-index estimate (and, where
computed, the downstream risk estimate) as a function of `k` or the join
quantile across a stated range, not only at the single value used, so a
reader can see whether the chosen depth sits in a stable region or where the
estimator is already collapsing." This session recommends **(b)** as the
minimum: it requires no judgement call from Spec about what "stable" means
across arbitrary domains, and it is what would have made this campaign's own
`k=50` choice's fragility visible without needing this investigation to
surface it.

**Confidence.** High — every number above is a direct re-run (300 and 200
reseeds respectively, plus a 5-point `top_fraction` sweep and a 6-point
`N_SITES` sweep, all against this repository's own campaign construction),
and the bulk-contamination alternative was tested and refuted, not merely
argued against. Medium for proposed wording (1)'s exact form, since Spec
does not specify *how* `ξ_a`'s interval should be estimated (bootstrap,
Hill's own asymptotic formula, a design-effect correction for spatial
correlation) or combined with the threshold sweep — that procedural gap is
itself unresolved here, consistent with rung 2's error bars being required
but Spec never specifying how they are obtained "by established
characterisation methodology... not by this framework." Medium-high for
proposed wording (2)(b) (a reporting requirement, unconditionally
implementable regardless of domain); lower for (2)(a), since "stable region"
is doing real work that would need its own operational definition to be
Spec-grade, and this construction's exactly-Pareto marginal may make its
Hill plot better-behaved than a real, only-asymptotically-Pareto defect
population's would be — this session's sweep demonstrates the trade-off
exists, not that (a)'s criterion generalises cleanly.

## E-19 — Core §3.9's completeness measures presuppose the erasure is already located; Spec §3.2's rank bound is vacuous for a real, finite-rate erasure, and the tolerance that fixes it is itself metric-dependent

**Target.** Core §3.9 (the erasure definition — "image of substantially
lower effective dimension" — and consequence 3's completeness measures)
read against Spec §3.2 (Proposition 3.2 / Corollary 3.3, the Gramian-
truncation guarantee keyed to literal Jacobian rank `r = rank F_ℰ`)

**Kind.** Correction

**Discovered.** Phase 3.1 (docs/ROADMAP.md),
`tests/test_flagship_real_erasure.py`, the first time `measure_erasure`/
`component_recoverability` have been run against a real declared erasure
operator (`HEATING_AND_SOAK`, flagship, `is_erasure=True`) rather than only
the exact-zero-singular-value diagonal construction in
`tests/oracles/known_erasure.py`.

**Finding.** Core §3.9 defines an erasure by a spectral property — "image of
substantially lower effective dimension," `L ≪ 1` — but the two completeness
measures it offers (consequence 3: mutual information between pre- and
post-erasure states, or residual variance explained by upstream variables)
both presuppose the erasure's location and boundary are already known; they
describe what *survives* an erasure, not how to *detect* one. Spec §3.2's
Proposition 3.2 supplies the detection criterion instead, and states it as
literal algebraic rank: `r = rank F_ℰ`, with the Gramian-truncation
guarantee (`rank G_k^post ≤ r`) keyed to that same literal `r`.

On `HEATING_AND_SOAK` — flagship's own declared erasure (Core §7.1: "erases
`z` and most of `m`") — `measure_erasure` reports rank **7 of 7**: full
rank, at the default numerical tolerance ADR-017 sets (machine-epsilon
scale), for an operator the domain declaration itself marks
`is_erasure=True`. The two damped directions have singular values
`≈ exp(-5) ≈ 0.0067`, three orders of magnitude below the next-smallest
surviving value (`0.74`), and align exactly with the components Core §7.1
names ("prior_deformation," "substructure_density") — genuinely erasure-like
in every qualitative sense the text describes, but not rank-deficient at
machine precision, because the decay is a finite `exp(-5)` damping, not an
exact algebraic zero. Read literally, Prop 3.2's bound says nothing
detectable here: `r = 7`, the full state dimension, so "`rank G_k^post ≤ r`"
is vacuous for the operator the framework itself calls an erasure.
`component_recoverability` fails from the other side, extending E-04's
diagonal-case finding to a real domain for the first time: every
component's R² > 0.999 regardless of the ~150x singular-value gap, since R²
is a correlation measure, scale-invariant for a noiseless deterministic
map — magnitude loss of any size still reads back as "fully recoverable."
Between the two existing completeness measures and rank itself, none says
"erased" here; only reading the spectrum directly does, and ADR-017
anticipated exactly this by reporting the full spectrum alongside the
integer rank rather than inventing a threshold — this is the first
real-domain case that shows why that anticipation was necessary, not merely
cautious.

**Proposed wording — three pasteable additions.** (1) Append to Core §3.9,
alongside its two existing completeness candidates: "A third, detection
(not completeness) criterion is required, since mutual information and
residual-variance-explained both presuppose the erasure is already
located: a spectral criterion — e.g. effective rank at a declared
singular-value ratio, or the participation ratio `(Σσᵢ²)²/Σσᵢ⁴` — is what
actually detects 'substantially lower effective dimension' in the first
place." (2) Replace Spec §3.2's Proposition 3.2 rank bound with: "`r` is
the numerically-significant rank of `F_ℰ` at a declared tolerance (not
literal algebraic rank); the Gramian-truncation guarantee `rank G_k^post ≤
r` holds up to that same tolerance. A finite-rate, non-exactly-singular
erasure is the common case for any physically damped operator, not a
pathology, and MUST NOT be read as full-rank merely because no singular
value is exactly zero." (3) Append to Proposition 3.2: "The tolerance
above MUST be declared alongside the metric it is computed in (Core §3.9's
general metric-dependence requirement, restated here explicitly): a
rescaled metric rescales every singular value and therefore the
tolerance's absolute cutoff identically, so numerically-significant rank
is exactly as metric-dependent as the rank measurement it qualifies."

**Confidence.** High for the finding itself — the rank/spectrum split
(`7` of `7` at machine-epsilon tolerance, with two directions at `exp(-5)`
matching Core §7.1's own named components) is a direct measurement against
this repository's own declared erasure operator, not a constructed
counterexample, and it is the first time this repository's rank statistic
has been run against anything other than an exact-zero-singular-value
construction. Medium for the exact proposed spectral criterion (effective
rank vs. participation ratio vs. a stated ratio threshold are not
equivalent, and Spec would need to commit to one, or to declaring the ratio
without naming a canonical measure); high that *some* spectral criterion is
needed, since both Core-offered candidates provably fail to supply it here.

## E-33 — Spec §9.2 makes the semigroup residual a conformance check and neither Core nor Spec declares a metric for it; measured, the answer to a physical question about it swings by sixteen orders of magnitude on that undeclared choice. Neither document treats timescale separation at all, and Core §3.3's single-cause attribution is under-qualified — though stiffness itself, tested, does not confound it

**Target.** Core §3.3's semigroup paragraph — "any trajectory can be resampled
into arbitrary sub-intervals with **arbitrary split points**, each a valid
training triple... **Violation of semigroup consistency under sub-interval
resampling is a cheap, automatable proxy for insufficiency of `𝒮`**" — read
against Core §3.7's closure-defect treatment and against the absence of any
treatment of stiffness or temporal resolution anywhere in either document.

**Kind.** Correction

**Discovered.** **`[domain-assessment]`** — `docs/PHYSICS-ADEQUACY.md` §3.5,
domain assessment from flat-rolled steel ("recovery, recrystallisation, grain
growth and precipitation span seconds to hours in the same anneal. Their
coupling is stiff"), which proposed the sweep below as the cheapest of the four
tests it names. **Unlike every other entry in this ledger, this one was then
tested**: the prediction was measured, and the measurement refuted it as stated
while establishing a sharper finding. This is the first physics-derived
prediction this build has put to a test.

**Finding, part 1: the absence.** Neither Core nor Spec addresses timescale
separation. Searched directly across both documents: `stiff`, `timescale`,
`time scale`, `step size`, `temporal resolution`, `temporal coarse`, `fast
mode`, `slow mode`, `multirate` — **zero occurrences of any of them**. Core
defines an elementary evolution operator over `[t_k, t_{k+1}]` and gives no
guidance anywhere on how that interval is chosen or bounded. Mori–Zwanzig
appears three times and every one is spatial: Core §3.7 projects "to **scale**
λ" via "computational homogenisation, variational Γ-convergence, bounds
hierarchies, and n-point statistical descriptors" and grounds its rejection of
RG in matter possessing "characteristic **lengths**"; Core §6.2 asks for
"Learnable Mori–Zwanzig memory kernels for **structural** coarse-graining" —
Core's own adjective. So the framework has a careful, measured treatment of
*spatial* coarse-graining and none whatsoever of the temporal analogue, which
raises the same Mori–Zwanzig issue.

**Finding, part 2: the prediction was measured twice, and refuted both times —
decisively at the sharpened design.** The first pass used a coupled generator
and swept two fast-mode regimes; the second pass used the canonical stiff-decay
design this finding's own motivation describes — state `(x_fast, x_slow)`,
**decoupled** pure decay, `r = λ_fast/λ_slow` swept over three decades, both
modes explicit so **sufficiency is exact rather than assumed** (Markovian by
construction, no hidden variable a residual could be blamed on). An exact
analytic null arm is run first at every ratio and must sit at machine precision,
so that anything the other arms report is attributable to the operator rather
than to the physics being stiff; it does (`worst 6.94e-18`). Reproducible via
`scripts/run_m10_4_stiffness_sweep.py`.

| arm | `r = 1` → `r = 1000` | verdict |
|---|---|---|
| exact analytic (the null) | worst `6.94e-18` | passes — stiffness alone generates no residual |
| fixed step **count**, explicit Euler, stable throughout (`max λ·h = 0.977 < 2`) | `1.271e-04` → `8.987e-05` | **flat**: spread `1.58×`, last/first `0.71×` |
| fixed step **size**, commensurable split | `0.00e+00` at every `r` | vacuous pass |
| learned operator trained at one `Δt` | `0.14`–`0.30`, no trend | dominated by unseen duration, not stiffness |

**The per-component decomposition supplies the mechanism, and it is physical.**
The slow component contributes `8.987e-05` at *every* ratio — stiffness-independent
to every digit, as it must be, since the slow mode's own dynamics do not depend on
`r`. The fast component's contribution rises briefly (peak at `r=3`) and then
collapses super-exponentially: `1.08e-06` at `r=10`, `1.52e-14` at `r=30`,
`4.94e-324` at `r=1000`. **Once the fast mode is stiff it is annihilated
identically in the coarse and the fine evaluation, so their difference vanishes
and it leaves the measurement.** Being under-resolved is precisely what removes a
stiff mode from this diagnostic, which is why stiffness cannot confound it in the
way the prediction supposed.

**Finding, part 3, and this is what the sweep did establish: Spec §9.2 makes the
semigroup residual a conformance check and no document declares a metric for it,
while the answer to a physical question about it swings by sixteen orders of
magnitude on that undeclared choice.** Spec §9.2 lists "semigroup consistency on
random sub-interval splits" among nine automated checks; Core §3.3 defines the
identity but no norm. This repository's own realisation returns a bare Euclidean
norm and defends the choice in its docstring — "a diagnostic residual, not a
metric-declared quantity" — while CLAUDE.md §5 invariant 1 holds that every
*state distance* is metric-dependent, and a semigroup residual is a state
distance. E-07/OQ-5 already established the dependence is real. Measured on the
two-mode system, where the fast mode's variance collapses as `r` grows:

| metric | `r = 1` → `r = 1000` | behaviour |
|---|---|---|
| raw Euclidean (this build's choice) | `1.271e-04` → `8.987e-05` | flat |
| identity, declared | identical to raw | flat |
| **incoming**-population σ (ADR-002's convention) | `6.338e-04` → `4.512e-04` | flat, spread `1.56×` |
| **outgoing**-population σ | `1.724e-03` → `9.789e+13` → `1.227e-03` | **spurious `5.7e+16×` excursion** |

The outgoing-σ arm divides by a vanishing number — `σ_fast` falls to `1.35e-155`
at `r=300` and underflows to exactly `0` at `r=1000`, where the zero-variance
guard fires and the value collapses back. **Anyone normalising that way would have
reported "residual grows with stiffness by fourteen orders of magnitude", and it
would have been entirely artifact.** ADR-002's convention draws σ from the
*incoming* population, which does not depend on `r`, so it is stiffness-independent
by construction and cannot manufacture the effect — the refutation above survives
every stiffness-independent metric. But nothing in Core or Spec says which
population the σ comes from, or that a metric is required at all. **A conformance
check whose reported value can differ by sixteen orders of magnitude on a choice
the specification never mentions is not a comparable quantity between two
implementations**, which is what a conformance level is for.

**Core §3.3's attribution is still under-qualified, though not for the reason
predicted.** It names one cause: "Violation of semigroup consistency under
sub-interval resampling is a cheap, automatable proxy for insufficiency of `𝒮`."
Temporal-resolution error is a second cause, present at exact sufficiency in
every non-null arm above — the fixed-step arm's `8.99e-05` and the learned arm's
`0.14`–`0.30` are both measured on states that are sufficient by construction,
so neither is insufficiency. What the sweep refutes is that this second cause
*grows with stiffness*; what it confirms is that the second cause exists, is not
small, and is not what the sentence names. The learned arm makes the practical
size of it plain: its residual runs `10×`–`106×` its own forward error at the
duration it was trained on, so the check reports mostly the fact that the network
was asked for an unseen `Δt`.

**Two candidate findings from this sweep, refuted and recorded rather than
filed.** *(a)* The fixed-step-size vacuous pass — exactly `0.00e+00` at every
stiffness ratio — looked like a defect in the check itself. It is not: Spec §9.2
specifies "**random** sub-interval splits", and a random split is almost surely
incommensurable with any fixed internal step, so the Specification already guards
against it. It remains a live hazard for implementations choosing *fixed* split
points, which this repository does (`t_mid` values of 0.2/0.5/0.8 and
0.2/0.4/0.6/0.8, none randomised) — a repository defect, not a framework one.
Measured, that hazard is worse than it first reads: on a commensurable split the
pass holds even where the fixed step has left explicit Euler's stability region
(`λ·h = 3`, `10`), because both paths diverge to the same wrong answer, so the
check scores `0.00e+00` on an operator whose output has blown up by twenty-seven
orders of magnitude.
*(b)* The first pass's confound claim — that a sufficient state and an
insufficient one give residuals within `1.25×` at one ratio — was measured
correctly but on a *persistently excited* (oscillatory) fast mode, not the
stiff-decay case this finding is about. It is narrowed to that case and no longer
carries this entry. Both are recorded in `docs/PHYSICS-ADEQUACY.md` §3.5.

**An artefact worth naming, because a careless version of this test would have
published it as a confirmation.** An early attempt used explicit Euler at a
coarse resolution and reported residuals of order `1e36` and `1e85` at high
separation. Those were the integrator diverging (`λ·h` past the explicit
stability limit of 2), not semigroup inconsistency. Every arm above therefore
reports `max λ·h` alongside its residual, and the sweep is confined to where the
scheme is stable.

**Proposed wording.** (1) **The metric, which is the robust finding.** Append to
Spec §9.2's semigroup bullet: "semigroup consistency on random sub-interval
splits, reported **against a declared metric on `𝒮`** (Core §3.2's `d_𝒮`). The
residual is a state distance and is therefore metric-dependent: on a system with
widely separated mode variances, the same operator's residual differs by many
orders of magnitude between a metric normalised by the incoming population's
per-component spread and one normalised by the outgoing population's, because the
latter divides by a variance that collapses. An implementation MUST state which
metric and, where the metric is population-normalised, which population — a
residual reported without both is not comparable to another implementation's and
MUST NOT be cited as evidence of conformance." (2) **The attribution.** Replace
Core §3.3's attribution sentence with: "Violation of semigroup consistency under
sub-interval resampling has at least two distinct causes and does not by itself
identify which is acting: insufficiency of `𝒮`, and inadequate temporal
resolution of the operator relative to the interval it is asked to span. The
second is present even when `𝒮` is sufficient by construction, and for an
operator fitted at one `Δt` it typically dominates. An implementation reporting a
semigroup residual as evidence about `𝒮` MUST also report the temporal resolution
at which its operators were fitted; without it the residual is not attributable.
**A small residual certifies neither cause absent**: a mode too fast to be
resolved at either the whole-interval or the split-interval step is annihilated
identically in both and drops out of the residual altogether, so an operator can
be grossly under-resolved in that mode and show no residual from it." (3) **The
temporal analogue.** Add to Core §4 item 7 (scale structure, which already
carries "where homogenisation is applied, between which scales"): "the temporal
resolution at which operators are defined, and the fastest mode timescale the
declared state is intended to represent — the temporal counterpart of the spatial
scale structure this item already requires." (4) Add to Core §3.7, whose closure
treatment is spatial throughout: "Temporal coarse-graining raises the same
Mori–Zwanzig memory-and-fluctuation issue as the spatial projection above, and
the three treatments (absorb, remember, fluctuate) apply to it unchanged. This
section's `Π_λ` is a projection in space; an analogous temporal projection is not
treated here and its closure defect is not currently measured."

**What this gives an interface sketch to look for** (`docs/SKETCHES.md`):
whether the domain's processes span timescales wide enough that one operator
interval cannot resolve the fastest, and — the question this sweep sharpens —
whether the fast mode *decays* or *persists*, since a decaying one drops out of
the diagnostic entirely while a persistent one does not. The assessment argues
that batteries span double-layer charging (microseconds) to SEI growth (months)
and so are stiffer than steel, that MOF guest diffusion, framework breathing and
degradation are similarly separated, and that semiconductor processing separates
implant-damage annealing from dopant diffusion by orders of magnitude; **those
are argued from domain knowledge, not from instantiations, and are recorded here
as claims with that basis, not as demonstrated.**

**Confidence.** High that Core and Spec contain no treatment of stiffness or
temporal resolution — a direct search returning zero hits on nine distinct terms
— and high that Core §3.7's closure discussion is spatial, on Core's own
vocabulary ("scale λ", homogenisation, "characteristic lengths", "**structural**
coarse-graining"). High that no document declares a metric for the semigroup
residual: Spec §9.2's bullet names the check without one, Core §3.3 defines the
identity without a norm. High on every measured number, each run against a
construction whose exact answer is known analytically, with an exact-flow null arm
confirming machine-precision residual at every ratio and `max λ·h` reported at
every point to exclude integrator divergence. High that the metric swing is real
and decision-relevant, on the `5.7e+16×` measurement, and high that ADR-002's
incoming-population convention is immune to it *by construction* rather than by
luck. **The prediction that residual grows with stiffness at exact sufficiency is
refuted, and is recorded as a refutation, not softened.** Medium on how far the
refutation generalises: a nonlinear stiff system, or a fast mode that is driven
rather than decaying, may behave differently — the first pass's oscillatory arm
did — so what is established is that stiffness does not confound the diagnostic
for the canonical stiff-*decay* case, not that no system can. Medium on the
proposed wording's placement for (3) (item 1 versus item 7).

## E-02 — Spec §1.4 does not specify how learning error composes across a chain mixing analytic and learned operators

**Target.** Spec §1.4 ("Learning error from rollout curve at matched
budget")

**Kind.** Demotion

**Discovered.** M8 (`src/omi/learning.py` added a learned-operator class for
the first time), noticed while writing ADR-023 and confirmed as an
unresolved gap during Phase 1's coverage-verification pass, four milestones
after M8.

**Finding.** `docs/COVERAGE.md` marks S-1.4 SPEC — a fully derived
procedure. In this repository, `learning_error()` takes no arguments and
unconditionally returns `0.0`. ADR-023 (`docs/DECISIONS.md`) declares this
the *correct* answer for a chain built entirely from exact analytic
operators (there is no learning error to report), which is a legitimate,
narrow reading of Spec §1.4 — but Spec §1.4 does not actually say how to
compute a learning-error term for a chain that mixes an exact analytic
operator with a learned one elsewhere in the same chain, which is exactly
the situation M8 makes possible and which S-1.1's three-term decomposition
implies should be supported (the learning term is one of the three, not a
term that vanishes whenever any part of the framework is used). No test,
oracle, or ADR in this repository has ever exercised `learning_error()`
against a mixed chain; the function has no code path that could return
anything other than `0.0` regardless of its (currently nonexistent)
arguments. A section marked SPEC ought not have an implemented function that
is only ever correct on the trivial sub-case.

**Update (Phase 3.2, ADR-036, `docs/DECISIONS.md`) — repository-side fix,
SPEC-text gap unchanged.** `learning_error` now takes a `chain: Chain`
parameter, returns `0.0` only when every segment is genuinely analytic,
and raises `NotSpecified` citing this entry when the chain contains a
learned operator — it no longer silently returns `0.0` regardless of chain
content. This closes the implementation-honesty problem ("a section marked
SPEC ought not have an implemented function that is only ever correct on
the trivial sub-case") but leaves the underlying Spec-text gap exactly as
found: Spec §1.4 still does not say what the correct nonzero answer is for
a mixed chain, which is why the fix is a refusal, not a computation.

**Proposed wording.** Append to Spec §1.4: "For a chain mixing analytic and
learned operators, the learning-error term is the rollout-curve error of
the learned sub-operator(s) alone (Spec §1.4's own procedure, applied to
just those segments), propagated through the surrounding analytic segments
via the chain's semigroup structure (Core §3.3) — not recomputed chain-wide
as if the whole chain were learned. Where a chain contains more than one
learned operator whose errors could interact non-additively through
intervening analytic segments, S-1.1's three-term decomposition MUST be
evaluated segment-wise, and a chain-wide learning term MUST NOT be reported
as if it were a single scalar with no stated combination rule."

**Confidence.** High that the gap exists (a repository-wide grep confirms
`learning_error` has exactly one behaviour, `0.0`, called from exactly one
test, which supplies an all-analytic chain). Medium on the exact fix, since
Spec would need to commit to a specific composition rule, and more than one
is defensible.

## E-10 — Spec §2.2's thermodynamic-admissibility category names a structure it does not supply

**Target.** Spec §2.2, fifth hard-constraint category (thermodynamic
admissibility / GENERIC / port-Hamiltonian structure)

**Kind.** Demotion

**Discovered.** M8, writing ADR-030 (`docs/DECISIONS.md`).

**Finding.** Spec §2.2 names five hard-constraint categories — symmetry,

presented with uniform specificity, and `docs/COVERAGE.md` marks S-2.2

(softplus for positivity, softmax for simplex/fractions, a monotone

parameterisation choice of the same kind as the other four; it is a missing
architectural decomposition that Spec §2.2 names by category label without
supplying.

**Proposed wording.** Re-mark Spec §2.2's fifth category: "Thermodynamic
admissibility (GENERIC / port-Hamiltonian structure) — **[Pass C]**:
requires committing to a specific decomposition of the learned operator's
own dynamics and how that structure composes with the chosen architecture;
neither this Specification nor Core resolves this decomposition. The other
four hard-constraint categories (symmetry, range, monotonicity,
conservation) are fully derived as stated." This mirrors S-7.1/S-7.2's
existing convention of splitting a SPEC part from a PASS-B/C part within
one row, applied here at the category level within §2.2.

**Confidence.** High — ADR-030's own text states the missing piece plainly
("a design question neither Spec nor Core resolves"), and the asymmetry
with the other four categories (parameterisation choice vs. architectural
decomposition) is a difference in kind, not degree.

## 8. A composition effect between two individually sound prescriptions

One entry in this ledger is not a defect in any single section, but a
consequence of composing two individually sound ones for the first time.
Spec §2.2's hard-constraint prescription and Core §5's gradient-based
search formulation, connected against the same contestant for the first
time this session, produce a failure mode — a zero-gradient extrapolation
shelf a search cannot move on — that neither section's own text anticipates
on its own (E-28). It is recorded separately from §4's and §7's groups
because it is neither a declaration satisfiable without its property nor a
stale marker: both prescriptions are correct as written, and the
consequence only exists once they are used together.

## E-28 — A hard monotone constraint's honest "no evidence" extrapolation shelf has zero gradient, so gradient-based search cannot move on it: Spec §2.2's constraint prescription and Core §5's search formulation compose into a failure mode neither names

**Target.** Spec §2.2 ("Hard constraints beat soft penalties, and this
matters most for inverse design... an optimiser searching for an optimal
route will find precisely the regions where enforcement is weak") read
together with Core §5 (inverse design as constrained optimal control;
"the optimiser is an adversary that seeks the region where the surrogate
is most confidently wrong" — the stated justification for the trust
region, `𝒰_trust`).

**Kind.** Addition

**Discovered.** M10.2's contrast control-inverse re-run (ADR-040,
`docs/DECISIONS.md`), building a hard-constrained operator
(`ConstrainedMonotoneOperator`, `src/omi/constraints.py::monotone_increasing`)
and inverting it with a genuinely new gradient-based search
(`gradient_control_search`, `src/omi/inverse.py`) — the first time either
prescription has been exercised together against the same contestant in
this repository.

**Finding.** Spec §2.2 argues for hard constraints on the grounds that a
soft penalty's enforcement is weak exactly where an adversarial optimiser
will search — its implicit picture is an optimiser that is always *moving*
under some gradient, and the risk is where that gradient carries it. Core
§5's trust region is motivated on a different, also implicit, picture: a
surrogate that is *miscalibrated but still confidently wrong* outside
`𝒰_trust`, and the risk is that an optimiser exploits that false
confidence. Neither passage anticipates a third case, which this session's
re-run produced directly: a hard constraint honestly built to represent
"no evidence past the training data" (`ConstrainedMonotoneOperator`'s
flat continuation once past `𝒰_TRUST` — not overconfident, not wrong, just
flat, exactly what Spec §2.2's own hard-constraint discipline should
produce when there is genuinely nothing to constrain against yet) has
**zero local gradient** on that flat region. `gradient_control_search`'s
update is `2 · residual · forward_grad(u)`; once the search enters the
flat shelf, `forward_grad(u) ≈ 0` regardless of how large the residual
against the true target still is, and the search simply stops — not
because it found a confidently-wrong answer (Core §5's risk) and not
because enforcement was weak there (Spec §2.2's risk), but because the
*combination* of "hard-constrained, honest about having no evidence" and
"gradient-based search" leaves nothing for the search to climb. This is
recorded directly in `docs/M10.2-BASELINE-CHARACTERISATION.md`'s ADR-040
addendum: the constrained operator's search genuinely leaves `𝒰_TRUST`
(unlike a grid search's fixed tie-break point) but then stalls on exactly
this shelf, at every record count tested.

**Not an argument against hard constraints.** Replacing the hard
constraint with a soft penalty here would not fix this — it would
reintroduce exactly the risk Spec §2.2 warns against (an optimiser
wandering into the region where a soft penalty's enforcement is weakest,
which is precisely the poorly-evidenced extrapolation region in
question). The finding is that the two sections' prescriptions, each
individually sound, **compose into a stated consequence that should be
declared rather than discovered by accident**: a hard constraint's
correctness (representing genuine absence of evidence honestly, as a flat
region rather than a fabricated trend) is exactly what removes the
gradient signal a search built on Core §5's own formulation needs.

**The trust region's role, reframed by this finding.** Core §5 states the
trust region's purpose as keeping the search "where the surrogate is
calibrated" — a calibration boundary. This finding shows a second,
distinct role it must *also* play when the operator is hard-constrained:
keeping the search **off the zero-gradient shelf entirely**, since once
the search crosses onto it, no further calibration concern is even
reachable — the search cannot move to discover whether it is confidently
wrong, because it cannot move at all. A trust-region check performed
*after* an unconstrained search (as `diagnose_infeasibility`, ADR-033,
already does — check where the returned candidate landed) can report that
the search stalled on the shelf; it cannot, by itself, keep the search
from stalling there in the first place. Expanding `𝒰_trust` "by targeted
experiments rather than by optimism" (Core §5's own stated remedy) is
exactly the right fix in this case too — but for a reason Core §5 does
not itself state: not only to keep the surrogate calibrated over a wider
region, but to give a gradient-based search terrain to climb at all.

**This was invisible until a hard-constrained operator was searched by an
actual gradient method, not merely certified or sampled.** M9's exit gate
built reachability certificates (necessary-condition checks on an
already-produced candidate) and apparatus parameterisation (uniform
forward sampling, never gradient-based) — neither exercises a
differentiable forward map under active search, so neither could have
surfaced this. It required M8's constraint machinery and a genuinely new
search method (this session) to be connected to the same contestant
before the interaction became visible at all.

**Proposed wording.** Append to Core §5, alongside the trust-region item:
"A hard-constrained operator's trust-region boundary should additionally
be understood as a *search-terrain* boundary, not only a calibration
boundary: where the constraint architecture defaults to a flat,
evidence-honest continuation past the region training data supports (the
correct behaviour Spec §2.2 recommends), a gradient-based search has no
local signal to exploit past that point, independent of whether the
surrogate there happens to be well- or mis-calibrated. Expanding `𝒰_trust`
by targeted experiments serves both purposes; declaring only the
calibration purpose understates why the expansion is necessary for a
gradient-searched, hard-constrained operator specifically."

**Confidence.** High that the mechanism is real: `forward_grad`'s value in
the shelf region is directly inspectable and is not merely small but
`≈0` at the resolution this repository's re-run used, and the search
trajectories recorded in `docs/M10.2-BASELINE-CHARACTERISATION.md` show
it stalling exactly there, at every record count tested. Medium on how
general the finding is beyond a piecewise-linear monotone constraint
specifically — a hard constraint with a non-vanishing derivative in its
"no evidence" region (a different architectural choice, not explored here)
might not exhibit this interaction at all, so the proposed wording is
written as a conditional ("where the constraint architecture defaults to
a flat continuation"), not a universal claim about all hard constraints.

## E-07 — OQ-5: metric dependence is already correctly required; no edit proposed

**Target.** Core §3.9 / Spec §2.5 (metric-dependence requirements)

**Kind.** Confirmation (no edit proposed — deliberately not one of the five
standard kinds)

**Discovered.** M2, `tests/oracles/test_metric_dependence.py` (the test
ADR-002, `docs/DECISIONS.md`, names).

**Finding.** A fixed linear coupling (raw off-diagonal coefficient 0.01, one
component's natural scale 100x the other's) demonstrates both halves of the
hypothesis directly: every reported Lipschitz constant changes with the
declared metric (a different matrix gets SVD'd, not an approximation), and
a bare/undeclared metric hides real coupling that the aleatoric-sigma metric
correctly reveals as comparable to the diagonal — matching direct empirical
perturbation. This confirms the existing requirement does what it is meant
to. **No framework edit is proposed.** Core §3.9 and Spec §2.5 already
require a declared metric and a local spectrum rather than a global bound;
this investigation supplies a constructed counterexample to the "just read
the raw Jacobian" alternative, demonstrating why the requirement exists,
without revealing any gap, error, or omission in the requirement itself.

**Proposed wording.** None. This entry exists specifically to record that
an investigation was run to completion, on the same footing as the four
that produced edits, and produced a negative result — the framework was
already right — rather than to be silently dropped for not yielding a
correction. Not every investigation should be expected to find a defect;
recording the ones that don't is what keeps the ones that do credible.

**Confidence.** High — this is a statement about what the investigation
found (nothing to change), not a claim requiring further evidence to
strengthen.

## 10. A second, orthogonal reading: which practitioner intervention each finding blocks

**This section reclassifies nothing.** §2–§9 group the entries by *defect
mechanism* — what is wrong with the framework. This section reads the same
thirty-three entries along a different axis: *what a practitioner cannot be
told* because of them. Both classifications are true, and neither subsumes the
other. An entry appears here under the intervention its finding most directly
blocks, and every entry is accounted for, including the ones that block none.

The axis exists because it is part of what the framework is *for*. Core's
purpose includes telling a practitioner which purchase to make next, and the
framework has machinery aimed squarely at that: Spec §1.7's blocking trichotomy
(variance-blocked → buy sensing; learning-blocked → buy data; bias-blocked →
falsification) and Spec §3.3's danger score with §3.4's value of information.
Reading the ledger along this axis asks whether that machinery covers the space
of interventions a practitioner actually has.

**It does not, and the shortfall is structural rather than incidental.**

| Intervention | Framework's mechanism | Entries that block it |
|---|---|---|
| **Buy sensing** — add or move an instrument | Danger score `𝒟ᵢ` (Spec §3.3); value of information `ΔV_c/cost` (Spec §3.4); Spec §1.7's variance-blocked branch | E-20, E-23, E-04, E-18, E-19 |
| **Buy characterisation** — commission a measurement of incoming material or defect population | **None.** See below. | E-31, E-29, E-13, E-05, E-15 |
| **Buy data** — more runs, more simulation, better-trained operators | `Err_learn` (Spec §1.4); Spec §1.7's learning-blocked branch | E-02, E-33 |
| **Buy physics** — commission or declare a mechanistic relationship | **None.** See below. | E-32, E-30, E-10, E-28, E-25 |
| **Run experiments** — a designed campaign, probes, a validation ladder | Sufficiency campaigns (Spec §8, with §1.6's probe design); Spec §4.6's four-rung ladder | E-14, E-12, E-03 |
| **Declare out of scope** — refuse, or state the chain is unpredictable at the required precision | The error-control dichotomy (Core §3.9); `omi.gaps.NotSpecified`; Core §6.1's falsification criteria; Spec §7.1's non-reachability certificates | E-11, E-16, E-17, E-26, E-27, E-21 |

**The two empty cells were predicted and the prediction holds.** Checked
against Core and Spec directly, not inferred: Spec §3.4 prices *observations*
and modalities, which is sensing; Spec §8 sizes *campaigns*, which is
experiments; Spec §1.4 measures *learning* error, which is data; Spec §1.7's
trichotomy names three branches and one of them (bias-blocked) is falsification,
which is the out-of-scope row. Nothing anywhere prices a **characterisation
suite** — E-31's finding is that the suite is not even declarable, so it cannot
be costed — and nothing anywhere lets a domain **declare a physics
relationship** as such, which is E-32's finding. **A framework that diagnoses
six practitioner interventions and supplies mechanisms for four is a finding in
its own right**, and it is this ledger's most practitioner-facing one.

**The two axes converge, which is the strongest thing this section says.** The
two mechanism-less rows are *exactly* the two whose missing declarable category
§5 documents: buy characterisation ↔ E-31 (the characterisation suite has no
declarable home), buy physics ↔ E-32 (a constitutive form has no declarable
home, and is refused by name). Ten of the thirty-three entries block an
intervention the framework has no mechanism for at all. A defect-mechanism
reading finds "the interface has no slot for this"; an intervention reading
finds "the practitioner cannot be told to buy this." They are the same hole,
and neither reading alone shows that it is load-bearing.

**Seven entries block no intervention on this axis, and that is not a
weakness in them.** E-01, E-08 and E-09 are status-marker corrections; E-22 and
E-24 are internal type-consistency findings (E-24 *unblocks*, being a
promotion); E-07 is the confirmation that found nothing wrong. E-06 is the
interesting exception: it is not blocked by anything on this axis because it
*is* this axis, in miniature — Spec §7.3's infeasibility report must say which
of trust region, admissible control, or aleatoric spread binds, in order, which
is the same "which purchase next" question posed for inverse design
specifically. E-06's ordered diagnosis is the closest thing the framework has to
a general intervention-selection mechanism, and it is scoped to one module.

**What would fill the empty cells.** For *buy physics*, E-32's proposed
declared-constitutive-form category already carries the mechanism in its own
proposed wording: an operator constrained to a declared form MUST report "where
the current query sits relative to that range." That is a computable
extrapolation signal — *this evaluation is outside the validated envelope of
this relationship* — and it is the first thing in the framework that would
answer "should I buy physics here?" with a number. For *buy characterisation*,
E-31's proposed suite declaration is the precondition (you cannot cost what you
cannot declare), but no pricing mechanism follows from it yet, and this ledger
does not propose one — that is an open framework question, not an
implementation choice, and is recorded as such.

## 11. What this implementation attempt could not test

The findings above are what this build found. This section states, with
equal deliberateness, what it never attempted — a reader should be able to
see the shape of the untested claims, not only the tested ones.

**CLAUDE.md §9's anti-goals, and what each one leaves permanently outside
this ledger's reach:**

- **Tier II boundary value problems and FE² coupling** (except Tier I½,
  ADR-035's bounded exception). No domain in this repository ever needed
  real meshing, element assembly, equilibrium iteration, or contact/
  friction. Every claim Core or Spec makes specifically about Tier II
  *performance* readouts (as opposed to Tier I/I½ *property* readouts,
  Core §2.6) is entirely unexercised here — this ledger has nothing to say
  about whether those claims hold, only that they were never attempted.
- **Hybrid mode/guard structure and jump maps** (Spec §5.1). E-24 shows a
  hybrid domain's *control-space declaration* survives this gap cleanly —
  but Core §3.4's own *evolution* claims (the mode-labelled graph, guards,
  jump maps themselves) were never simulated for any domain in this
  repository. Layer-wise additive manufacturing's control programme was
  declared; it was never executed.
- **Body-indexed state and the registration operator** (Spec §5.2) — the
  direct cause of §2's finding, the single largest in this ledger. This is
  not incidental: this anti-goal is *why* Core §2.5 was never going to be
  resolved by this implementation attempt, by its own declared scope, not
  by an oversight discovered along the way. E-14, E-21, E-22, and E-25 are
  the visible symptoms of a boundary this build set for itself before any
  of them were found.
- **Closure-defect measurement procedure** (Spec §6). Core §3.7's
  *definition* of closure defect is implemented; the *measurement*
  procedure is an unconditional refusal stub. Core §6.1's own criterion 2
  (closure defect blocking multi-scale composition) can never be evaluated
  while this stays out of scope — named explicitly in E-16, not a separate
  finding.
- **Closed-loop confounding remedies** (Spec §5.3). Untouched. Every
  assimilation campaign in this repository (`src/omi/assimilate.py`'s EnKF
  and smoother) is open-loop: forecasting against a fixed, predetermined
  control sequence, never a controller reacting to its own state estimate.
  Nothing here bears on what happens when the two feed back on each other.
- **The linear-Gaussian proof of the error-control dichotomy** (Core
  §3.9). This repository's evidence (E-20, and the domain triage work it
  draws on) bears on whether each domain's *declared* satisfaction of
  conditions (a)/(b) holds up under a real, non-degenerate query point —
  never on whether the two conditions are provably the *complete* set a
  theorem would establish. The dichotomy's own proof was never attempted.
- **Compute-budget and modality catalogue numbers** (Spec §3.7, §12).
  Untouched. No resource-cost, wall-clock, or instrumentation-catalogue
  claim appears anywhere in this ledger.

**Two further limits, not from a named anti-goal but from this
repository's own nature:**

- **Prospective inverse-design validation** (Spec §9.3: "propose settings,
  execute them, report hit rate") is structurally unreachable in a
  repository whose only "ground truth" is the same analytic simulator used
  to generate training labels — there is no independent execution to
  propose settings *to*. This is E-16 criterion 4's own finding, restated
  here as a boundary rather than a defect: no amount of further
  in-repository work closes it, since closing it needs a real apparatus,
  not more code.
- **The generality claim's own falsification condition** — a domain that
  *fails* to fill Core §4's seven-item interface — remains untested. The
  four sketches attempted here (flagship and contrast implemented in full;
  layer-wise additive and crystallisation/formulation declared but not
  simulated) filled the interface in every case, including where filling
  it strained the framework's own text badly enough to produce a finding
  (E-21, E-22, E-23, E-24) — but strain is not failure. No sketch was
  pushed to the point of being unable to fill an item at all, so whether
  the seven-item interface is *falsifiable* in this specific sense — not
  merely stretchable — is a question this build raised and did not answer.

None of this is a gap in what was reported; it is a boundary this
implementation attempt drew around itself from the start, stated here so a
reader can weigh the twenty-eight findings above against what they were,
and were not, given the chance to find.

- Add an entry the moment a framework defect is found (CLAUDE.md §10),
  before writing the ADR that records how this repository copes with it in
  the meantime. Give it the next `E-NN` number in sequence — numbers are
  assigned once and never reused or reordered, regardless of where the
  entry ends up presented.
- File the new entry into whichever of §2–§9 shares its root cause; if it
  shares none, open a new numbered section rather than forcing it into the
  nearest existing one, and update §1's summary table and the entry
  locator table accordingly. A grouping that stops matching the entries it
  contains is a sign the grouping needs revisiting, not that an entry
  should be bent to fit it. **§2–§9 hold entries; §10 and §11 do not.** §10
  is a second, orthogonal reading of the same entries and must be updated
  when one is added — assign the new entry an intervention row, or state
  that it blocks none, which is a legitimate outcome and already true of
  seven entries. §11 is the closing statement of what was never attempted.

  gravity and **cross-referenced** from the other group's lead, never split
  across two sections and never duplicated under a second number. E-33 is
  the precedent: filed in §6 for its metric finding, cross-referenced from
  §5 for its temporal-resolution finding, counted in both places explicitly
  so neither count misleads.
