# V1.4-EDITS.md

The ledger of everything this build has learned that the framework itself —
not this repository's implementation of it — should absorb before a v1.4
revision. CLAUDE.md §2: "the codebase's primary outputs are evidence and
*corrections*." This file is where a correction goes the moment it is found,
before any ADR records how the code copes with it in the meantime.

This document is written to be read **without** the repository: it quotes
rather than cross-references wherever the finding itself needs no repository
context to state or evaluate, and gives repository pointers only as
supporting evidence for readers who want to verify a finding, not as a
substitute for stating the finding in full.

Entries are numbered `E-NN` in discovery order, not by section or severity.

---

## Entry template

```markdown
## E-NN — <short title>
**Target.** Core §x / Spec §y, precise location
**Kind.** Correction | Addition | Promotion | Demotion | Threshold
**Discovered.** milestone, and by what — test, oracle, or implementation attempt
**Finding.** what is wrong or missing, with the evidence
**Proposed wording.** verbatim replacement or addition text
**Confidence.** high / medium / speculative, and what would raise it
```

A couple of entries below are not clean fits for the five `Kind` values
(they are confirmations that an investigation found no defect, or findings
still awaiting a proposed wording). Rather than force them into the wrong

## E-01 — Core §7.2's comparison table names six of Core §4's seven items, not seven

**Target.** Core §7.2 (the flagship/contrast comparison table) against Core
§4 (the seven-item instantiation interface)

**Kind.** Correction

**Discovered.** Phase 1 of remediation work following the M0–M9 build, by a
provenance-labelled review extraction (`build/REVIEW-EXTRACT.md` §3) that
mapped Core §7.2's table rows onto Core §4's interface items one by one, and
formalised as ADR-034 (`docs/DECISIONS.md`).

**Finding.** Core §7.2's table has seven rows: "Erasure operators,"
"Observation suite," "Dominant slot," "Control axis," "Tier structure,"
"Class B," and "Nonlocal slot ν." Core §4 declares seven interface items:
(1) state schema, (2) control space, (3) erasure inventory, (4) readout
catalogue, (5) observation suite, (6) invariants, (7) scale structure.
Mapping the table's rows onto the items shows the table's seven rows test
only **six** distinct items — "Dominant slot" and "Nonlocal slot ν" both
name item 1 (the state schema), and item 6 (invariants) has no row in the
table at all. Core §7.3's own prose is careful about this ("behave
oppositely on **six** of seven interface items"), but the table itself, read
on its own, has seven rows and invites the reader to count seven-for-seven.
An implementation checking "differs on at least six of seven" against the
*table's row count* rather than against the *specific six items* would
validate on the wrong axis, and — as this repository's own first
implementation did (ADR-003's original pinning test, superseded by ADR-034)
— could pass for the wrong reason: by counting an incidental difference on
item 6 (invariants, untested by the table) rather than a difference on all
six of the items the table actually names.

**Proposed wording.** Restructure Core §7.2's table (or add an explicit
mapping note beside it) so each row states which Core §4 item it tests, and
add an explicit statement that item 6 (invariants) is untested by this
comparison. If item 6 is meant to be part of the inversion claim, Core §7.2
should add a row for it directly rather than leaving it to be inferred from
counting; if it is not meant to be part of the claim, that should be stated
so a reader does not assume all seven items are covered.

**Confidence.** High — this is a mechanical mismatch between two lists in
the same document, checkable by lining them up side by side; it does not
depend on interpretation.

## E-02 — Spec §1.4 does not specify how learning error composes across a chain mixing analytic and learned operators

**Target.** Spec §1.4 ("Learning error from rollout curve at matched
budget")

**Kind.** Demotion

**Discovered.** M8 (`src/omi/learning.py` added a learned-operator class for
the first time), noticed while writing ADR-023 and confirmed as an
unresolved gap during Phase 1's coverage-verification pass, four milestones
after M8.

**Finding.** `docs/COVERAGE.md` marks S-1.4 SPEC — a fully derived
procedure. In this repository, `learning_error()` takes no arguments and
unconditionally returns `0.0`. ADR-023 (`docs/DECISIONS.md`) declares this
the *correct* answer for a chain built entirely from exact analytic
operators (there is no learning error to report), which is a legitimate,
narrow reading of Spec §1.4 — but Spec §1.4 does not actually say how to
compute a learning-error term for a chain that mixes an exact analytic
operator with a learned one elsewhere in the same chain, which is exactly
the situation M8 makes possible and which S-1.1's three-term decomposition
implies should be supported (the learning term is one of the three, not a
term that vanishes whenever any part of the framework is used). No test,
oracle, or ADR in this repository has ever exercised `learning_error()`
against a mixed chain; the function has no code path that could return
anything other than `0.0` regardless of its (currently nonexistent)
arguments. A section marked SPEC ought not have an implemented function that
is only ever correct on the trivial sub-case.

**Proposed wording.** Spec §1.4 should state explicitly how the
learning-error term composes across a chain with heterogeneous
sub-operators — at minimum, whether it is the rollout-curve error of the
learned sub-operator(s) alone, propagated through the surrounding analytic
segments via the chain's own semigroup structure (Core §3.3), some other
explicit combination rule, or (if genuinely no general combination exists)
a statement that S-1.4 applies per-operator and the three-term
decomposition of S-1.1 must be evaluated segment-wise rather than
chain-wise for a mixed chain.

**Confidence.** High that the gap exists (a repository-wide grep confirms
`learning_error` has exactly one behaviour, `0.0`, called from exactly one
test, which supplies an all-analytic chain). Medium on the exact fix, since
Spec would need to commit to a specific composition rule, and more than one
is defensible.

## E-03 — OQ-1: the divergence fingerprint table should name paired-probe contrasts, not single probes

**Target.** Spec §1.6 (divergence fingerprint table)

**Kind.** Addition

**Discovered.** M4, `tests/oracles/test_known_insufficiency.py`
(`test_oq1_single_probe_direction_gives_the_same_deficit_either_way`,
`test_oq1_discriminating_signature_separates_kinematic_from_magnitude_type`).

**Finding.** Spec §1.6 identifies missing components by *which single probe*
shows divergence (e.g. "reversed driving only → kinematic variable"). A
constructed kinematic-type hidden variable, tuned so its effect on the
response has equal magnitude under forward and reversed subsequent driving
and differs only in sign, diverges under *either* probe alone at
essentially the same magnitude (ratio within 30% at 8000 pairs) — so
"reversed driving only" is false of this variable even though it is exactly
the directional/kinematic type Spec §1.6's table means to name. A
single-probe reading reports "insufficient" correctly but cannot
distinguish this candidate from a non-directional one showing the same
single-probe divergence: `discriminating()` on the naive single-probe
signature returns `False` for two candidates tuned to share one probe's
divergence, while the symmetric/antisymmetric decomposition (ADR-022,
`docs/DECISIONS.md`) correctly separates them.

**Proposed wording.** Rows in the divergence fingerprint table (Spec §1.6)
should name *contrasts between paired-probe responses* (e.g. "antisymmetric
under forward/reversed reversal → kinematic variable") rather than "which
single probe diverges" — the latter is unreliable exactly for the
directional-variable case the table most wants to catch.

**Confidence.** High — demonstrated on a constructed counterexample where
the single-probe rule provably fails to discriminate two variables the
framework needs to tell apart.

## E-04 — OQ-2: erasure completeness must be read from recoverability, not raw magnitude

**Target.** Core §3.9, consequence 3

**Kind.** Addition

**Discovered.** M2, `tests/oracles/test_known_erasure.py`
(`test_oq2_naive_magnitude_heuristic_disagrees_with_recoverability`).

**Finding.** Core §3.9 consequence 3 offers "mutual information between
pre- and post-erasure states, *or* residual variance explained by upstream
variables" as alternative erasure-completeness criteria, without warning
against a third, more naive reading: a component's own raw magnitude or
variance reduction. On a diagonal, designed-rank Jacobian with one
full-gain, one small-gain (0.15), and one exactly-zero-gain component, a
naive "fraction of variance retained" reading calls the small-gain component
more than 95% erased (it loses 97.75% of its variance), while the
operator-level rank (`measure_erasure`, via SVD) and a per-component
recoverability estimate (`component_recoverability`, R² of post-step
regressed on pre-step) agree with each other and correctly call it fully
surviving/assimilable (R² > 0.999). The naive magnitude heuristic is the one
that is wrong.

**Proposed wording.** Append a caveat to Core §3.9 consequence 3: "Erasure
completeness must not be read off a component's raw magnitude or variance
reduction: a component can lose most of its magnitude and remain exactly
recoverable. Use mutual information or residual variance explained (R²)
against the pre-erasure state, not the component's own scale."

**Confidence.** High for the diagonal (non-mixing) case demonstrated here.
The genuinely open half of this question — whether operator-level rank
still predicts *per-component* influence under a mixing (non-diagonal)
erasure Jacobian — remains untested in this repository at every milestone
through M9 (`tests/oracles/known_erasure.py`'s `DiagonalErasureOperator` is
the only erasure oracle that exists); no wording is proposed for that half
until it is.

## E-05 — OQ-3: competing defect populations require separate tail transfer, not a pooled fit

**Target.** Spec §4.3, after Proposition 4.1

**Kind.** Addition

**Discovered.** M6, `tests/test_classb_competing_risks.py`.

**Finding.** Spec §4.3 transfers a tail index from one defect population.
With several populations of differing `α` and `β`, survival is
`∏ₚ[1−Fₚ]^{Nₚ}` and no single `ξ` describes the range of interest. A common,
light-tailed population (`α=5`, 10,000 members) and a rare, heavy-tailed
population (`α=1.5`, 10 members) driving the same component: at a design
point deep enough that the rare population's heavier tail dominates its
total exceedance contribution despite 1000x fewer members, pooling every
descriptor and fitting one Hill tail index — exactly what a practitioner
unaware of the two populations would do — underestimates the true,
competing-risk-aware failure probability by orders of magnitude (observed
ratio > 1000x in the constructed case; a fresh re-run for
`build/REVIEW-EXTRACT.md` measured 2597x at a fixed seed). The pooled fit's
tail index lands close to the *common* population's own `α`, because the
top order-statistic window used for fitting is filled overwhelmingly by its
far greater count, even though every individual common-population value is
smaller than the rare population's.

**Proposed wording.** Append a requirement to Spec §4.3, after Proposition
4.1: "Where more than one defect population plausibly contributes to the
same driver, each population's tail index MUST be measured and transferred
separately (`ξ_{D,p} = β_p·ξ_{a,p}`) and combined via the competing-risks
survival product; fitting a single pooled tail index across populations of
differing severity is non-conforming, since the fit is dominated by
whichever population is most numerous in the fitting window, not by
whichever population actually governs the design point."

**Confidence.** High — demonstrated at more than three orders of magnitude
of error in the unsafe (underestimating) direction, on a constructed case
built specifically so the answer is known.

## E-06 — OQ-4: inverse design must report which term makes the feasible set empty, in order

**Target.** Spec §7.3

**Kind.** Addition

**Discovered.** M9, `tests/oracles/test_known_infeasible_specification.py`.

**Finding.** Spec §7.3 selects within a feasible set but does not say what
to report when the set is empty. `diagnose_infeasibility` (ADR-033,
`docs/DECISIONS.md`) checks three candidate binding terms in a fixed,
principled order — trust region, then control/`𝒰_adm`, then aleatoric
spread at a declared coverage fraction — and four constructed scenarios
(one per binding term, plus a genuinely feasible case) sharing one linear
response model, each engineered so exactly one term is responsible, confirm
the diagnostic recovers the constructed truth in all four. The order is not
incidental: a trust-region violation means the model was never asked to
extrapolate there (a modelling-scope question), a control violation means
the apparatus cannot reach the window regardless of noise (a capability
question), and only when both are satisfied does the aleatoric question
("is incoming variation too wide") become meaningful at all. Checking them
in any other order, or reporting all three simultaneously as an unordered
set, would obscure this dependency.

**Proposed wording.** Append to Spec §7.3, as an explicit requirement: "When
the decision layer's feasible set is empty, an implementation MUST report
which of trust region, apparatus admissibility (`𝒰_adm`), or aleatoric
spread is responsible, checked in that order (a violation earlier in the
order makes the later checks not yet meaningful). Reporting only that the
set is empty is non-conforming."

**Confidence.** High — the diagnostic recovers the constructed truth exactly
in all four engineered scenarios, and the ordering argument follows directly
from what each term means, not from an arbitrary convention.

## E-07 — OQ-5: metric dependence is already correctly required; no edit proposed

**Target.** Core §3.9 / Spec §2.5 (metric-dependence requirements)

**Kind.** Confirmation (no edit proposed — deliberately not one of the five
standard kinds)

**Discovered.** M2, `tests/oracles/test_metric_dependence.py` (the test
ADR-002, `docs/DECISIONS.md`, names).

**Finding.** A fixed linear coupling (raw off-diagonal coefficient 0.01, one
component's natural scale 100x the other's) demonstrates both halves of the
hypothesis directly: every reported Lipschitz constant changes with the
declared metric (a different matrix gets SVD'd, not an approximation), and
a bare/undeclared metric hides real coupling that the aleatoric-sigma metric
correctly reveals as comparable to the diagonal — matching direct empirical
perturbation. This confirms the existing requirement does what it is meant
to. **No framework edit is proposed.** Core §3.9 and Spec §2.5 already
require a declared metric and a local spectrum rather than a global bound;
this investigation supplies a constructed counterexample to the "just read
the raw Jacobian" alternative, demonstrating why the requirement exists,
without revealing any gap, error, or omission in the requirement itself.

**Proposed wording.** None. This entry exists specifically to record that
an investigation was run to completion, on the same footing as the four
that produced edits, and produced a negative result — the framework was
already right — rather than to be silently dropped for not yielding a
correction. Not every investigation should be expected to find a defect;
recording the ones that don't is what keeps the ones that do credible.

**Confidence.** High — this is a statement about what the investigation
found (nothing to change), not a claim requiring further evidence to
strengthen.

**Target.** Core §2.2 ("State selection as measurable bias–variance")

**Kind.** Promotion

**Discovered.** Phase 1's coverage-verification pass, cross-referencing

**Finding.** `docs/COVERAGE.md`'s own Part I entry for C-2.2 already

**estimators are SPEC** in Spec §1." Core §2.2 is marked PASS-B — result
stated, derivation missing — on the strength of Core's own text read in
isolation. But Spec §1 supplies a complete, implemented, oracle-verified,
and domain-exercised three-term deficit estimator (`δ² = E[(ρ_A−ρ_B)²] −
2σ²_rep − Σ(∂ρ/∂s)²E[Δs²]`, S-1.2) for exactly the content Core §2.2

been stale since Spec §1 was read alongside it, and nothing in either
document currently says so — a reader of Core §2.2 alone would have no way
to know the derivation it flags as missing already exists, two documents
away.

**Proposed wording.** Either (a) Core §2.2 should be repromoted (from
PASS-B to a status reflecting that Spec §1 discharges its derivation in
full) with its text amended to cite Spec §1 directly, so the claim does not
read as underived in isolation; or (b) if Core §2.2 is intended to name
strictly more than Spec §1's specific bias-variance decomposition delivers,
that additional scope should be stated explicitly, so the remaining gap is
nameable rather than left implicit in a marker that predates the section
that (partially or fully) resolves it.

**Confidence.** Medium — this is a cross-document consistency finding
within the framework's own text, not an implementation-derived discovery of
the same kind as the others in this ledger. Raising confidence requires the
framework authors to state whether Core §2.2 was scoped to be identical to
Spec §1's estimator or to cover something Spec §1 does not yet reach.

## E-09 — Spec §4's SPEC marking covers boxed formulas but not the numeric conventions around them

**Target.** Spec §4.2 ("Driver/tail separation; join threshold"), §4.3
("Tail transfer"), §4.4 (correlation length), §4.5 (subset simulation) —
S-4.2 through S-4.5 in `docs/COVERAGE.md`

**Kind.** Demotion (contested — see Confidence)

**Discovered.** M6, writing ADR-027 (`docs/DECISIONS.md`).

**Finding.** `docs/COVERAGE.md` marks S-4.1 through S-4.6 all SPEC. ADR-027
explicitly declines to treat this as a gap ("Gap. none... every item below
is a declared numerical convention within a fully derived formula, not a
derivation gap"). But the count of choices ADR-027 had to make by its own
ADR, rather than by reading Spec §4's text, is not small: the join threshold
(§4.2 states only "typically the 90th to 95th percentile," not a value);
the tail-index estimator (§4.3 requires a "measured" tail index but names
no estimator, so ADR-027 chose the Hill estimator over a GPD fit); the
correlation-length crossing convention and its error-bar procedure (§4.4
says `ℓ_D` comes "from the two-point autocorrelation of the driver field"
without naming a crossing rule or an error-bar method, and separately notes
the estimate is "biased low on short domains" without supplying a
correction); and the subset-simulation proposal distribution (§4.5 names
"modified Metropolis sampling" without fixing a proposal). Four separate,
ADR-worthy numerical decisions inside one nominally fully-derived section is
a materially larger implementer's burden than other SPEC sections in this
repository carry — contrast S-1.2's boxed formula, which needed no ADR at
all to implement.

**Proposed wording.** Either split Spec §4's SPEC marking per sub-item to
distinguish the boxed formulas (Proposition 4.1's `ξ_D = βξ_a`, Proposition
4.2's two-branch `N_eff` formula) — genuinely fully derived — from the
surrounding numeric conventions that are not fixed by the text (join
threshold value, tail-index estimator choice, correlation-length crossing
convention and error bar, subset-simulation proposal distribution); or
supply default values for each convention directly in Spec §4, matching the
specificity Propositions 4.1 and 4.2 already have.

**Confidence.** Speculative — this repository's own ADR-027 disagrees with
classifying this as a gap, on grounds that are reasonable (a "convention
within a derived formula" is a real and different category from "the
formula itself is undetermined"). Recorded here as a candidate for the
framework authors to weigh, since the volume of convention-level decisions
required is unusual even if each individual one is defensible as "just a
convention."

## E-10 — Spec §2.2's thermodynamic-admissibility category names a structure it does not supply

**Target.** Spec §2.2, fifth hard-constraint category (thermodynamic
admissibility / GENERIC / port-Hamiltonian structure)

**Kind.** Demotion

**Discovered.** M8, writing ADR-030 (`docs/DECISIONS.md`).

**Finding.** Spec §2.2 names five hard-constraint categories — symmetry,
thermodynamic admissibility, range constraints, monotonicity, conservation —
presented with uniform specificity, and `docs/COVERAGE.md` marks S-2.2
SPEC accordingly. Four of the five were implemented directly from Spec's own
named mathematical shapes as literal, differentiable reparameterisations
(softplus for positivity, softmax for simplex/fractions, a monotone
cumulative sum of softplus increments, an affine projection for
conservation) — each needed only a parameterisation choice. The fifth,
thermodynamic admissibility, could not be implemented the same way: ADR-030
found it "requires committing to a specific decomposition of the *learned
operator's own dynamics*... which in turn requires deciding how a
GENERIC/port-Hamiltonian structure composes with [an] architecture, a design
question neither Spec nor Core resolves." This is not a missing
parameterisation choice of the same kind as the other four; it is a missing
architectural decomposition that Spec §2.2 names by category label without
supplying.

**Proposed wording.** Either Spec §2.2 should supply the GENERIC/
port-Hamiltonian decomposition it currently only names by category, or the
section should mark thermodynamic admissibility as a distinct, less-derived
sub-item than the other four categories — the way S-7.1 and S-7.2 already
split a SPEC part from a PASS-B/PASS-C part within one row — rather than
presenting all five categories as uniformly specified.

**Confidence.** High — ADR-030's own text states the missing piece plainly
("a design question neither Spec nor Core resolves"), and the asymmetry
with the other four categories (parameterisation choice vs. architectural
decomposition) is a difference in kind, not degree.

## E-12 — Spec §4.6 rung 4 does not distinguish "observed" from "recomputed," and a closed-form implementation can satisfy its letter while validating nothing

**Target.** Spec §4.6, rung 4 ("Volume-scaling exponent")

**Kind.** Correction

**Discovered.** Phase 2 review (post-implementation audit of
`src/omi_domains/flagship/classb_bend.py`, Tier I½/ADR-035), by re-reading
the committed rung-4 call site against Spec §4.6's text.

**Finding.** Spec §4.6 rung 4 reads in full: "Volume-scaling exponent — at
≥3 driven volumes, chosen to straddle ℓ_D where §4.4's reduction is
expected." This states *what* to compute (an observed exponent, compared
against a predicted one) but not *how* "observed" must be obtained. The
flagship's Tier I½ Class B campaign
(`src/omi_domains/flagship/classb_bend.py:205–209`) satisfies rung 4's
letter this way:

```python
def _failure_probabilities(thicknesses: FloatArray, ell_d: float, p0: float) -> tuple[FloatArray, FloatArray]:
    volumes = FIXED_FOOTPRINT_AREA * thicknesses
    counts = np.array([n_eff(float(v), ell_d, float(t)) for v, t in zip(volumes, thicknesses)])
    failure_probabilities = 1.0 - (1.0 - p0) ** counts
    return volumes, failure_probabilities
```

`failure_probabilities` here is the closed-form weakest-link formula
applied to `n_eff`'s own output — the same function
`validate_volume_scaling_exponent`'s `predicted_exponent` is supposed to
represent "the exponent n_eff's regime predicts." Fitting an exponent from
data generated by the formula being checked against necessarily recovers
that formula's own exponent, up to floating-point error: the committed
residuals were `2.22e-16` (bulk) and `-2.23e-16` (thin) — machine epsilon,
not a measurement. Re-running rung 4 with a genuine empirical
`P_fail` — drawing `round(N_eff)` i.i.d. sub-volume samples per trial,
taking the per-trial maximum driver value, thresholding, and repeating
across many trials — produces residuals of `-1.8e-3` (bulk) and `1.8e-2`
(thin): three to four orders of magnitude larger, and of the size genuine
sampling noise should be. The gap between "closed-form residual ≈ 1e-16"
and "empirical residual ≈ 1e-3–1e-2" is entirely attributable to Spec §4.6
never having said which of these two "observed" is required — an
implementation that never samples anything can still produce a rung-4
number and a low residual, and nothing in the text flags that number as
uninformative.

**Proposed wording.** Append to Spec §4.6, rung 4: "The observed exponent
MUST be obtained from data independent of the model being validated — by
direct measurement, or by Monte Carlo simulation of the weakest-link
construction (drawing `N_eff` sub-volumes, recording the per-trial maximum
driver value, thresholding) — never by substituting the predicted count or
probability back into the same formula used to state the prediction. A
rung-4 residual computed from the latter is not a validation and MUST NOT
be reported as one."

**Confidence.** High — the closed-form/empirical residual gap
(`1e-16` vs `1e-3`–`1e-2`) is a direct, reproducible measurement, not an
interpretation; re-run command and full output are in this session's
transcript (`empirical_rung4.py`, not committed — see the Phase 2 review
report for the exact figures per thickness).

## E-13 — Spec §4.3 gives no guidance for the degenerate β ≈ 1 case, where Proposition 4.1's transfer is a no-op

**Target.** Spec §4.3 ("Tail transfer: the defect-population → driver map")

**Kind.** Demotion

**Discovered.** Phase 2 review, by comparing the flagship Class B
campaign's declared physics-map exponent (`BETA = 1.0`,
`src/omi_domains/flagship/interface.py`'s item 4b) against Spec §4.3's own
worked example.

**Finding.** Spec §4.3's own "sanity check" is explicit that the point of
Proposition 4.1 is to demonstrate a *nontrivial* rescaling: "for defect-
initiated fatigue with a threshold scaling as `(√area)^-1/6`, the driver
exponent... is β = 1/6, so ξ_D = ξ_a/6: a heavy-tailed inclusion population
produces a markedly *lighter*-tailed strength distribution... **Any
implementation of §4 SHOULD reproduce a known scaling of this kind as a
check on Ψ**." At β = 1, `tail_index_transfer(xi_a, beta) = beta * xi_a`
(`src/omi/classb.py:27–32`) returns `xi_a` unchanged — the flagship
campaign's own `xi_d_hat` is numerically identical to `xi_a_hat` in every
run (confirmed: `xi_d_hat == pytest.approx(xi_a_hat)` passes in
`tests/test_flagship_classb_bend.py`). `estimate_tail_index_hill` and

**Confidence.** Medium — the degeneracy at β = 1 is a direct reading of

## E-14 — Class B's dimensional-reduction claim (Proposition 4.2) cannot be validated as an emergent phenomenon at Tier I or Tier I½; only formula self-consistency is checkable until Core §2.5's body-indexed state resolves — one blocker, surfacing in two places (the flagship bend campaign and the ranking-inversion oracle)

**Target.** Spec §4.4 (dimensional reduction) read against Core §2.5 (the
body-indexed state, `[Pass C]`)

**Kind.** Correction

**Discovered.** Phase 2 review, prompted directly by the question "does
thickness-insensitivity emerge from sampling a driver field correlated over
`ℓ_D > t`, or only from `n_eff`'s branch selection?"

**Finding.** Spec §4.4 states the dimensional-reduction mechanism as a
consequence of the driver field's *spatial* correlation structure relative
to the process zone's own spatial extent: "correlation length `ℓ_D`
obtained from the two-point autocorrelation of the driver field... When
`ℓ_D` exceeds the zone thickness `t`, independent units tile only
in-plane." This presumes the driver field has a genuine spatial coordinate
*through the thickness* for `ℓ_D` to be compared against `t` in the first
place. Core §2.5 marks exactly this — "a production unit is not one state
but a field of states indexed by material coordinate — position along the
body, **through-thickness**, across-width" — `[Pass C]`, requiring "the
registration operator relating apparatus-frame observations to material
coordinates," and CLAUDE.md §9 lists "body-indexed state and the
registration operator (Spec §5.2)" as an anti-goal. The flagship's state
schema has no such coordinate: every component in
`src/omi_domains/flagship/state.py:10–20` is declared with dimension `1`
(a scalar), and `BendAngle.evaluate` (`src/omi_domains/flagship/
readouts.py:183–197`) varies only the *driving control* across its
through-thickness quadrature — `for i, eps in enumerate(strain): ...
operator.respond(control)` — never the bound `operator`'s state, so
`inclusion_content` (the defect-population component) is constant across
every quadrature point in a single evaluation. The `ℓ_D` the Phase 2
campaign estimates is measured along a *different* axis entirely (an
invented "site" coordinate standing in for separate specimens/locations,
`classb_bend.py`'s `_correlated_pareto_field`), never coupled to the
through-thickness axis at all. Consequently, the thin-regime
thickness-insensitivity this repository reports — both in the original
closed-form campaign and in the empirical resampling attempted for E-12 —
follows entirely from `n_eff`'s algebraic identity
(`(volume/thickness)/ℓ_D² = FIXED_FOOTPRINT_AREA/ℓ_D²`, thickness cancelling

numerically: `n_eff` returns `12.755102040816325` at three different
declared thicknesses (`0.21`, `0.42`, `0.70`) in the same run. No sampling

occurs, and per Core §2.5's own `[Pass C]` status this cannot be made to
occur without the body-indexed state refinement — which is out of scope
(CLAUDE.md §9) and was **not** synthesised to force this validation to look
more real than it is.

the oracle as "the quantitative content of Core §3.6's claim that 'the

`severity_a`/`severity_b` constants (`known_ranking_inversion.py:27-31`) —
there is no driver field, no spatial sampling, and no `estimate_correlation_length`
call anywhere in this oracle; `truth()` is simply the two process-zone
thicknesses (`THICK_ZONE_THICKNESS`, `THIN_ZONE_THICKNESS`) the parameters
were chosen to invert at. `test_the_inversion_is_driven_by_dimensional_reduction_not_by_severity_alone`
(`tests/oracles/test_known_ranking_inversion.py:53-75`) asserts
`n_eff_a_thick == n_eff_a_thin` and `n_eff_b_thin > n_eff_b_thick` — properties
of `n_eff`'s own regime-branch arithmetic under chosen constants, the same
kind of check as the bend campaign's thin-regime test, not a recovery of an
independently-generated ground truth from a spatially-correlated field. The
oracle is a legitimate unit-level check that the two-regime branch logic is
wired correctly (CLAUDE.md §7's "known by construction" philosophy applies
to *that* claim), but it is not, and was never built to be, evidence that
the reduction is an *emergent* consequence of sampling a real
through-thickness-correlated driver field — the same gap E-14 already
names for the bend campaign, surfacing here because this is the only other
place in the repository `n_eff`'s regime split is exercised at all.

**Proposed wording.** Append to Spec §4.4: "Proposition 4.2's dimensional
reduction is a claim about the driver field's spatial structure relative to
the process zone. An instantiation whose Tier I (or Tier I½) state has no
spatial coordinate through the suppressed dimension — i.e., every domain
before Core §2.5's body-indexed state refinement is adopted — cannot
observe the reduction as an emergent consequence of sampling; it can only
confirm that its own `N_eff` formula is evaluated self-consistently across
thicknesses. Reports MUST distinguish these two and MUST NOT present the
latter as validation of the former."

**Confidence.** High — every element (Core §2.5's `[Pass C]` marker,
CLAUDE.md §9's anti-goal listing, the flagship schema's all-scalar
declaration, `BendAngle`'s control-only quadrature loop, the numeric
identity of `n_eff` across three thicknesses, and `known_ranking_inversion.py`'s
absence of any driver field or `estimate_correlation_length` call) is a
direct quote or a direct re-run, not an inference.

## E-15 — Spec §4.2's join-threshold sensitivity MUST varies only `u`, so it cannot surface the dominant, already-acknowledged source of `p0` uncertainty that §4.6 rung 2 requires be measured with its own error bar

**Target.** Spec §4.2 ("An implementation MUST state the join threshold,
the quantile at which it sits, the number of ensemble members above it, and
the sensitivity of the final risk estimate to `u` over at least a factor of
two in exceedance probability") read against §4.6 rung 2 ("Defect population
tail `ξ_a` — independently measured by established characterisation
methodology, **with its own error bars**") and §4.3 (Proposition 4.1, tail
transfer `ξ_D = β ξ_a`)

**Kind.** Correction

**Discovered.** Follow-up review of E-12's fix: "was `p0` calibrated or
chosen, and empirically it reads ~13-15% lower than the model-based value —
is the gap threshold instability or GPD fit bias?" Sharpened on a second
pass: the mechanism needed confirming with more than six reseeds, a
bias/noise decomposition, a check against Hill's own theoretical standard
error, and a scaling demonstration rather than a single-seed inference.

**Finding.** All four of Spec §4.2's MUSTs are satisfied and directly
verifiable in `run_bend_classb_campaign`'s output
(`src/omi_domains/flagship/classb_bend.py`, `omi.classb.JoinDiagnostics`):
join threshold `108.070`, quantile `0.9`, `50` ensemble members above it,
and a sensitivity sweep over quantiles `0.90`–`0.975` — a range whose own
marginal exceedance probability spans `0.10` down to `0.025` (4×, exceeding
Spec's "at least a factor of two"). Re-run at seed 0: the resulting
design-point risk estimate varies only `0.0459`–`0.0476` across that span
(ratio `1.037`) — **the gap is not threshold instability**.

**Note, Spec §4.6 rung 2 already requires the missing diagnostic — for
`ξ_a`, just not for the composite `p0` estimate §4.2 governs.** Rung 2
requires `ξ_a` be measured "with its own error bars"; the defect is not that
Spec never asks for tail-index uncertainty, but that §4.2's *own* stated
sensitivity MUST — the one an implementation is told to run to bound `p0`'s
uncertainty — varies only the join threshold `u`, never `ξ_a`'s error bar,
so satisfying §4.2 in full gives no signal that this second source exists,
let alone dominates.

**Bias and noise, decomposed (300 reseeds, not six).** Re-running the
campaign's `_correlated_pareto_field`/`estimate_tail_index_hill` construction
(`top_fraction=0.1`, `N_SITES=500`, so `k=50` tail observations) at 300
independent seeds against the true generative shape (`XI_A_INCLUSION=0.4`):
`mean(ξ_a_hat) = 0.342` (a **displaced mean**: bias `-0.058`, `-14.5%`
relative — a genuine Hill-estimator bias, not sampling noise) and
`SD(ξ_a_hat) = 0.168`. Hill's i.i.d. theoretical standard error,
`ξ_a/√k = 0.4/√50 = 0.0566`, is roughly **3.0×** smaller than the observed
SD — both effects (a displaced mean and an inflated spread) are present
simultaneously, as anticipated.

**The 3× excess variance and the displaced mean are not threshold-selection
artefacts — tested and ruled out directly.** Sweeping `top_fraction` from
`0.30` down to `0.02` (i.e., cutting deeper into the nominal tail, the fix a
"threshold too shallow, contaminated by bulk" diagnosis would predict) makes
the **relative bias worse, not better**: `-4.7%` at `top_fraction=0.30`
(`k=150`) rising in magnitude to `-65.7%` at `top_fraction=0.02` (`k=10`),
while the SD-to-theory ratio stays in the `0.76`–`3.24` band with no
monotonic improvement at shallower cuts. This is the opposite of what
bulk-contamination predicts, and rules it out as the mechanism here — a
result made possible only because `_correlated_pareto_field`'s marginal is
*exactly* Pareto by construction (probability-integral transform), so there
is no separate bulk regime for a shallow cut to leak in from. The actual
driver is **spatial correlation reducing the Hill estimator's effective
independent sample size below its nominal `k`**: adjacent sites within one
correlation length (`~2.0`, i.e. `~20` site-spacings at `SITE_SPACING=0.1`)
are strongly correlated, so the top-`k` order statistics cluster in space
rather than sampling `k` independent extremes.

**Demonstrated, not merely inferred, to scale as `1/√k`.** Varying `N_SITES`
from `125` to `4000` at fixed `top_fraction=0.1` (200 reseeds each): `SD ×
√k` converges to a stable constant (`0.50, 0.94, 1.09, 1.24, 1.28, 1.30` as
`N_SITES` runs `125→4000`) rather than growing or diverging — a genuine
`C/√k` law, just with `C ≈ 1.3` in place of the naive `ξ_a = 0.4` (an
inflation factor consistent with a much smaller effective sample than the
nominal `k`, from spatial clustering). The downstream quantity that actually
matters — `|p0_hat − p0_true|` — was directly measured at the same `N_SITES`
sweep (60 reseeds each, `p0_true = 0.0399` from the earlier `2×10⁶`-sample
ground truth): mean absolute gap shrinks monotonically, `0.0198 → 0.0151 →
0.0106 → 0.0074 → 0.0052` as `N_SITES` runs `250→4000`, while `rmse × √k`
holds constant at `0.118`–`0.133` — the gap in the flagship campaign's own
reported `p0` is not a one-off draw; it is this scaling law evaluated at
this campaign's chosen `N_SITES=500`.

**β-dependence, and why this domain sees the worst case.**
`tail_index_transfer` is exactly `ξ_D = β·ξ_a` (linear), so an *absolute*
error in `ξ_a_hat` propagates into `ξ_D_hat` scaled by `β`, unchanged in
relative terms. At this domain's `β = 1.0` (E-13's degenerate case), the
absolute error transfers **undamped**. At Spec §4.3's own worked
sanity-check value, `β = 1/6` (defect-initiated fatigue, "a heavy-tailed
inclusion population produces a markedly *lighter*-tailed strength
distribution"), the same absolute `ξ_a_hat` error would be damped
**sixfold** before it ever reaches the GPD fit. This domain does not merely
happen to show a `p0` gap — at `β=1`, it is structurally the *worst case*
for this error-propagation mechanism among the `β` values Spec itself
discusses, which is why E-13's finding (this domain cannot exercise Prop
4.1's transfer as anything but the identity) and E-15's finding (this domain
maximally exposes tail-index estimation noise) are the same degeneracy
surfacing twice.

**Proposed wording.** Append to Spec §4.2, after the existing MUST: "Where
`ξ_a` is estimated (§4.6 rung 2) rather than supplied with a
specification-grade error bar, the sensitivity MUST above MUST additionally
be evaluated over `ξ_a`'s own estimation interval, not only over the join
threshold `u` — propagated through §4.3's transfer at the domain's declared
`β`. A stable result under threshold choice alone MUST NOT be reported as
bounding the risk estimate's total uncertainty when `ξ_a`'s own interval has
not also been swept; at `β` near 1 this second source typically dominates
the first."

**Confidence.** High — every number above is a direct re-run (300 and 200
reseeds respectively, plus a 5-point `top_fraction` sweep and a 6-point
`N_SITES` sweep, all against this repository's own campaign construction),
and the bulk-contamination alternative was tested and refuted, not merely
argued against. Medium for the proposed wording's exact form: Spec does not
specify *how* `ξ_a`'s interval should be estimated (bootstrap, Hill's own
asymptotic formula, a design-effect correction for spatial correlation) or
combined with the threshold sweep — that procedural gap is itself
unresolved here, consistent with rung 2's error bars being required but
Spec never specifying how they are obtained "by established
characterisation methodology... not by this framework."

## E-17 — Spec §9.1's OMI-2 "reachability certificates" line item does not, at the level-table text itself, restate the soundness requirement Core §5 makes unconditional — and this repository's own conformance.py demonstrates the gap is real, not hypothetical

**Target.** Spec §9.1 (OMI-2 row, "reachability certificates (§7.1)") read
against Core §5 ("Learned reachable sets are unsound and **cannot discharge
this contract**; sound certificates are constructed from the invariants
declared in §4, item 6") and Spec §7.1's own boxed definition ("A
**reachability certificate** is a functional `Φ`... with a provable bound...
Any target with `Φ` beyond the achievable bound is **provably**
unreachable")

**Kind.** Correction — to Spec §9.1's text, and to this session's own
earlier conclusion on the same question.

**Discovered.** Direct challenge to this session's prior finding
(`docs/COVERAGE.md`'s S-9.3 "Depends on" cell, first version): "presence-only
checking being satisfiable by an unsound certificate is not the absence of a
defect." Re-verified rather than defended.

**Finding.** The prior conclusion — "not a regime defect, since Spec §7.1's
hierarchy anticipates weaker, unsound-but-present certificates that would
satisfy [OMI-2's presence check]" — conflated two different things and does
not survive a careful re-read. Spec §7.1's hierarchy (forward sampling →
latent-space over-approximation → invariant certificates) lists three
*workflow tools* of increasing strength, but its own **definition box**
("A reachability certificate is a functional `Φ`... with a provable
bound...") describes only the last, sound kind — forward sampling and
latent-space over-approximation are not instances of "a reachability
certificate" under Spec's own definition; they are weaker, separately-useful
artefacts on the way to one. Core §5 is unconditional and names the
excluded case explicitly: "Learned reachable sets are unsound and **cannot
discharge this contract**." Read together, Spec §9.1's OMI-2 line item —
"reachability certificates (§7.1)" — by cross-reference already means the
sound kind; there is no textual gap in what Spec *says*, once the
cross-reference into §7.1's definition is chased.

**The gap is that this repository's own implementation did not chase it,
and nothing forced it to.** `ConformanceInputs.reachability_certificates`
(`src/omi/conformance.py:221`) is typed `tuple[str, ...] | None` — a tuple
of **strings**, not `tuple[omi.inverse.ReachabilityCertificate, ...]`. It is
entirely decoupled from `omi.inverse.ReachabilityCertificate`, the actual
sound, `Φ(s)=w·s` dataclass (ADR-031). `_check_satisfied`
(`src/omi/conformance.py:379-380`) checks only
`inputs.reachability_certificates is not None` — a caller could satisfy
`reachability_certificates_reported`, and therefore OMI-2's line item, by
passing a tuple of arbitrary description strings, with **no type-level
guarantee that a real certificate object of any kind — sound or unsound —
was ever constructed.** This is not a hypothetical risk: it is the literal
current state of this repository's own conformance-reporting code, following
directly from ADR-028's general "presence, not accuracy" philosophy (correct
for most OMI-line items — e.g. "sufficiency test run and reported" is
genuinely presence-only, its accuracy read from the residual, not
gatekept) applied without exception to a line item Core §5 treats
differently in kind: not a reporting-completeness matter but an
unconditional prohibition on the artefact class. ADR-028's philosophy is
right for most of §9.1's table and wrong for exactly this row, and nothing
in `conformance.py` or its own ADR flags the row as an exception.

**Answering the question as posed.** Not "OMI-2 as written can be claimed
with an artefact Core forbids" in the sense of a framework text defect —
Spec's own definition, chased fully, already excludes it. It **is** true
that OMI-2 **as implemented in this repository** can be so claimed, because
the implementation's type does not encode what the cross-referenced Spec
text requires. The defect is real and is best located at the boundary
between the two: Spec §9.1's level-table entry is terse enough ("reachability
certificates (§7.1)") that an implementer applying the *general* philosophy
established for the rest of the table (presence, not accuracy) — exactly
what this repository's own author did — will not be warned that this
particular row is the one exception where presence of the wrong kind is
equivalent, in Core's own terms, to absence. The same composition trap this
session's dependency sweep already found once (E-15: a diagnostic
satisfying its own stated MUST can still miss the dominant thing that
matters) recurs here at the conformance-gate level.

**Proposed wording.** Append to Spec §9.1's OMI-2 row, inline, not merely by
cross-reference: "reachability certificates (§7.1) — **sound**, per §7.1's
definition; a forward-sampling or other unsound artefact (Core §5) MUST NOT
be reported against this requirement, and an implementation checking for
this line item's presence MUST verify the reported object is of the sound,
invariant-based kind, not merely that *something* was supplied."

**Related, but not itself a framework finding: this repository's own
`conformance.py` should be corrected to match.** `reachability_certificates`
should be typed against `omi.inverse.ReachabilityCertificate` (or a
protocol requiring `.phi`/a provable-bound method) rather than
`tuple[str, ...]`, so the type system — not just documentation — prevents
what this entry found. This is an ordinary implementation-defect fix, not a
V1.4-EDITS-worthy framework correction (CLAUDE.md §10 reserves this file for
the framework, not this repo's own bugs); flagged here because the defect
is exactly what E-17's framework-level finding is about, and left as a
reported, unimplemented follow-up pending confirmation rather than
patched inline with this finding.

**Confidence.** High — the type mismatch is a direct code citation
(`src/omi/conformance.py:221,379-380`), and the Core §5 / Spec §7.1 textual
argument quotes both sources directly rather than paraphrasing. Medium for
whether "unenforceable at the conformance level" (the alternative this entry
was asked to weigh) is entirely ruled out: a sufficiently motivated caller
could still fabricate a type-correct-but-substantively-fake
`ReachabilityCertificate` (e.g. a `weight` vector for an invariant it does
not actually hold), so type-checking closes the gap this entry found but
does not make the honesty of the underlying claim self-enforcing — that
residual relies on the same good faith every other OMI line item already
depends on.
