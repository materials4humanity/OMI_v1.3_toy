# M10.2 — Baseline characterisation: control inverse vs. structure inverse

**Framing correction (before this document was taken as final).** The
first version of this document presented its flagship sweep as answering
Spec §9.3's baseline-comparison requirement without flagging, prominently
enough, which of Core §5's two distinct inverse problems it actually
tested. Spec §9.3's own claim — and ROADMAP M10.2's own phrase, "include
inverse-design hit rate... that is the axis on which tabular models are
structurally incapable rather than merely worse" — concerns the **control
inverse**: target response → driving programme, searched within the
domain's declared `𝒰_adm` and trust region (Core §5). What the original
sweep ran was a **structure inverse**: target response → incoming
composition. Core §5 is explicit that these are distinct problems;
conflating them is exactly the kind of error CLAUDE.md §10 exists to
catch. The computed numbers are unchanged and are not withdrawn — they
are a valid characterisation of the structure-inverse regime, and are
labelled as such below, not as evidence about the control inverse Spec
§9.3 actually asks about.

**Snapshot.** Sections 1–5 (flagship) generated at HEAD `85f8ac3` by
`scripts/run_m10_2_baseline_sweep.py`, seed base `1000`; reproducible
exactly by re-running that script unchanged. Section 6 (contrast) is a
later addition, generated at the HEAD stated in its own header. Per
CLAUDE.md §10, this is a point-in-time computed record — corrected by
dated addendum below its own findings, never by silently rewriting

## 0. The headline finding

**Flagship cannot exercise the operator graph's distinguishing
capability, because its declared readouts are invariant to its declared
controls.** `AggregateHardness` and `BendAngleAtReferenceGeometry` are
both, by Core §2.6's property/performance distinction, functionals of the
constitutive operator alone — confirmed directly
(`tests/test_baseline_characterisation.py::test_flagships_declared_readouts_do_not_respond_to_the_process_control`):
sweeping `heating_intensity` from 2 to 14 changes neither readout's value
at all. A control-inverse comparison (target response → recipe, under
`𝒰_adm`, Core §5) is therefore **vacuous** on this domain's two declared
readouts: every point in `𝒰_adm` gives an identical response, so there is
nothing for a trust region or an admissibility constraint to bind against,
and no axis on which an operator graph's differentiable forward map could
out-search a tabular model's black-box one. Spec §9.3's actual claim
cannot be tested on flagship's declared readout catalogue as it stands.

What sections 1–5 below report — and what still stands, correctly
labelled — is a **structure inverse** run instead, over the one axis
flagship's readouts do respond to (incoming composition:
`inclusion_content`, `prior_grain_size`). This is a real, valid
comparison of a genuinely different problem (Core §5 names both; neither
subsumes the other), not a weaker substitute for the control inverse.

**Section 6 attempts the control inverse on contrast, and it is
testable there — sensitivity was verified first.** Contrast's
`DendriteRisk` responds substantially and monotonically to its declared
control (`current`); the control inverse is not vacuous on this domain.
Run under a declared admissible range and trust region (Core §5), the
result is genuine but not the one the framework's text anticipates:
**inside the trust region all three models are competitive, but past
it, only the tabular linear model (ridge) generalises — the
gradient-boosted-tree baseline and the (unconstrained) operator-graph
contestant both fail to extrapolate, indistinguishably from each
other, at every record count tested.** The most likely reason, and the
natural next investigation this result points to: the operator-graph
contestant used here has none of `src/omi/constraints.py`'s hard
structural constraints wired in — Spec §2.2's own motivation for
building them is exactly this kind of extrapolation robustness, and
this comparison did not test a *constrained* operator. See §6 in full.

## 1. Design of the structure-inverse sweep (flagship) — ADR-039, docs/DECISIONS.md

- **Tabular baselines**: `RidgeRegressor` (closed-form ridge) and
  `GradientBoostedTreeRegressor` (from-scratch boosted regression trees),
  both `src/omi/baseline.py`, numpy-only — no new pinned dependency.
- **Operator-graph contestant**: a `DeepONetOperator` (M8,
  `src/omi/learning.py`) trained on the *same* record count as the tabular
  models at each configuration — not the exact analytic simulator, which
  would win every cell trivially and test nothing about data efficiency.
  The simulator is ground truth only, never a contestant.
- **Domain and axis**: flagship, swept over its **composition** axis
  (`inclusion_content`, `prior_grain_size` — both of which the constitutive
  operator's response formula genuinely depends on), *not* its control
  axis, per §0 above. The inverse-design comparison below is accordingly a
  structure inverse (Core §5: target response → incoming composition).
- **Sweep axes**: labelled-record count `N ∈ {20, 50, 200}`;
  window-width-to-noise ratio `∈ {2, 10, 50}` (noise fixed at `σ=0.5`,
  window = the swept `inclusion_content` range); readout `∈`
  `{AggregateHardness, BendAngleAtReferenceGeometry}`. 18 configurations.
- **Metrics**: forward RMSE against the true simulator on a fixed,
  independent 200-point held-out set; **structure**-inverse-design hit
  rate — grid-search inversion through each model's own predicted response
  at a fixed grain size (`20.0`), scored against the true simulator with
  tolerance `0.5`, over 8 evenly-spaced targets spanning the true response
  range. (No `𝒰_adm`/trust region applies here — those are properties of
  the control axis this sweep does not use; see §6 for the sweep where
  they do apply.)

## 3. The honest outcome — structure-inverse regime, flagship

**Ridge wins almost the entire swept regime, on both metrics, for both
readouts.** Of 18 configurations, Ridge has the best (or tied-best) RMSE
in 16 and the best (or tied-best) hit rate in 15. This is not a close
contest across most of the grid — at wide windows (ratio ≥ 10) Ridge's
RMSE is frequently 3–10× smaller than either alternative, regardless of
record count.

**Why, stated plainly rather than left implicit**: the true response, at
this domain's fixed control and swept composition, is very close to an
affine function of `inclusion_content` (the constitutive operator's own
formula, `src/omi_domains/flagship/readouts.py`, is exactly linear in
`inclusion_content`) with only a mild nonlinearity from `prior_grain_size`
(`20/(1+|grain_size|)`, nearly flat over the swept range `[14, 26]`).
Ridge's own inductive bias matches the true function almost exactly; GBT's
piecewise-constant tree structure and DeepONet's from-scratch, data-hungry
network both pay a real cost for flexibility the true function does not
need, especially at low record counts. **This is Spec §9.3's own
qualitative caveat, quantified for the structure-inverse regime**: a
near-linear regime is exactly a case for tabular regression — this sweep
did not have to search for that boundary, it fell inside it almost
everywhere by the toy domain's own construction. (This says nothing about
the control-inverse regime, which flagship cannot test at all; see §0.)

**GBT is the weakest of the three almost everywhere.** It wins outright
only at `N=20, ratio=2` (both readouts) — the narrowest window, where its
coarse splits happen to interpolate adequately over a small range — and
degrades sharply at wide windows with few records (RMSE up to 7.1,
hardness `N=20, ratio=50`), the opposite of a graceful degradation.

**DeepONet's one clear win, and where it is competitive at all**: at
`N=200, ratio=2` (hardness), DeepONet's RMSE (`0.060`) is the single best
result in the entire table, beating Ridge (`0.068`) outright. More
broadly, DeepONet is competitive with Ridge (within roughly 2×) mainly at
the highest record count and/or narrowest windows — the regime with the
most data and the least range to cover, i.e. where a data-hungry learned
approximator is least disadvantaged. At low record counts and wide
windows it is generally the worst performer alongside GBT (e.g. RMSE
`5.4`, hardness `N=20, ratio=50`).

**The regime boundary, stated as ROADMAP asks, for the structure-inverse
regime**: in this toy domain, tabular regression (specifically, linear/
ridge regression) wins almost everywhere the sweep covers; the operator
graph only reaches parity or a narrow win at the highest tested record
count combined with the narrowest tested window. No configuration in this
sweep shows the operator graph winning by a wide margin, and no cell shows
GBT winning convincingly. **A wider record-count sweep (beyond `N=200`)
would very plausibly show the operator graph's relative position
continuing to improve** — the trend from `N=20→50→200` is consistently
upward for DeepONet's competitiveness — but that regime was not tested
here and is not claimed.

**The Type-2 axis did not differentiate as expected, and that is worth
stating rather than hiding.** `BendAngleAtReferenceGeometry`'s pattern
across the sweep closely mirrors `AggregateHardness`'s, because ADR-037
holds the readout's geometry argument (`thickness`, `curvature`) **fixed**
— at fixed geometry, `BendAngle`'s own aggregation (`max` over
through-thickness quadrature, Core §7.1/ADR-035) is, like
`AggregateHardness`, still exactly linear in `inclusion_content` (verified
directly: `inclusion_content` enters every quadrature point identically,
so it cannot change which point achieves the max, and the response is an
additive shift of whichever point already dominated). **A genuine test of
the "geometry-dependent response" axis would need to sweep geometry
itself** (`thickness`/`curvature`) as an additional tabular feature and an
additional learned-operator input — this harness does not do that, and
the axis as actually swept here (readout identity alone, geometry fixed)
does not distinguish Type-0 from Type-2 in any way this sweep detected.

## 5. Limitations, stated rather than concealed (structure-inverse sweep)

1. **Flagship's declared readouts cannot test the control inverse at
   all** — see §0. This is now the headline finding, not a buried scoping
   note; §6 attempts the control inverse on contrast instead.
2. **The Type-2 axis, as swept (readout identity, fixed geometry), did not
   distinguish Type-0 from Type-2** — see §3. Testing geometry-dependence
   properly needs geometry itself in the sweep.
3. **`DeepONetOperator` was trained on a 2-feature carrier schema**
   (`inclusion_content`, `grain_size`) rather than the full 7-dimensional
   flagship state, so this is a fair comparison of *readout regression*
   under a shared data budget, not a test of full-state reconstruction
   fidelity — stated explicitly since the distinction matters for reading
   the RMSE numbers correctly.
4. **Hyperparameters (GBT depth/estimators, DeepONet width/epochs, ridge's
   `alpha`) were fixed once, not tuned per configuration** — a genuine,
   accepted simplification (ADR-039): a full per-cell hyperparameter
   search was out of scope for this milestone's tractable, 18-configuration
   sweep.
5. **One seed per configuration** — the exact numbers above carry sampling
   noise from a single draw; the qualitative pattern (Ridge's broad
   dominance, GBT's fragility at wide windows/low N, DeepONet's improving
   trend with record count) is the reportable finding, not the specific
   third decimal place.

## 6. Contrast — the control-inverse attempt (Core §5)

**Snapshot.** Generated at HEAD `59e8f28` by
`scripts/run_m10_2_contrast_control_inverse_sweep.py`, seed base `2000`.

**Sensitivity verified first, as instructed, before running anything.**
Contrast's declared control (`current`, Core §7.2's usage-determined duty
cycle) drives `DendriteRisk` directly and substantially — confirmed
(`tests/test_baseline_characterisation.py::test_contrasts_dendrite_risk_responds_to_the_declared_control`):
risk rises monotonically from `0.141` at `current=0.2` to `3.165` at
`current=5.0`, strictly increasing at every sampled point. Unlike
flagship, contrast's declared readout genuinely responds to its declared
control — Spec §9.3's actual claim (the control inverse) is testable on
this domain, not vacuous. This is a real difference between the two
implemented domains, not an artefact of how each was swept.

**Design.** `𝒰_ADM = [0.2, 5.0]` and `𝒰_TRUST = [1.0, 3.0]` (Core §5's
trust region — "restrict to where the surrogate is calibrated") are this
investigation's own **stated assumptions**: `CONTRAST_DECLARATION`'s
control space is prose-only ("bounded by manufacturer charge/discharge
limits"), with no numeric bound to draw from — the same gap flagship's
declaration has, noted but not separately investigated here (see E-26,
`docs/V1.4-EDITS.md`, on the adjacent finding that item 2 never requires
declaring readout sensitivity in the first place). All three models
train on `current` drawn **only from `𝒰_trust`** — a realistic
data-collection assumption (you calibrate near typical operating
conditions, not across the apparatus's full range) — then are scored
twice: **in-trust** (a held-out draw from `𝒰_trust` itself) and
**extrapolation** (a held-out draw from `𝒰_adm` *outside* `𝒰_trust`).
Inverse-design grid search spans the *full* `𝒰_adm` in both cases (a real
search considers the whole admissible set), with targets split the same
way. `N ∈ {20, 50, 200}`, tolerance `0.3`.

### The honest outcome — a genuine, somewhat surprising finding

**Inside the trust region, DeepONet is competitive or best** (RMSE
`0.058→0.023→0.020` as `N` grows, beating Ridge at `N=20,50` and losing
narrowly at `N=200`) — unsurprising, since the true response is close to
affine over `𝒰_trust` too and all three models fit it well given enough
data.

**Outside the trust region, the result inverts sharply, and neither
flexible model — GBT or DeepONet — shows any advantage over the other.**
Ridge's extrapolation RMSE *improves* with more data (`0.303→0.070→0.066`)
and its extrapolation hit rate reaches `1.00` by `N=50`. GBT's
extrapolation RMSE is **consistently poor and does not improve with
record count** (`0.753→0.689→0.613`) — the textbook tree-model failure
mode: a boosted tree ensemble predicts a **constant** (the boundary
leaf's value) for any input past the training data's range, so it cannot
extrapolate a trend at all, only hold flat. **DeepONet's extrapolation
RMSE is equally poor and, if anything, gets slightly worse with more
data** (`0.344→0.346→0.423`) — statistically indistinguishable from GBT's
failure mode, not closer to Ridge's success. Both GBT's and DeepONet's
extrapolation hit rate are **stuck at `0.50` at every record count
tested** — more data does not help either of them search past the trust
region at all, while Ridge reaches `1.00`.

**Why this matters, stated plainly.** Core §5 and ROADMAP M10.2 both
frame inverse-design extrapolation as "the axis on which tabular models
are structurally incapable rather than merely worse" — the operator
graph's differentiable, physically-groundable structure is supposed to
be the advantage here. **This comparison does not show that advantage.**
The most likely reason, stated as a scoping limitation rather than a
refutation of the framework's claim: the `DeepONetOperator` used here is
M8's **generic, unconstrained** branch/trunk architecture — a plain
data-fitted neural network with no injected physics. `src/omi/constraints.py`
(M8, Spec §2.2) exists specifically to give a learned operator hard
structural constraints (monotonicity, conservation, range) that a purely
data-fitted network does not have, and Spec §2.2's own motivation for
building it is exactly extrapolation robustness — but this comparison's
harness does not configure `DeepONetOperator` to use it. **A second, compounding limitation**: this comparison's inverse-design
search is a naive grid search over each model's *own predictions*,
applied identically to all three — it does not exploit the operator
graph's differentiability, `src/omi/inverse.py`'s gradient-based
apparatus-parameterised search, or its reachability certificates at all.
Core's actual mechanism for the operator graph's claimed advantage is
this machinery, not merely "a neural network was used" — a grid search
treats the operator graph exactly like a black box, the same way it
treats the tabular models, so this comparison could not have detected
the advantage even if the operator itself had been constrained.

**The finding as run is real and worth recording as-is**: an
*unconstrained* neural operator, searched by grid inversion rather than
by the framework's own gradient/certificate machinery, shows no
extrapolation advantage over gradient-boosted trees on this domain, at
this record-count range. **What remains untested**: whether a
*constrained* operator (wired to `src/omi/constraints.py`), inverted via
`src/omi/inverse.py`'s actual apparatus-parameterised search rather than
a naive grid, recovers the advantage Core's text claims — that is the
natural next investigation this result points to, not performed here.

### Limitations (contrast sweep)

1. **`𝒰_ADM`/`𝒰_TRUST` are stated assumptions**, not drawn from a declared
   numeric bound (neither implemented domain has one — see E-26).
2. **The `DeepONetOperator` used is unconstrained** — see above. This is
   the central limitation of this section's finding, not a minor caveat.
3. **The inverse-design search is a naive grid search over each model's
   own predictions, identical across all three models** — it does not
   exploit `src/omi/inverse.py`'s gradient-based, apparatus-parameterised,
   certificate-aware search, which is the actual mechanism Core attributes
   the operator graph's claimed advantage to. This compounds limitation 2:
   even a constrained operator's advantage might not show up under a grid
   search that treats it as a black box.
4. **A single fixed incoming cell state** was used throughout, varying
   only `current` — a deliberate simplification to isolate the control
   axis cleanly, matching this section's purpose as a control-inverse
   test (unlike §1-5's composition-axis structure-inverse test).
5. **One seed per configuration** — as in §5, the qualitative pattern
   (Ridge's extrapolation success, GBT's and DeepONet's shared failure to
   extrapolate) is the reportable finding, not the specific decimal place.

### Addendum (2026-07-28, HEAD `a1ec522`): re-run with hard constraints and a genuine gradient-based control search (ADR-040)

Per CLAUDE.md §10, this section is a point-in-time snapshot; the
correction below is an addendum appended after it, not a rewrite of the
numbers above, which stand as the honest characterisation of the
*unconstrained, grid-searched* configuration they were computed for.

**Diagnosis of the original `0.50` plateau, done first, before anything
below was interpreted.** The instruction that prompted this re-run
specifically asked for this diagnosis before any reinterpretation, because
an exact, record-count-invariant `0.50` across two unrelated model
families is more consistent with a degenerate search than with matched
generalisation failure. Reproducing the original `N=50` run and inspecting
the grid search's actual proposals directly (not just the aggregate hit
rate) showed **two different mechanisms, not one**:

- **GBT's plateau is a pure degenerate-search artifact.** A boosted tree
  ensemble's predictions are *exactly* constant beyond the training
  feature range (confirmed by direct comparison of the predicted values,
  not merely their closeness) — this is a structural property of tree
  ensembles, not a training-data-limited effect. The grid search's
  `argmin` then ties across the entire flat region, and NumPy's
  first-occurrence tie-break resolves every tie to the same point (the
  low edge of the search grid), regardless of the true optimum. The
  resulting `0.50` is an accident of tie-breaking convention, not a
  meaningful measure of GBT's extrapolation ability.
- **The original DeepONet's plateau was closer to genuine, if
  quantitatively insufficient, extrapolation.** Its predictions were *not*
  exactly flat outside the training range (confirmed directly: predictions
  at `current=3.0` and `current=5.0` differ materially) — it extended the
  trend somewhat, but undershot the required target value even at the
  `𝒰_adm` boundary, so the grid search saturated at that boundary because
  it was the closest approach available. A real range-compression
  limitation, not a tie artifact.

These have different implications, as anticipated: GBT's number says
nothing about extrapolation at all, while the original DeepONet's number
reflected a real, if inadequate, extrapolation attempt.

**Correcting a premise before reporting the re-run.** The request to
"connect... `inverse.py`'s gradient-based control search" presupposed that
function already existed. It did not — confirmed directly
(`grep -n "gradient\|optimize\|scipy.optimize" src/omi/inverse.py` returned
zero matches before this work started). `gradient_control_search`
(projected gradient descent over an `ApparatusParameterization`'s box
bounds) is new machinery added to `src/omi/inverse.py` by this re-run
(ADR-040, `docs/DECISIONS.md`), not a reconnection of something dormant.
This is reported plainly rather than silently absorbed.

**The re-run's design (ADR-040).** The operator-graph contestant is
rebuilt as a `ConstrainedMonotoneOperator`
(`tests/test_baseline_characterisation.py`): a fixed `K=60`-point grid
spans `𝒰_ADM`; a learnable raw-parameter vector passes through
`src/omi/constraints.py`'s existing `monotone_increasing`
(`positive` + cumulative sum) to produce a risk profile that is
non-decreasing *by construction*, for any parameter values whatsoever —
violating monotonicity is not representable, the hard-constraint property
Core §4.1/Spec §2.2 and CLAUDE.md invariant 5 require and the original
unconstrained `DeepONetOperator` lacked. Prediction between grid points is
linear interpolation (itself monotone, preserving the guarantee). It is
inverted, per target, by `gradient_control_search` under `𝒰_adm`, and the
trust region is checked and reported as an **active diagnostic on every
search result** (whether the returned control lies inside `𝒰_TRUST`),
mirroring `src/omi/inverse.py`'s existing ordered `diagnose_infeasibility`
discipline (ADR-033) rather than folding trust-region status silently into
the raw hit/miss score. Ridge and GBT are byte-for-byte unchanged from
above.

**A second diagnosis, found while building this contestant, reported for
the same reason as the first.** An initial version initialised the
monotone operator's raw parameters near zero, on the (wrong) assumption
that "near-zero parameter" would mean "near-zero contribution" to the
profile. It does not: `positive` is `softplus`, and `softplus(0) ≈ 0.693`,
not `0` — confirmed directly. With roughly 25 of the 60 grid cells never
touched by a training-data bracket (everything outside `𝒰_TRUST`), each
contributed its own untrained `≈0.693` default increment to the monotone
cumulative sum, producing a nonsensical extrapolated profile that ran away
far above the true response (`rmse_ex ≈ 8.3`, extrapolation hit rate
`0.00` — a **worse** apparent failure than either original contestant's,
and, like the original `0.50`, an artifact of an implementation choice
rather than a finding about the framework). Fixed by initialising raw
parameters strongly negative, so `positive(raw_params) ≈ 0` by default and
an untrained cell contributes ≈0 to the cumulative sum — a genuine
"no evidence of further increase" default under a constraint that still
forbids decrease. That fix then exposed a **second-order effect**: the
strongly-negative initialisation sits in `positive_grad`'s
(`sigmoid`) near-flat region, so plain gradient descent moved the
trained-region parameters only negligibly within a few hundred epochs (a
fitted profile that stayed nearly flat across the whole grid, including
inside `𝒰_TRUST`). Switched to Adam (from-scratch, no torch, matching
ADR-029/`learning.py`'s existing precedent) for training, since it
rescales each parameter's step by that parameter's own gradient history
rather than the raw gradient magnitude — this converges to a profile that
tracks the true response well inside `𝒰_TRUST` (see below).

**In-trust, the constrained operator is now the best-fitting model at
every `N` tested** (RMSE `0.069/0.031/0.034` vs. Ridge's
`0.123/0.037/0.012` and GBT's `0.143/0.049/0.049`) — the hard monotonicity
constraint matches the true response's actual shape, which helps sample
efficiency exactly as Spec §2.2 motivates, most visibly at `N=20`.

**Outside the trust region, `gradient_control_search` behaves
genuinely differently from grid search — it is not tie-broken to a fixed
boundary.** The `outside_trust` column shows the search actually leaving
`𝒰_TRUST` (unlike GBT's grid-search artifact, which never needs to "leave"
anything — the tie-break point is fixed regardless of the target).
Direct inspection of the search trajectories shows a **third, distinct
plateau mechanism**, different again from both mechanisms diagnosed
above: the constrained operator's profile is, by construction, exactly
flat past wherever training evidence ends (the "no evidence of further
increase" default fixed above). `gradient_control_search`'s gradient step
is `2 * residual * forward_grad(u)`, and `forward_grad` is the
*operator's own* local slope — which is ≈0 throughout that flat region.
Once the search enters the flat region, its own gradient vanishes and it
stops moving, however large the residual against the true target still
is. This is a genuine optimisation stall caused by the constrained
operator's own designed extrapolation shape, not a tie-break accident and
not (as with the original DeepONet) a range-compression undershoot with a
live gradient — a third mechanism, with its own distinct implication:
a hard constraint that is honest about having no evidence beyond its
training data also has no gradient to search with once there, and Core
§5's trust-region diagnostic exists for exactly this reason.

### A result in its own right: three unrelated mechanisms, one identical number

Across the original sweep and this re-run, three structurally different
implementations — GBT under grid search, the original unconstrained
DeepONet under grid search, the constrained operator under genuine
gradient search — have now each landed on an extrapolation hit rate of
exactly `0.50`, for three entirely unrelated reasons:

1. **GBT (grid search): a pure tie-break artifact.** The model's own
   predictions are exactly constant past the training range; `argmin`
   resolves the resulting tie to the grid's edge, regardless of the true
   optimum. This is a fact about `np.argmin`'s tie-breaking convention
   applied to a flat prediction surface — it says nothing whatsoever
   about GBT's capacity to extrapolate, because the search never
   genuinely searches once inside the flat region.
2. **The original, unconstrained DeepONet (grid search): genuine but
   insufficient range compression.** Its predictions are not flat — the
   trend continues, undershooting the required target even at the
   `𝒰_adm` boundary. This *is* a real finding about that specific fitted
   network's extrapolated range, distinct from GBT's artifact, but it is
   a finding about one particular unconstrained fit, not about "the
   operator graph" as an approximation class.
3. **The constrained operator (genuine gradient search): a
   vanishing-gradient stall on a deliberately honest shelf.** The search
   *does* leave the trust region — unlike GBT's fixed tie-break point —
   but then stalls because the hard constraint's own flat, "no evidence
   of further increase" continuation has zero local slope for
   `gradient_control_search` to climb. This is a finding about the
   *interaction* between a specific hard-constraint design and
   gradient-based search (recorded as its own entry, `docs/V1.4-EDITS.md`
   E-28, below) — not a capacity failure of either mechanism alone.

**The pre-diagnosis reading — "the operator graph plateaus at `0.50`
outside the trust region" — was wrong for all three, not merely
imprecise for one.** It is wrong for GBT because there was never a real
search to plateau: the number is a tie-break accident that would be
identical for any target landing in the flat region, information-free
about extrapolation. It is wrong, in a different way, for the original
unconstrained DeepONet: "plateaus" implies a search that got stuck, when
what actually happened is a search that found its (undershooting) genuine
optimum every time — a real limitation, but of range, not of search
behaviour. And it is wrong for the constrained operator in a third way
again: this is the only one of the three where a search process
genuinely stalls mid-optimisation, and the reason is specific to the
chosen hard-constraint architecture, not a general property of
"constrained operators" or "gradient search." Only the third mechanism
says anything about the method under test at all; the other two are
facts about a tie-breaking convention and one network's fitted range,
respectively, that happen to produce the same two-decimal number. Reading
`0.50` as a single comparable statistic across the three — which the
identical figure invites — would have been actively misleading, exactly
the failure mode the original instruction's suspicion ("more consistent
with a degenerate search... than with genuine generalisation failure")
was raised to catch.

**The required framing, checked against this re-run: unchanged.** Ridge's
extrapolation win is not a defeat for the operator graph; it reflects a
well-matched inductive bias — a linear model extrapolating a response
that is itself near-monotone and close to affine over the sampled range.
**This re-run does not change that ordering** (Ridge still reaches
`hit_ex = 1.00` at `N=50,200`; neither GBT nor the constrained operator
does), so the honest framing from the original section is retained, per
instruction, rather than re-read as a win for the operator graph now that
it is constrained.

**`𝒰_ADM` and `𝒰_TRUST` remain declared, stated assumptions of this
investigation**, not values drawn from a numeric bound either domain
declares — see E-27 (`docs/V1.4-EDITS.md`), a new entry distinct from
E-26: E-26 concerns item 2's missing *sensitivity* requirement between
controls and readouts; E-27 concerns item 2's separate absence of any
requirement that `𝒰_adm` itself be given a numeric value at all. Any
inverse-design result on either domain, including this one, rests on
assumptions supplied by the experimenter, not the framework or the
domain's own declared interface.

**Updated limitations, superseding items 2–3 above for this
contestant only:** the operator graph is now hard-constrained
(`ConstrainedMonotoneOperator`) and inverted by a genuine gradient search
(`gradient_control_search`) rather than an unconstrained network and a
naive grid search — but the resulting extrapolation stall (a vanishing
local gradient in the operator's own flat continuation) is a limitation of
*this specific hard-constraint design* (a piecewise-linear monotone
profile with no evidence-driven slope past the trust region), not
necessarily of hard constraints or gradient search in general. Items 1,
4, and 5 above still apply unchanged.
